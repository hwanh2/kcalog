# 설계

## D1. 왜 비율이 아니라 체중인가

단백질 필요량은 **제지방량에 비례**한다. 칼로리는 활동량·목표 방향으로 결정되므로 체중과 느슨하게만 연결된다. 그래서 `kcal × 비율`은 두 방향 모두에서 틀린다.

- 칼로리가 크면(증량·활동적) 단백질이 필요 이상으로 부풀어 오른다 — 3.15 g/kg까지 나온다
- 칼로리가 작으면(감량·마른 체형) 근손실을 막는 선(1.6) 아래로 떨어진다

**비율을 버리지는 않는다.** 비율은 설명하기 쉽고("탄 55 단 20 지 25"), 대부분의 회원에게 합리적인 값을 낸다. 비율로 구한 뒤 **체중으로 자르는** 구조를 쓴다 — 평소엔 비율이 보이고, 극단에서만 체중이 개입한다.

```
단백질 = clamp(목표kcal × 단비율 / 4,  체중×1.2,  체중×2.0)
```

## D2. 상한 2.0 · 하한 1.2

- **상한 2.0 g/kg** — 근거 있는 상단(2.2)보다 약간 아래다. 이 값을 넘겨도 추가 이득이 없고, 그만큼 탄수·지방을 밀어낸다.
- **하한 1.2 g/kg** — 감량기 권장선(1.6)보다 낮게 잡았다. 하한을 1.6으로 올리면 감량 회원 다수가 하한에 걸려 **사실상 감량은 비율이 아니라 체중으로만 계산**되고, 저칼로리 여성에서는 단백질이 총 칼로리의 26%를 차지해 비율이 깨진다. 하한은 바닥을 막는 안전망이지 기본 계산식이 아니다.

감량하면서 단백질을 더 원하는 회원은 **근력 운동 토글**로 20%→30% 구간으로 올라간다. 토글이 하한보다 더 정확한 신호다.

## D3. 근육량 목표를 왜 새로 받나

기존 필드로는 갈라지지 않는다.

- `Goal`(CUT/MAINTAIN/BULK)은 **체중이 어디로 갈지**다. 이 값은 **그 체중을 근육으로 채우고 싶은지**다. 감량하면서 근육을 지키려는 회원이 정확히 여기서 빠진다.
- `ActivityLevel`(LOW/MID/HIGH/VERY_HIGH)은 이미 유지칼로리에 계수로 곱해져 있다. 매크로에서 또 쓰면 **같은 신호를 두 번 반영**한다. 게다가 유산소만 하는 사람과 웨이트를 하는 사람을 구분하지 못한다.

그래서 `member.muscle_goal BOOLEAN NOT NULL DEFAULT false`를 새로 둔다.

처음에는 "근력 운동을 하는가"로 받았다가 **"근육량도 목표인가"로 바꿨다.** 묻는 것이 습관이 아니라 목표여야 이 화면의 다른 질문(감량·유지·증량)과 같은 층위가 된다. 마이그레이션이 아직 배포 전이라 컬럼명까지 함께 맞췄다 — 나중이면 새 버전 파일이 필요했다.

같은 이유로 `Goal.BULK`의 라벨을 "근육 증량"에서 **"체중 증량"**으로 고쳤다. 근육은 이제 옆 토글이 맡는다 — 둘 다 "근육"이라고 하면 무엇이 다른지 알 수 없다.

**기존 회원은 전부 `false`다.** `activity_level >= HIGH`로 백필하는 안을 검토했으나, 유산소만 하는 활동적 회원을 오분류한다. 이번 변경의 목적이 "단백질을 낮추는 것"이므로 기본값도 낮은 쪽에 두는 편이 일관된다.

**받는 곳은 온보딩 한 곳뿐이다.** 프로필에도 토글을 두었다가 뺐다 — 영양 목표 카드가 "보는 카드"인데 켜고 끄는 스위치가 섞여 성격이 흐려졌다. 대신 `updateProfile`·`UpdateMemberRequest`에서도 이 필드를 빼서, 호출부 없는 API 필드가 남지 않게 했다. 온보딩 뒤에 바꾸려면 화면이 다시 필요하다 — 그때 프로필 **편집 시트**(설정 성격의 화면)에 넣는 편이 맞다.

## D4. 온보딩 4단계(목표)에 붙인다

새 스텝(6단계)으로 분리하지 않고 **목표 스텝의 방향 선택 바로 아래**에 토글로 넣는다.

처음에는 활동량 스텝에 뒀다가 옮겼다. 활동량 옆에 있으면 "얼마나 움직이는가"의 연장으로 읽히는데, 이 값은 **무엇을 원하는가**다. 감량·유지·증량과 나란히 놓여야 "방향은 체중, 토글은 그 체중의 내용"이라는 관계가 드러난다.

문구도 그에 맞춘다 — "근육량도 목표인가요?"이고, 설명에 "감량 중에 근육을 지키고 싶을 때도 켜세요"를 붙여 증량 전용이 아님을 밝힌다.

## D5. 지방을 25%로

기존 20%는 2700kcal에서 60g = **0.82 g/kg**으로 권장 최소(0.8~1.0)에 걸쳐 있었다. 저칼로리에서는 더 내려간다(48kg 여성 1620kcal → 36g = 0.75).

지방 25%는 근력 ON/OFF 양쪽에 **똑같이** 적용한다. 근력 쪽만 20%로 두면 **토글을 켰을 때 지방이 75g→60g으로 줄어드는 역전**이 생긴다. 단백질을 올리는 몫은 탄수에서만 가져온다.

```
기본  탄 55 · 단 20 · 지 25
근력  탄 45 · 단 30 · 지 25
         ~~        ~~
      탄수만 내려서 단백질로 보낸다
```

## D6. 남은 칼로리는 탄수로

단백질이 상·하한에 잘리면 비율의 합이 100%가 아니게 된다. 남거나 모자란 칼로리는 **전부 탄수로 흡수**한다.

지방을 건드리지 않는 이유는 지방이 이미 하한선 근처이기 때문이다 — 여기서 더 깎으면 D5에서 올린 의미가 없어진다. 탄수는 셋 중 유일하게 필수 섭취 하한이 없다.

계산 순서가 곧 우선순위다: **단백질(체중) → 지방(비율) → 탄수(나머지)**.

## D7. 체중이 없으면 상·하한을 건너뛴다

`MacroTargetG.from(kcalTarget, weightKg, strengthTraining)`에서 `weightKg`가 null이면 비율만 쓴다.

온보딩이 체중을 필수로 받고 `weight_log`에 upsert하므로 실제로는 항상 있다. 다만 `MacroTargetG`는 순수 계산이라 호출부의 사정을 알 수 없고, 대시보드·리포트는 `weight_log`를 조회해서 넘긴다 — 조회가 비면 목표를 통째로 null로 만드는 것보다 **비율값이라도 주는 편**이 낫다. 이 경로는 기존 동작(비율만)과 같다.

## D8. 대시보드가 체중을 읽어야 한다

`MacroTargetG`에 체중이 필요해지면서 호출부 세 곳의 사정이 갈린다.

| 호출부 | 체중 출처 |
| --- | --- |
| `MemberService.suggestKcal` | `request.weightKg()` — 이미 손에 있다 |
| `ReportService.get` | `weightLogRepository`를 이미 주입받고 `latest`를 조회하고 있다 |
| `DashboardService.get` | **없다** — `WeightLogRepository`를 새로 주입한다 |

대시보드에 리포지토리가 하나 늘지만, 이미 `MemberRepository`를 직접 쓰고 있어 계층 규칙에서 벗어나지 않는다.

## D9. (i) 안내는 바텀시트로

툴팁 컴포넌트가 없고, 모바일에서 hover 툴팁은 접근성이 나쁘다. 기존 `ui/Sheet.tsx`를 재사용해 (i) 버튼 → 바텀시트로 연다.

**이미 쓰는 화면에 둔다** — 홈의 "오늘의 탄·단·지 달성도"와 프로필 영양 목표. 홈이 특히 중요하다. 목표를 매일 마주하는 자리이고, "탄수가 왜 이렇게 많지"·"고기를 이만큼 먹어야 하나"가 생기는 곳도 거기다.

**온보딩 결과 화면에는 (i)를 두지 않는다.** 거기는 숫자를 처음 보는 자리라 누를 사람이 적고, 홈과 똑같이 생겨 새로 만든 화면처럼 읽히지 않는다. 대신 근거를 화면에 직접 적는다(D19).

**항상 노출하지는 않는다.** (i) 버튼만 두고 누른 사람에게만 보인다 — 같은 문구가 매일 화면에 깔려 있으면 잔소리가 된다. 버튼 하나는 잔소리가 아니다.

세 곳이 함께 쓰므로 시트는 `features/dashboard/`에 둔다. 매크로 목표는 대시보드가 파생하는 값이다.

담을 내용은 둘이다.

- **탄단지는 기준선이다** — 탄수가 많게 느껴지면 일부를 지방으로 바꿔도 된다. 총 칼로리만 지키면 된다
- **단백질은 생각보다 쉽게 채워진다** — 목표에는 밥·채소·빵의 단백질도 이미 포함돼 있다. 고기나 보충제로만 채우지 않아도 된다

## D10. 새 필드는 `Boolean`으로 받는다

`OnboardingRequest`·`KcalSuggestionRequest`에 `boolean strengthTraining`을 primitive로 넣었더니 회원 통합 테스트 11개가 한꺼번에 400으로 떨어졌다.

```
JSON parse error: Cannot map `null` into type `boolean`
```

Jackson은 **누락된 primitive를 null로 보고 거절한다.** 테스트가 아니라 실제 배포에서 더 위험하다 — 서버가 먼저 뜨고 프론트가 나중에 반영되는 순간이 있고, PWA는 캐시된 구버전이 한동안 살아 있다. 그 사이 온보딩 요청이 전부 400이 된다.

`Boolean`으로 받고 `strengthTrainingOrDefault()`가 누락을 `false`로 읽는다. 기본값을 `false`로 정한 D3와도 같은 방향이다.

## D11. 반올림

기존과 같이 g 단위 `HALF_UP`이다. 다만 순서가 생겼다 — **단백질과 지방을 먼저 g으로 반올림하고, 그 g에서 역산한 kcal을 뺀 나머지로 탄수를 구한다.** 반올림 전 값으로 나머지를 구하면 화면에 보이는 세 값의 합이 목표 칼로리와 어긋난다.

## D12. 유지칼로리 안내 — 왜 별도 시트인가

칼로리 링 헤더("오늘의 칼로리")에 (i)를 하나 더 둔다. 탄단지 안내와 **합치지 않는다** — 답하는 질문이 다르다. 탄단지 시트는 "이 세 숫자를 어떻게 읽나"이고, 이쪽은 "애초에 이 목표가 어디서 나왔나"다. 하나로 묶으면 둘 다 안 읽힌다.

담는 내용과 그 근거:

- **유지칼로리가 기준선이다.** 목표는 거기서 얼마나 빼거나 더할지를 정한 결과다. 기준을 모르면 목표를 조절할 수도 없다.
- **조절 폭과 결과를 표로.** 체지방 1kg ≈ 7700kcal — 백엔드 `TdeeCalc.KCAL_PER_KG`와 같은 값이다. −500이면 주 0.45kg·월 2kg, −300이면 주 0.27kg·월 1.2kg.
- **증량은 감량과 대칭이 아니다.** 잉여 칼로리가 전부 근육이 되지 않는다. 앱의 `Goal`도 CUT −500 / BULK +300으로 비대칭인데, 안내가 둘을 같은 숫자로 묶으면 그 비대칭이 실수처럼 보인다.
- **처음 값은 추정이다.** Mifflin-St Jeor는 개인차가 10~15% 난다. `TdeeService`가 14일 창에서 커버리지 80%(≈12일) 이상이면 실제 섭취·체중 추세로 역산한 값(`ADAPTIVE`)으로 바꾼다. **앱의 핵심 기능인데 화면 어디에도 설명이 없었다.**
- **체중은 하루에도 흔들린다.** 물·염분·글리코겐으로 1kg 넘게 움직인다. 이걸 모르면 하루 오른 숫자를 실패로 읽고 그만둔다.

원안에는 "300~500 덜 먹으면 주 0.5kg, 한 달 2kg"으로 적혀 있었다. 7700kcal 기준으로는 **−500일 때의 값**이고 −300이면 그 절반쯤이다. 범위와 결과를 한 줄로 묶으면 −300을 고른 사람이 두 배 빠른 결과를 기대하게 되므로 표로 갈랐다.

## D13. 안내 시트의 위계

처음에는 같은 회색 카드(`bg-track`) 네 개를 세로로 쌓았다. **읽히지 않았다.** 모든 블록이 같은 무게라 어디부터 봐야 할지 알 수 없고, 핵심 숫자가 본문과 같은 크기에 묻혔다.

네 단계로 갈랐다.

1. **결론** — 제목을 `text-xl font-black` 두 줄로. "유지칼로리를 알아야 조절할 수 있어요"
2. **근거 숫자** — 한 달 결과를 카드에서 가장 큰 글자(`text-2xl`)로. `tabular-nums`로 자릿수를 맞춘다
3. **보조 설명** — 배경 있는 블록 하나
4. **각주** — 구분선 목록과 마지막 한 줄

숫자 카드에서 **"한 달"을 큰 숫자와 같은 줄에 둔다.** 아래 작은 줄로 내렸더니 무엇의 값인지 읽히지 않았다 — 큰 숫자만 눈에 들어오고 라벨은 건너뛴다. 다만 라벨을 11px로 두면 24px 숫자와 크기 차가 두 배를 넘어 따로 노는 것처럼 보인다. 14px로 올려 같은 줄에 놓이게 했다.

**제목 줄바꿈은 `text-balance`에 맡긴다.** `<br>`로 고정했더니 한쪽 줄만 짧아졌고, 기기 폭이나 사용자 글자 크기 설정이 바뀌면 그 자리가 더 어긋난다. 390px에서는 한 줄에 들어가고, 좁아지면 균형이 맞은 두 줄이 된다.

**증량 카드는 감량과 색을 달리 쓴다.** 감량은 `brand-soft` 2열, 증량은 `track` 한 줄이다. 셋을 같은 색으로 나란히 두면 대칭으로 읽혀서, 본문에서 "증량은 다르다"고 쓴 것과 화면이 어긋난다.

탄단지 시트도 같은 언어로 맞췄다 — 결론 한 줄 뒤에 구분선 목록. 두 시트가 다른 짜임이면 같은 (i)를 눌렀는데 다른 앱처럼 보인다.

## D14. 칼로리 카드 전체를 리포트 링크로

헤더 오른쪽에 (i)와 "리포트 ›"가 나란히 있었다. 달성도 카드는 (i) 하나뿐이라 **두 카드의 (i) 위치가 어긋났다.** 리포트 링크를 떼어 카드 전체로 옮기고 (i)만 오른쪽 위에 남겼다.

**링크로 감싸지 않는다.** `<a>` 안에 (i) 버튼을 넣으면 중첩 인터랙티브라 HTML 규칙에 어긋나고, 버튼을 눌러도 클릭이 링크로 새어 올라간다. 대신 `absolute inset-0` 링크를 **형제로 깔아** 면만 덮고, (i)에 `relative z-10`을 준다.

`z-10`이 없으면 실제로 샌다. 브라우저 히트 테스트로 확인했다.

```
z-10 없음 → 버튼 중심의 elementFromPoint = <a>     (리포트로 이동)
z-10 있음 → 버튼 중심의 elementFromPoint = <button>  (안내 열림)
카드 다른 곳 → <a>                                  (리포트로 이동)
```

**jsdom은 stacking을 모르므로 이 회귀를 테스트가 잡지 못한다.** `z-10`을 지워도 vitest는 통과한다. 테스트에는 그 한계를 적어두고 실기기 확인 항목으로 넘겼다.

두 카드의 (i)는 `-my-2 -mr-2` + 카드 `p-4`로 **모서리에서 각각 8px**에 놓인다(측정 확인). 칼로리 헤더는 코칭 한 줄이 붙어 두 줄이 될 수 있어 `items-start`를 준다 — `items-center`면 그때만 (i)가 아래로 내려가 달성도 카드와 어긋난다.

카드를 눌러 이동할 수 있다는 표시로 제목 옆에 `›`를 둔다. 없으면 누를 수 있는지 알 길이 없다.

## D15. 신체 정보 입력과 나이 규칙

**슬라이더를 걷어낸다.** 드래그로는 1cm를 맞추기 어렵고, 390px 화면에서 100~230cm를 훑으면 한 픽셀이 한 칸을 넘는다. 양쪽 −/+ 버튼(44px)과 가운데 큰 숫자 입력으로 바꾼다 — 버튼은 눌린 만큼만 움직이고, 멀리 갈 때는 숫자를 직접 친다.

버튼은 범위를 넘지 않지만 **직접 입력은 막지 않는다.** 타이핑을 중간에 막으면 "17"을 치다 걸린다. 범위 검증은 지금처럼 '다음'에서 문구와 함께 알린다.

**나이는 세는나이다** — 2002년생이 2026년에 25세. 기존 코드는 `연도 − 나이`라 25를 넣으면 2001년생이 됐다.

이 결정에는 딸린 곳이 있다. 프로필 카드와 편집 시트가 각자 `연도 − 출생연도`로 나이를 표시하고 있었다. 그대로 두면 **온보딩에서 25를 입력했는데 프로필에서 24로 보인다.** 세 곳이 `lib/age`의 함수 하나를 공유하게 했다.

**서버 계산은 바꾸지 않는다.** Mifflin-St Jeor는 만 나이 공식이고 `DailyKcalCalculator`는 `연도 − 출생연도`를 쓴다. 세는나이를 넣으면 한 살 많게 계산된다. 화면용과 계산용이 갈리는 것은 의도한 것이고, 저장하는 값(출생연도)이 하나라 어긋날 여지가 없다. BMR 차이는 5kcal이다.

## D16. 신체 정보 시작값

시작값의 목적은 정확도가 아니라 **조절 횟수를 줄이는 것**이다. 성별을 고른 직후 그 성별의 평균에서 시작한다.

| | 키 | 몸무게 |
| --- | ---: | ---: |
| 남성 | 174cm | 75kg |
| 여성 | 162cm | 58kg |

키는 20~30대 평균(건강검진통계 기준 남 174.4~174.7 / 여 161.8~161.9)을 반올림했다. **체중은 근사치다** — 공개 통계 표를 직접 확인하지 못했다. 시작점이므로 그 정도로 충분하지만, 키만큼 단단한 근거는 아니다.

나이는 25에서 시작한다.

**이미 고친 값은 덮지 않는다.** 되돌아가 성별만 바꿨을 뿐인데 맞춰둔 키가 평균으로 되돌아가면 입력을 잃는다. `bodyTouched` 플래그로 한 번이라도 손댔는지를 들고 있다가, 손대지 않았을 때만 갈아끼운다.

## D17. 방향과 목표 체중이 어긋날 때

감량을 골랐는데 목표 체중이 지금보다 무겁거나, 증량인데 가벼운 경우가 있다.

**막지 않는다.** 지금 체중을 잘못 넣었을 수도 있고, 정말 그렇게 하려는 것일 수도 있다(증량 후 감량을 계획했다든지). 어느 쪽인지 화면이 알 수 없으므로 결정은 회원에게 남기고 한 번 보여주기만 한다.

그래서 `role="alert"`이 아니라 **`role="status"`** 다. 진행을 막는 오류가 아니라 확인 요청이고, 스크린리더도 그 차이를 읽어야 한다. 색도 `text-danger`가 아닌 `text-brand-ink`를 쓴다.

문구에 **지금 체중을 함께 넣는다** — "감량을 골랐는데 목표가 지금보다 무거워요. 지금 체중은 75kg이에요." 어긋났다는 말만으로는 무엇을 고쳐야 할지 알 수 없다.

## D18. 한국어 줄바꿈은 전역에서 잡는다

목표 단계에서 문구가 이렇게 끊겼다.

```
...탄수화물을 그만큼 줄여요. 감      ← "감량"이 쪼개짐
량 중에 근육을 지킬 때도...

...지금 체중은 75kg이에             ← "요."만 홀로 떨어짐
요.
```

기본 줄바꿈 규칙은 한국어를 글자 단위로 끊는다. 한국어는 어절 단위로 읽으므로 단어가 갈리면 좁은 칸일수록 문장이 읽히지 않는다.

**한 화면만 고치지 않고 `body`에 둔다** — 앱 전체가 한국어라 어디서든 같은 일이 생긴다.

```css
word-break: keep-all;      /* 어절을 지킨다 */
overflow-wrap: break-word; /* 다만 칸보다 긴 한 덩어리(URL·영문)는 끊어 넘치지 않게 */
```

`overflow-wrap`을 함께 두는 이유는 `keep-all`만 쓰면 칸보다 긴 단어가 잘리지 않고 그대로 넘치기 때문이다.

문구도 함께 줄였다. "감량을 골랐는데 목표가 지금보다 무거워요. 지금 체중은 75kg이에요." → **"감량인데 목표가 더 무거워요 (지금 75kg)"**. 두 문장을 한 줄로 합쳐 줄바꿈이 걸릴 자리를 없앴다. 덧붙이는 값은 엠대시가 아니라 괄호로 묶는다 — 엠대시는 폭을 많이 먹고 좁은 칸에서 줄바꿈 지점을 하나 더 만든다.

## D19. 결과 화면에 근거를 붙인다

온보딩 마지막 화면은 숫자 네 개(유지 칼로리·목표·탄단지)를 처음 보여주는 자리인데, **왜 그 값인지가 없었다.** 그러면 "앱이 정해준 값"으로 읽히고, 목표 섭취량 칸이 수정 가능한데도 고칠 생각을 하지 않는다.

세 자리에 한 줄씩 붙인다.

**(i)를 두지 않고 화면에 직접 적는다.** 처음 보는 자리라 (i)를 누르는 사람은 소수이고, 아이콘이 붙으면 홈 화면과 구분이 안 된다.

설명은 **두 층**이다. 숫자 옆 한 줄은 "무엇"만 말하고, 화면 아래 섹션이 "왜"를 이어 받는다.

| 자리 | 한 줄 (무엇) |
| --- | --- |
| 유지 칼로리 | 먹어도 체중이 그대로인 칼로리예요 |
| 목표 섭취량 | 감량이라 500kcal 적게 · 주 0.45kg 속도 |
| 탄단지 | 단백질 체중 1kg당 2.0g · 지방 25% · 나머지 탄수화물 |

**맨 위에는 "매일 기록해야 정확해져요"를 둔다.** 이 앱에서 가장 중요한 한 가지이기 때문이다 — 지금 보이는 숫자는 공식으로 낸 추정이고, 매일 남겨야 `TdeeService`가 실제 섭취·체중 추세로 다시 계산한다(D12). 색이 있는 카드로 다른 설명과 층을 나눈다. 체중을 재는 시각(아침·화장실 뒤)까지 적는 이유는 그래야 추세가 흔들리지 않기 때문이다.

그 아래 섹션은 셋을 다룬다.

- **유지 칼로리를 알면 스스로 조절할 수 있다** — 2주 뒤 안 움직이면 여기서 200~300kcal만 더 빼면 된다. 기준을 모르면 무작정 굶는 것 말고는 방법이 없다
- **단백질 → 지방 → 탄수화물 순서로 정했다** — 계산 순서가 곧 우선순위다(D1). 탄수화물이 가장 큰 이유가 여기서 드러난다
- **탄수화물을 지방으로 옮겨도 된다** — 탄수 4kcal/g, 지방 9kcal/g이라 탄수 20g ↔ 지방 9g이 맞바꿔진다. 숫자를 주면 "옮겨도 된다"가 막연한 위로가 아니라 실행 가능한 말이 된다

접거나 (i)로 숨기지 않는다. 스크롤해야 닿는 위치라 급한 사람은 그냥 시작하면 되고, 궁금한 사람은 내려보면 있다.

**단백질 g/kg는 실제 목표 g에서 되짚어 계산한다**(`proteinTargetG / weightKg`). 비율값(20%·30%)을 그대로 문구에 박으면 체중 상·하한에 잘렸을 때 화면의 150g과 설명이 어긋난다. 되짚으면 잘린 뒤에도 항상 맞는다.

## D20. 플랜을 만드는 시간

계산은 순식간이라 '다음'을 누르면 결과가 즉시 튀어나왔다. 그러면 방금 답한 다섯 가지가 **쓰이긴 했는지** 알 수 없다 — 숫자만 갑자기 나타난다.

한 줄에 1.5초씩, 세 줄로 무엇을 계산하는지 보여준다(합쳐 4.5초).

가운데는 **접시에 한 조각씩 담기는 그림**이다. 단계가 넘어갈 때마다 탄·단·지 색 조각이 하나씩 떨어져 자리를 잡는다.

여기까지 세 번을 갈아엎었다.

1. 이모지 하나(🍽️) + 도는 링 — 무난했지만 링과 그림이 따로 놀았다
2. 단계마다 다른 이모지(🔥→🏃→⚖️) — 세 그림이 제각각이라 산만했고, `DESIGN.md`의 "인라인 SVG만, lucide 기준"도 어겼다
3. 단계마다 다른 선 아이콘 — 규칙은 지켰지만 링 안에서 아이콘까지 바뀌니 시선 둘 곳이 없었다

문제는 아이콘 고르기가 아니라 **가운데가 진행을 말하지 못한다는 것**이었다. 접시에 담는 그림은 그 자체가 진행이라 도는 링도, 점 세 개짜리 진행 표시도 필요 없어졌다.

색은 앱의 탄·단·지 색 그대로다 — 마지막 조각이 놓이는 순간 접시가 차고, 곧바로 다음 화면의 탄단지 카드에 같은 세 색이 나타난다. 무엇을 담고 있었는지가 그때 밝혀진다.

접시는 **위에서 내려다본** 모양이다. 옆에서 본 타원으로 먼저 그렸더니 조각이 접시 위에 떠 보였다. 랜딩의 `MealArt`가 쓰는 시점과도 같다.

조각의 `key`는 인덱스가 아니라 색이다 — 인덱스로 두면 조각이 늘 때 이미 놓인 것까지 다시 떨어진다.

한 줄에 머무는 시간이 짧으면 읽기 전에 지나가 설명 구실을 못 한다.

**연출이 아니라 계산 과정의 설명이다.** 세 줄이 곧 앞 단계에서 물어본 것들(신체 정보·활동량·목표)과 짝을 이룬다.

시간은 `Promise.all([요청, 2초 타이머])`로 잡는다 — 응답이 2초보다 빠르면 2초를 채우고, 느리면 응답을 기다린다. 일부러 늦추는 것이 아니라 **최소 시간**이다.

몇 가지를 함께 지킨다.

- 5단계로 **먼저 이동한 뒤** 만든다. 4단계에서 기다리게 하면 어디로 가는지 모른 채 멈춰 있다
- **위저드 셸을 벗는다.** 단계 번호("STEP 5", "5/5")·뒤로가기·진행 막대·CTA는 지금 손댈 수 있는 것이 없는 동안 장식일 뿐이고, 시선을 진행 문구에서 뺏는다. 처음에는 셸 안에 넣고 CTA만 비활성화했는데, 눌리지 않는 큰 버튼이 화면 아래를 차지하고 있는 편이 더 어수선했다
- **결과 화면도 단계 표시를 감춘다**(`showSteps={false}`). 더 물을 것이 없는 마지막 화면에서 "STEP 5"·"5/5"·진행 막대는 할 말이 없고, 정작 봐야 할 숫자들과 시선을 나눈다. 뒤로가기와 CTA는 남긴다 — 목표를 다시 고르러 갈 길과 홈으로 갈 길은 필요하다
- 제목은 "맞춤 플랜을 **만들고 있어요**"다. "준비됐어요"로 두면 화면이 스스로와 어긋난다
- 실패하면 **4단계로 되돌린다.** 빈 5단계에 남겨두면 할 수 있는 것이 없다
- 결과는 `animate-settle-in`으로 자리를 잡는다. 기다린 뒤라 툭 나타나면 어색하다
- 문구는 `role="status"` — 모션 축소 설정이면 링이 멈추므로 글이 유일한 단서가 된다
- 문구를 바꿀 때 **live 영역째 갈아끼우지 않는다.** `<p role="status">`는 그대로 두고 안쪽 `<span>`만 `key`로 교체한다 — 영역 자체가 새로 생기면 스크린리더가 바뀐 내용을 읽지 않을 수 있다

시간(`PLAN_BUILD_MS`)은 모듈에서 내보내고 **테스트에서는 그 값만 20ms로 바꾼다.** 그 시간을 그대로 기다리면 결과 화면까지 가는 테스트마다 그만큼 붙는다(2초씩 쓰던 때 온보딩 테스트 파일이 12초까지 늘었다). 화면은 진짜를 그리고 시간만 줄인다 — 최소 시간을 실제로 채우는지는 실기기 확인 몫이다.

## D21. 숫자 입력칸의 폭

목표 섭취량 입력이 `w-32`(128px) 고정이라 값이 네 자리보다 짧으면 남은 자리만큼 옆의 `kcal`이 멀리 떨어졌다. 숫자와 단위가 한 덩어리로 읽히지 않는다.

폭을 값 길이에 맞춘다.

```tsx
style={{ width: `${Math.max(kcalInput.length, 2)}ch` }}
className="... tabular-nums ..."
```

`tabular-nums`와 함께 쓰는 것이 핵심이다 — 그래야 숫자 한 자가 정확히 `1ch`이고, 값이 바뀌어도 폭이 딱 맞는다. 최소 2ch는 남겨 값을 다 지웠을 때 칸이 사라지지 않게 한다.

## D22. 설명 글의 가독성

세 항목을 넣고 보니 글 덩어리로만 보였다. 대비는 문제가 아니었다 — `muted`(#5b6878)는 흰 배경에서 5.7:1로 AA를 넘는다. 밀도와 위계가 문제였다.

세 가지를 고쳤다.

- **줄간격** `leading-relaxed`(1.625) → `leading-[1.75]`. 한국어는 글자가 촘촘해 라틴 문자 기준 줄간격으로는 답답하다
- **제목과 본문의 거리** — 둘 다 `text-sm`이라 굵기 하나로만 갈렸다. 제목을 `text-[15px] font-bold`로 올려 크기로도 벌린다
- **본문 색** `text-muted` → `text-ink/75`. 읽는 글이지 보조 설명이 아니다. 강조는 `font-semibold text-ink`로 한 단계 더 위에 둔다

항목 간 여백도 `py-3` → `py-4`로 늘렸다. 구분선만으로 나누면 선이 내용보다 먼저 보인다.

## D23. 설명이 길어지면 버튼을 붙인다

결과 화면에 "왜"를 적고 나니 '시작하기'가 스크롤 아래로 밀려났다. 온보딩을 끝내려면 읽지도 않을 글을 지나 내려가야 한다.

**설명을 접지 않는다.** (i)나 아코디언으로 숨기면 결국 아무도 안 본다 — 처음 보는 자리라 펼칠 이유를 아직 모른다. 대신 **하단을 화면에 붙인다**(`sticky bottom-0`).

```
설명은 그대로 길게 두고     →  스크롤로 읽는다
버튼은 항상 손 닿는 곳에    →  언제든 시작할 수 있다
```

`sticky`는 `fixed`와 달리 **일반 흐름에서 자리를 차지한다.** 그래서 스크롤 끝에서 본문 마지막 줄을 가리지 않는다 — 아래 여백을 따로 계산해 넣을 필요가 없다.

두 가지를 덧댄다.

- 배경을 `bg-canvas`로 채운다. 투명하면 지나가는 내용이 버튼 뒤에 비친다
- 위쪽에 `-top-8` 높이의 그라데이션을 한 겹 얹는다. 없으면 내용이 버튼 경계에서 딱 잘려 사라진다

`WizardShell` 전체에 적용하므로 다른 단계도 같아진다. 내용이 짧은 단계에서는 원래도 버튼이 화면 아래였으니 보이는 변화는 없다.
