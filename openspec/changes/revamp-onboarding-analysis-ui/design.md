# Design: revamp-onboarding-analysis-ui

## Context

현재 온보딩은 2스텝(6개 입력 → 제안 칼로리 확인)이고 전 항목 필수다. 계산은 `DailyKcalCalculator`가 담당하며 유지칼로리는 내부 변수로만 쓰이고 응답(`KcalSuggestionResponse`)은 `dailyKcalTarget` 하나만 돌려준다. 목표 방향은 `목표체중 vs 현재체중` 비교로 도출한다.

사진 분석 확인 화면(`MealRecordPage`)은 오버레이 모드에서 합계를 `TotalsLine` 한 줄로만 보여주고 항목 리스트가 없다(위치 없는 항목만 칩으로).

결정은 사용자 그릴링(2026-08-12) 확정. 목업 6장(성별 → 키·나이 → 활동량 → 목표 → 완료)과 "키·몸무게·나이 한 페이지" 지시를 반영해 **5단계**로 정리했다.

## Decisions

### D1. 온보딩 = 5단계 위저드 (그릴링 확정)
```
1 성별            카드 2개(남/여)
2 키·몸무게·나이   슬라이더 3개 (한 화면)
3 활동량          옵션 카드 4개
4 목표            방향 3개(감량/유지/증량) + 감량·증량이면 목표 체중(선택) 입력
5 완료 플랜        유지칼로리(TDEE) · 목표 섭취량 · 탄단지 · 시작하기
```
- 단계마다 `STEP n` 라벨 + 질문 한 문장 + 보조 설명, 상단 진행 표시(n/5), 하단 고정 CTA(선택 전 비활성).
- 뒤로 가기로 이전 단계 수정 가능. 단계 상태는 페이지 로컬(서버 임시저장 없음).
- **시각 언어는 현재 앱 토큰**(brand 오렌지·`Card`·`Button`·slate 계열)을 쓴다 — 목업의 색·폰트를 그대로 옮기지 않는다(사용자 지시).

### D2. 목표 = 방향 입력, 목표 체중은 선택 (그릴링 확정)
- `Goal { CUT, MAINTAIN, BULK }`를 회원에 저장(V12 `member.goal`).
- 조정치는 **기존 상수 유지**(감량 −500 / 유지 0 / 증량 +300). 목업의 400/350은 예시 수치로 보고, 적응형 TDEE 추천(`toTarget` 재사용)과 값이 어긋나지 않도록 기존 값을 따른다. 화면 문구는 "유지 칼로리보다 500kcal 적게"처럼 실제 상수를 그대로 쓴다.
- **목표 체중**: 감량·증량을 고른 경우에만 4단계에서 선택 입력으로 노출. 비워도 진행된다. 있으면 체중 탭의 "목표 달성 예상"이 즉시 동작한다.
- `DailyKcalCalculator.toTarget(maintenance, gender, goal)`로 시그니처 변경 — 방향이 명시적이라 목표 체중 없이도 목표를 낸다.
- **부수 이득**: `TdeeService`의 추천 목표가 지금은 목표 체중이 없으면 `null`인데, 방향만 있으면 낼 수 있다.

### D3. 활동량 4단계 (그릴링 확정)
`ActivityLevel`에 `VERY_HIGH(1.9)` 추가. 라벨·설명을 구체화한다.

| 값 | 라벨 | 설명 | 계수 |
|---|---|---|---|
| LOW | 거의 앉아서 생활 | 주 0~1회 운동 | 1.2 |
| MID | 보통 | 주 2~3회 운동 | 1.5 |
| HIGH | 활동적 | 주 4~5회 운동 | 1.75 |
| VERY_HIGH | 매우 활동적 | 거의 매일 운동·육체노동 | 1.9 |

미배포 상태라 기존 데이터 영향 없음(값 추가만, 기존 값 의미 불변).

### D4. 완료 화면이 계산 근거를 보여준다
`KcalSuggestionResponse`를 `{ maintenanceKcal, dailyKcalTarget, carbTargetG, proteinTargetG, fatTargetG }`로 확장. 탄단지는 이미 `MacroTargetG.from(kcal)`(탄5:단3:지2)로 계산하므로 **백엔드가 계산해 내려준다** — 프론트에 비율 상수를 복제하지 않기 위해서다.

### D5. 사진 분석 확인 화면 = 요약 카드 + 항목 리스트 (A안 확정)
- **요약 카드**: "분석 결과 · N개 음식" + 총 kcal(큰 글씨) + 탄·단·지 3칩(기존 carb/protein/fat 토큰).
- **항목 리스트**: 오버레이 모드에서도 사진 아래에 항상 표시. 행 = 이름 + kcal + 배지(`보정됨`/`확인 필요`), 탭하면 기존 `ItemEditSheet`. "위치 없는 항목" 칩은 리스트로 흡수한다.
- **CTA**: "저장" → "점심으로 저장하기"처럼 선택된 끼니 라벨 반영.
- **넣지 않는 것**: 목업의 항목별 `120g · 신뢰도 94%`. `AnalyzedItem`에 양·항목별 신뢰도가 없고 `overallConfidence`는 사진 전체 값이라, 표시하면 지어낸 수치가 된다. 별도 change로 미룬다.

## Risks / Trade-offs

- [단계가 늘어 이탈 증가] → 단계당 입력이 가벼워지고 진행 표시로 끝이 보인다. 목표 체중을 선택으로 낮춰 총 필수 입력은 오히려 줄었다.
- [목표 방향 추가로 도메인 확장] → `Goal`은 값 3개짜리 열거형이고 nullable 컬럼이라 회귀 위험이 낮다. 방향이 없는 기존 데이터는 목표 체중 비교로 폴백한다.
- [슬라이더 입력의 정밀도] → 키·몸무게는 소수점이 필요할 수 있어 슬라이더 + 직접 입력을 함께 둔다(접근성: 슬라이더에 `aria-label`, 숫자 입력 병행).
- [분석 화면 정보 중복] → 오버레이 라벨과 리스트가 같은 값을 두 번 보여주지만, 오버레이는 "어디"·리스트는 "얼마"를 담당해 역할이 다르다.

## Migration Plan

- **V12**: `ALTER TABLE member ADD COLUMN goal VARCHAR(10)` (nullable). 기존 회원은 null → 목표 체중 비교로 폴백.
- `ActivityLevel.VERY_HIGH`는 문자열 저장이라 스키마 변경 없음.
- 온보딩 완료 판정(`dailyKcalTarget != null`)은 그대로 둔다 — 목표 방향을 고르면 항상 목표 kcal이 확정되므로 미완료로 남을 일이 없다.

## Open Questions (구현으로 확정)

- ~~목표 체중 선택 입력의 위치~~ → **4단계 안**. 감량·증량을 고르면 그 자리에서 입력칸이 나타난다(유지를 고르면 아예 없음).
- ~~슬라이더 범위~~ → 키 100~230cm, 몸무게 30~250kg(기존 검증 범위와 동일), 나이 10~100세 → `birthYear = 올해 − 나이`.
- ~~진행 표시 형태~~ → 상단 `n/5` 텍스트 + 하단 바 **둘 다 유지**(목업과 동일). 하단 바에 `role="progressbar"`를 줘 테스트·스크린리더가 현재 단계를 읽는다.

## 구현 이탈 (design 대비)

- **`KcalSuggestionRequest`에서 목표 체중 제거**: 제안 계산이 방향만 쓰므로 파라미터에서 아예 뺐다(선택으로 남기지 않음). 목표 체중은 저장 전용 정보가 된다.
- **오버레이 박스와 리스트 행의 접근성 이름 분리**: 둘 다 편집 시트를 열어 이름이 겹치면 스크린리더·테스트가 구분할 수 없어, 박스는 `{이름} 편집`, 리스트 행은 `{이름} 항목 편집`으로 나눴다.
- **"위치 없는 항목" 칩 제거**: 항목 리스트가 위치 유무와 무관하게 전부 담으므로 별도 칩 영역이 중복이 됐다.
- **슬라이더는 큰 숫자 자체가 입력칸**: 별도 입력칸을 덧붙이는 대신 `type="number"`를 크게 노출하고 그 아래 `type="range"`를 둬, 정밀 입력과 빠른 조절을 한 컴포넌트에서 처리한다.
- **프로필 화면에 목표 방향 선택 추가**: 온보딩에서 방향을 받게 되면서 프로필에서도 바꿀 수 있어야 해 `goal` 셀렉트를 넣고, 제안 재계산 조건을 목표 체중 대신 방향 변경 기준으로 바꿨다.

## 리뷰 대응 (PR #32)

- **온보딩 죽은 버튼(🔴)**: 신체 정보 검증이 4→5단계에서만 일어나는데 그 오류 문구는 2단계에만 있어, 범위 밖 값을 넣으면 4단계에서 아무 안내 없이 '다음'이 막혔다. **검증을 2단계 확정 시점으로 옮겨** 값이 보이는 화면에서 바로 알리고, 4단계에서 뒤늦게 걸리면 2단계로 되돌려 문구를 보여준다. 기존 테스트가 "제안 API 미호출"만 확인해 이 공백을 놓쳤으므로, 오류 문구·현재 단계·수정 후 진행까지 검증하도록 보강했다.
- **`SliderField`가 빈 입력을 무시(위 수정 중 발견)**: 지우고 다시 칠 수 없어 잘못 넣은 값을 고칠 수 없었다. 표시 문자열을 따로 들고 숫자로 읽히는 동안만 부모에 올리도록 바꿨다.
- **'확인 필요' 배지 미구현(🔴)**: 오류 항목을 테두리 **색으로만** 구분해 색을 못 보는 사용자에게 전달되지 않았다(design D5·tasks 5.2가 약속한 배지). 텍스트 배지를 추가했다.
- **차트 좌표 투영 중복(nit)**: 홈 미니 카드와 체중 탭 추세선이 같은 `x/y` 공식을 각자 갖고 있어 `features/weight/trendScale.ts`로 뽑아 공유한다(최소 표시 폭 옵션 포함).
- **스펙 시나리오 동기화(nit)**: '감량 목표 계산'이 목표 체중 기반으로 남아 있어 방향 기반으로 고치고, 중복되던 시나리오를 '목표 체중 없이 계산'으로 정리했다.
- **유지: 목표 조정치 문구의 500/300 하드코딩(nit)** — 리뷰는 `maintenanceKcal` 대비 차이로 파생하라 했으나, 이 문구가 쓰이는 4단계는 **제안 API를 아직 호출하기 전**이라 파생할 값이 없다. 방향별로 API를 미리 부르거나 상수를 별도 API로 내리는 건 라벨 하나에 비해 과하다. design D2의 트레이드오프를 유지한다.
