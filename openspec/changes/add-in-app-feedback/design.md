# 설계 — 앱 안에서 의견 받기

## D1. 왜 메일이 아니라 서버 저장인가

| | 대가 |
| --- | --- |
| `mailto:` | 프론트 한 줄로 끝나지만 **서버에 기록이 안 남고**, 메일 계정이 안 묶인 기기에서는 막히며, 이메일 주소가 페이지에 노출된다 |
| 메일 발송 | `spring-boot-starter-mail` + SMTP 계정(시크릿)이 새로 필요하다 |
| **서버 저장** | 앱을 벗어나지 않고, 맥락을 자동으로 붙일 수 있고, 기존 도메인 패턴을 그대로 따른다 |

**메일 알림은 저장 위에 얹었다**(D9). 저장이 먼저 있었기 때문에 알림은 덧붙이는 일로 끝났다.

## D2. 기기 정보는 본문이 아니라 헤더에서

```java
@RequestHeader(value = HttpHeaders.USER_AGENT, required = false) String userAgent
```

본문으로 받으면 두 가지가 나빠진다. 화면마다 실어 보내는 것을 **빠뜨리고**, 값을 **마음대로 적을 수 있다.** 헤더는 브라우저가 붙이므로 클라이언트 코드가 잊을 수 없다.

앱 버전은 반대로 본문으로 받는다 — 서버가 알 방법이 없고, 클라이언트만 아는 값이다.

기기 문자열은 아주 길게 오는 경우가 있어 서비스에서 500자로 자른다. **컬럼 길이에서 잘리면 저장 자체가 실패한다** — 의견이 길다는 이유가 아니라 기기 이름이 길다는 이유로 실패하면 회원은 영문을 모른다.

## D3. 도배 상한 — 달력 하루가 아니라 최근 24시간

```java
Instant since = clock.instant().minus(WINDOW);   // 24시간
countByMemberIdAndCreatedAtAfter(memberId, since) >= 10
```

달력 하루로 세면 **시간대를 정해야 하고**, 자정 직전·직후에 몰아 보내면 상한이 사실상 두 배가 된다. 최근 24시간은 그 두 가지가 없다.

10건인 이유: 실수로 두 번 누르는 것은 통과해야 하고, 도배는 막아야 한다. `analysis`·`coaching`이 쓰는 것과 같은 모양의 상한이라 예외도 같은 방식으로 429에 매핑한다.

## D4. 보낸 글을 되돌려주지 않는다

```java
public record FeedbackResponse(Long id, Instant createdAt) {}
```

화면이 이미 갖고 있는 글을 응답에 실으면 같은 내용이 두 번 오간다. 받았다는 확인만 돌려준다.

## D5. 답장을 약속하지 않는다

알림 경로가 없으므로 **답장할 방법이 없다.** 화면에도 "확인 후 연락드릴게요" 같은 말을 두지 않았다 — 지킬 수 없는 말이다. "보내주신 의견은 잘 도착했어요"까지만 말한다.

## D6. 보내는 정보 안내는 넣었다가 뺐다

처음에는 입력칸 아래에 "앱 버전과 기기 정보가 함께 전달돼요"를 두고, 스펙에도 **화면에 밝혀야 한다(MUST)**로 적었다. 요청에 따라 뺐다(2026-08-17 결정).

**저장하는 것은 그대로다** — 앱 버전과 기기 정보는 계속 함께 남는다. 바뀐 것은 그 사실을 시트에서 말하지 않는다는 것뿐이라, 스펙에서도 "무엇이 함께 가는지 밝힌다"를 "맥락을 함께 저장한다"로 고쳐 **코드와 스펙이 어긋나지 않게** 했다.

⚠️ 나중에 개인정보 처리방침이나 안내가 필요해지면 이 결정을 다시 볼 자리다. 지금 남기는 것은 **기기 문자열과 앱 버전**이지 그 이상은 아니다.

## D7. 도움말은 함께 뗀다

한 줄이 "도움말 & 피드백"이었지만 **도움말에 해당하는 내용이 없다.** 없는 것을 가리키는 메뉴를 두면 누른 사람은 매번 헛걸음한다. 필요해지면 그때 만든다.

## D8. 회원이 지워지면 의견도 지운다

```sql
member_id BIGINT NOT NULL REFERENCES member (id) ON DELETE CASCADE
```

남겨두면 **주인 없는 개인 진술**이 된다. 통계로 쓸 계획이 있는 것도 아니라 남길 이유가 없다.

## D9. 메일 알림 — 커밋 뒤에, 다른 스레드에서

```
FeedbackService.send()
  ① feedback 테이블 저장 → 커밋
  ② FeedbackSubmittedEvent 발행
        ↓  @TransactionalEventListener(AFTER_COMMIT) + @Async
     FeedbackMailNotifier → SMTP
```

같은 트랜잭션 안에서 보내면 두 가지가 깨진다.

| | |
| --- | --- |
| 회원이 묶인다 | SMTP는 몇 초씩 걸린다. 그동안 "보내는 중…"에서 멈춘다 |
| 의견이 사라진다 | 발송 실패로 롤백되면 **가장 중요한 것을 부수적인 것 때문에 잃는다** |

이벤트에는 엔티티가 아니라 **값을 실어 보낸다.** 알림은 커밋 뒤 다른 스레드에서 도는데, 그때는 영속성 컨텍스트가 닫혀 있어 엔티티를 건드리면 지연 로딩이 터진다.

알림에는 **보낸 사람의 이름과 이메일**을 함께 싣는다. 회원 번호만 있으면 누가 보냈는지 알려고 매번 DB를 뒤져야 한다. 이메일은 `Reply-To`로도 세워, 메일에서 그대로 "답장"을 누르면 그 사람에게 간다 — 본문에서 주소를 찾아 복사할 필요가 없다.

⚠️ 이름·이메일은 **feedback 행에 복사하지 않는다.** 저장해두면 회원이 닉네임을 바꿨을 때 두 값이 갈리고, 회원 삭제와 함께 지워야 할 개인정보가 한 벌 늘어난다. 필요한 것은 "메일에서 바로 아는 것"뿐이라 알림에만 싣는다. 카카오가 이메일을 주지 않는 경우가 있어 둘 다 없을 수 있다.

발송 실패는 **삼킨다.** 요청은 이미 응답을 돌려줬으므로 예외를 올려도 받을 곳이 없다. 대신 `log.error`로 원인을 남긴다 — 의견은 DB에 있으니 잃는 것은 알림뿐이다.

## D10. 설정이 없으면 조용히 건너뛴다

로컬·테스트에서 SMTP를 갖추지 않아도 **의견 보내기는 그대로 동작해야 한다.** 알림은 있으면 좋은 것이지 저장의 조건이 아니다.

`JavaMailSender`는 `ObjectProvider`로 받는다 — 생성자로 직접 받으면 빈이 없는 환경에서 기동이 실패한다.

⚠️ 다만 **빈이 있다고 보낼 수 있는 것은 아니다.** `${MAIL_HOST:}`처럼 값이 비어 있어도 속성 자체는 존재해 빈이 만들어진다. 그래서 실제 판단은 **받는 주소(`app.feedback.mail-to`)가 있는가**로 하고, 그래도 실패하는 경우(자격증명 오류 등)는 위에서 삼킨다.

## D11. 메일을 헬스체크에서 뺀다

메일 스타터를 넣자 **헬스체크가 SMTP 연결을 확인하기 시작했고**, 로컬·테스트에서 `/actuator/health`가 DOWN이 되어 기존 테스트 2개가 깨졌다.

```
management.health.mail.enabled: false
```

메일은 의견 알림에만 쓰는 부수 기능이라 **메일 서버가 안 떠도 서비스는 정상이다.** 켜두면 SMTP가 막히는 순간 감시·로드밸런서가 서비스 전체를 죽은 것으로 본다 — 사진 분석도 기록도 멀쩡한데 사이트가 내려간 것으로 처리된다.
