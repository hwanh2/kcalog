# Design: refine-profile-and-chrome

## D1. 나이는 "출생연도"로 받는다 — 화면에만 "나이"라고 쓴다

엔티티가 가진 것은 `birthYear`다(`Member.birthYear`). 만 나이를 저장하면 **해가 바뀔 때마다 값이 썩는다** — 저장한 날의 나이가 그대로 남아 유지칼로리가 조용히 틀려진다. 프로필 카드도 이미 `new Date().getFullYear() - birthYear`로 표시만 계산하고 있다.

그래서 저장·전송은 `birthYear`, 입력 라벨은 "출생연도"로 둔다. 프로필 카드의 "나이 32세"와 편집 시트의 "출생연도 1994"가 다른 말처럼 보일 수 있으므로, **입력 아래에 계산된 나이를 함께 보여준다** ("만 32세").

검증은 프론트·백엔드 모두 이미 있는 것을 쓴다 — `BIRTH_YEAR_MIN=1920` ~ 올해, 그리고 `MemberService.validateBirthYear`의 미래 연도 차단.

⚠️ 미래 연도 차단은 지금 **온보딩·제안 경로에만** 걸려 있다(`completeOnboarding`, `suggestKcal`). 수정 경로를 여는 순간 그 구멍이 열리므로 `updateProfile`에도 같은 검증을 태운다.

## D2. 성별도 수정 허용 — "바뀌지 않는 값"이라는 가정을 두지 않는다

성별은 Mifflin-St Jeor 공식에서 상수항(+5 / −161)을 가른다. 온보딩에서 잘못 고르면 **유지칼로리가 166kcal 어긋난 채 영구히 남는다.** 되돌릴 방법이 앱 안에 없어서는 안 된다.

`PATCH`는 지금대로 **null인 필드는 건드리지 않는** 부분 수정이다. 성별·출생연도도 같은 규칙을 따르므로 기존 호출부(체중 탭의 목표 적용 등)는 영향받지 않는다.

## D3. 진입점 두 개를 서로 다른 곳으로 보낸다

현재:

```
설정 메뉴 "프로필 편집"  ──┐
                          ├──▶ ProfileEditSheet
영양 목표 카드 "✎ 조정"  ──┘
```

바꾼 뒤:

```
설정 메뉴 "프로필 편집"      ──▶ ProfileEditSheet   (나이·성별·키·목표·활동량·칼로리)
영양 목표 카드 "유지칼로리     ──▶ TdeeRecalcSheet   (현재 유지칼로리·근거·추천 목표·적용)
              다시 계산"
```

버튼 이름이 곧 도착지다. "조정"은 무엇을 조정하는지 말하지 않아 어느 쪽으로 보내도 말이 됐고, 그래서 둘이 겹쳐도 아무도 눈치채지 못했다.

## D4. 유지칼로리 요약은 한 컴포넌트에서 그린다

같은 숫자를 두 곳(체중 탭 카드 · 프로필 시트)에서 보여준다. **따로 그리면 갈라진다** — 한쪽만 "최근 14일 실측" 배지를 빼먹거나, 반올림이 어긋나거나, 추천 목표가 현재 목표와 같을 때의 문구가 달라진다.

`features/tdee/TdeeSummary.tsx`로 본문(유지칼로리 · 출처 배지 · 추천 목표 · 적용 버튼 · 실패 알림)을 뽑고, `TdeeCard`(카드)와 `TdeeRecalcSheet`(시트)가 껍데기만 각자 갖는다.

**"다시 계산"은 서버에 새 계산을 요청하는 버튼이 아니다.** `GET /api/tdee`는 호출할 때마다 최근 기록으로 계산하므로 이미 항상 최신이다. 이 시트가 하는 일은 **계산 결과를 보여주고 목표에 반영하는 것**이다. 그래서 시트를 열 때 해당 쿼리를 무효화해 다시 받아온다 — 사용자가 "다시 계산"을 눌렀는데 캐시된 옛 값이 뜨면 버튼이 거짓말이 된다.

## D5. 확대·축소 잠금 — 세 겹으로 막고, 접근성 손실을 기록한다

한 겹으로는 안 막힌다.

| 수단 | 막는 것 | 안 막는 것 |
| --- | --- | --- |
| `maximum-scale=1, user-scalable=no` | Android Chrome, **iOS 홈 화면 실행(standalone)** | iOS Safari 브라우저 탭 |
| `touch-action: manipulation` | 더블탭 확대 | 핀치 |
| `gesturestart` preventDefault | iOS Safari 핀치 | — |

셋을 모두 넣는다. iOS 10부터 Safari는 `user-scalable=no`를 **의도적으로 무시**하므로, 브라우저 탭에서 열었을 때는 제스처 이벤트를 직접 막는 것 외에 방법이 없다.

⚠️ **이것은 WCAG 2.1 AA 1.4.4(Resize text) 위반이다.** 저시력 사용자가 확대로 읽던 수단을 없앤다. 요청받은 대로 넣되, 대신할 것 — 본문 글자 크기 설정 — 은 이 change 밖으로 두고 여기 남긴다. 잠금을 되돌리려면 세 곳(`index.html`·`index.css`·`main.tsx`)을 함께 되돌려야 한다.

## D6. 추세 범위 라벨 — 값과 표시를 분리하지 않는다

`TrendRange`는 지금 표시 문자열이 곧 타입이다(`'1주' | '1월' | '3월'`). 라벨만 고치면 되므로 **표시용 라벨 맵을 따로 만들지 않고 타입 자체를 바꾼다** — 맵을 두면 값과 라벨이 갈릴 자리가 하나 더 생기는데, 얻는 게 없다.

`'1월' → '1개월'`, `'3월' → '3개월'`. `RANGE_DAYS`(30·90)는 그대로다.

## D7. 즐겨찾기 검색 제거 — 검색창을 목록 밖으로 올린다

`SearchField`는 지금 `FoodList` 안에 있다. 탭에 따라 켜고 끄려면 `FoodList`에 플래그를 더하는 방법도 있지만, **검색은 목록의 일부가 아니라 목록을 고르는 수단**이다. `AddFoodPanel`로 올리고 `tab !== 'favorite'`일 때만 그린다.

`FoodList`는 `query`를 계속 받는다 — 결과 없음 화면의 "'X' 을(를) 찾지 못했어요 / 직접 추가하기"가 그 값을 쓴다. 즐겨찾기 탭에서는 `query`가 항상 빈 문자열이라 그 가지로 가지 않고 `EmptyFavorites`가 뜬다.

⚠️ 검색을 빼도 **필터링 코드(`searchFoods`)는 남긴다.** 즐겨찾기 탭도 같은 함수를 통과하지만 빈 질의는 원본을 그대로 돌려주므로 동작이 같다. "자주 먹는" 탭이 계속 쓰고 있어 제거 대상이 아니다.

## D8. 첫 요소는 스스로 위 여백을 갖지 않는다

셸의 `<main>`이 `pt-4`를 준다. 그 위에 화면이 또 `mt-4`를 얹으면 32px가 된다.

```
홈       -mt-1   (당겨서 12px)
리포트    없음    (16px)
체중      mt-4   (32px)  ← 어긋남
AI PT    mt-4   (32px)  ← 어긋남
```

체중·AI PT의 첫 요소에서 `mt-4`를 뺀다. 뒤따르는 카드들의 간격(`mt-4`, `space-y-3`)은 건드리지 않는다 — 문제는 카드 사이가 아니라 **화면 맨 위**다.

## D9. 리포트 날짜 구분자는 스펙 델타 없이 바꾼다

`–`(en dash) → `~`. **한 글자짜리 표시 변경인데 스펙 델타를 쓰면 충돌한다** — 이 문구를 규정하는 요구사항("리포트 상단에 조회 기간을 보여준다")은 아직 아카이브되지 않은 `polish-ui-details`가 들고 있어서, 같은 요구사항에 대한 델타를 두 change가 각각 갖게 된다. 아카이브 순서에 따라 한쪽이 덮인다.

그래서 tasks.md의 항목으로만 추적한다. `polish-ui-details`가 아카이브되면 그때 `weekly-report` 스펙 본문에 `~`가 반영된 채로 들어간다.

## D10. "제안 적용"은 문장에서 꺼내 면 위에 올린다

원래는 `<p>새 제안 일일 칼로리: 2250 kcal [제안 적용]</p>` — `ghost` 변형(`text-muted hover:text-ink`)이라 **회색 글자가 문장 안에 섞여** 누를 수 있는 것으로 보이지 않았다.

같은 시트 아래쪽 "추천 목표" 줄이 이미 답을 갖고 있었다: 면(`bg-brand-soft`) 위에 값은 왼쪽, 버튼은 오른쪽. 그 모양을 그대로 쓴다. 두 자리가 하는 일이 같으므로(계산된 값을 목표에 반영) 모양도 같아야 한다.

## D11. 계산 근거는 방식이 아니라 **입력**을 말한다

배지는 `최근 14일 실측` / `공식 추정` — 이건 **어느 방식인지**만 말한다. 회원이 알고 싶은 것은 "무엇을 보고 저 숫자가 나왔나"다. 이 화면은 그 숫자를 근거로 목표 칼로리를 바꾸라고 권하는 자리라 더 그렇다.

세 갈래로 나눠 적는다.

| 상태 | 설명하는 것 |
| --- | --- |
| 실측(ADAPTIVE) | 최근 N일 식사 기록의 하루 평균 칼로리 − 같은 기간 체중 추세 변화의 에너지 환산(7,700kcal/kg) |
| 공식(FORMULA) | 성별·나이·키·현재 체중으로 기초대사량 + 활동량 계수. **무엇을 더 하면 실측이 되는지**까지 |
| 데이터 부족 | 둘 다 안 되는 이유와 무엇을 채워야 하는지 |

⚠️ **목표 조정폭(감량 −500 / 증량 +300)은 적지 않는다.** 서버(`DailyKcalCalculator`)가 가진 정책 상수를 화면에 베껴 두면 서버만 바뀌었을 때 화면이 조용히 거짓말을 한다. `NutritionTargetCard`가 탄단지 비율에서 이미 같은 이유로 피했다 — "프론트에 비율 상수를 복제하지 않는다". 대신 "내 목표 방향만큼 더하거나 뺀 값"이라고만 쓴다.

체지방 1kg ≈ 7,700kcal는 정책이 아니라 생리 상수라 적어도 된다.

## D12. 세트 담기는 줄 전체가 아니라 + 버튼

세트 줄은 지금 **줄 전체가 버튼**이고 그 옆에 휴지통이 붙어 있다. 바로 아래 음식 목록은 **줄은 정보, 담기는 + 버튼**이다. 한 화면에서 담는 방법이 두 가지라 배우는 비용이 두 배다.

음식 목록 쪽으로 맞춘다 — 이름·개수·합계는 그냥 정보가 되고, 담기는 `+`, 삭제는 휴지통. 곁가지로 **중첩 인터랙티브도 사라진다**: 줄이 통째로 버튼이면 휴지통이 버튼 안의 버튼이 되는데, 지금은 형제로 나란히 선다.

`aria-label`은 `"{이름} 담기"` 그대로 둔다 — `+` 하나만으로는 무엇을 담는지 읽히지 않는다.

⚠️ 이 화면을 규정하는 요구사항은 아직 아카이브되지 않은 `add-favorite-meal-set`에 있어, D9와 같은 이유로 **스펙 델타를 두지 않고** tasks.md로만 추적한다.

## D13. 담는 자리는 모두 같은 마무리 줄을 쓴다

`[점심 ▾] 에 [기록하기]`는 분석 결과 시트에만 있었다. 나머지 세 곳은 **끼니를 버튼 문구에 박아뒀다.**

| 자리 | 전 | 후 |
| --- | --- | --- |
| 분석 결과 | `[점심 ▾] 에 [기록하기]` | 그대로 (여기서 시작한 모양) |
| 음식 담기(수량) | `저녁에 기록하기` | `[저녁 ▾] 에 [기록하기]` |
| 직접 입력 | `아침에 기록하기` | `[아침 ▾] 에 [기록하기]` |
| 세트 담기 | `점심에 기록하기` | `[점심 ▾] 에 [기록하기]` |

문구에 박아 두는 방식은 잘못된 끼니에 담는 사고는 줄였지만 **그 자리에서 고칠 수가 없었다** — 시트를 닫고 위 세그먼트를 바꾼 뒤 다시 들어와야 했다. 꺼내 두면 둘 다 된다: 보이고, 고칠 수 있다.

`features/meal/RecordButton`으로 뽑아 네 곳이 공유한다. `useId()`로 select id를 만든다 — 시트가 겹쳐 열릴 때 `label`-`input` 짝이 엉키지 않게.

**즐겨찾기 저장은 예외다.** 라이브러리에 넣는 것이지 끼니에 담는 것이 아니라 고를 끼니가 없다 — `FoodDraftSheet`는 `mode`로 갈라 favorite일 때 기존 버튼을 그대로 쓴다.

이 때문에 `onMealTypeChange`를 `FavoriteMealSection` → `FavoriteMealApplySheet`까지 내려보냈다. 원래 `AddFoodPanel`이 이미 갖고 있던 값이라 새로 만든 상태는 없다.

## D14. 홈의 식사 줄 — 자리표시와 끼니 표식

**사진 없는 기록에 자리표시가 없었다.** 음식기록 탭은 이미 식기 아이콘을 넣고 있었는데(DESIGN.md §5 "사진 없는 식사 자리표시는 어디서나 같은 식기 아이콘") 홈만 빠져 있어, 사진 없는 줄은 글자가 왼쪽 끝에서 시작해 줄마다 시작점이 달랐다. 같은 아이콘을 넣는다.

**끼니는 칩으로 세운다.** 홈은 아침·점심·저녁이 **한 목록에 섞이는 유일한 자리**다(음식기록 탭은 세그먼트로 한 끼니만 걸러 본다). 그런데 10px 회색 대문자로 시각과 붙어 있어 훑어지지 않았다.

⚠️ **색으로 가르지 않는다.** 같은 카드에 탄(앰버)·단(로즈)·지(시안) 칩이 이미 있어서, 끼니에 색을 배정하면 그 칩들과 섞여 읽힌다. 대신 중립 칩(`bg-track`) + 끼니별 표식(🌅☀️🌆🍪🌙)으로 가른다 — 코치 탭 추천 카드가 이미 같은 방식으로 이모지를 쓴다.

**표식(이모지)은 넣었다가 뺐다** — 아래 D15 참고. 칩과 정렬만 남는다.

## D15. 홈 목록은 끼니 순서로 정렬한다 — 이모지 표식은 뺀다

이모지 표식(🌅☀️🌆🍪🌙)은 **정렬이 없을 때의 임시방편이었다.** 목록이 아침→점심→저녁 순으로 서면 칩의 글자만으로 충분하고, 이모지는 줄마다 시선을 끄는 장식이 된다. 뺀다.

정렬이 필요한 진짜 이유는 따로 있다. 서버는 `eatenAt` 오름차순으로 주는데, **`eatenAt`은 저장한 순간이다**:

```ts
// lib/date.ts — 오늘이면 지금 시각으로 박는다
export function eatenAtFor(date: string, now = new Date()): string {
  if (date === todayServiceDate(now)) return now.toISOString()
  ...
}
```

저녁을 먹고 나서 그날 아침을 뒤늦게 채워 넣으면 **아침의 `eatenAt`이 저녁보다 늦다.** 목록에서 아침이 맨 아래로 가면 하루를 훑을 때 무엇을 빠뜨렸는지 알 수 없다.

`sortByMealOrder`를 `mealDefaults`에 둔다 — `MEAL_TYPE_ORDER`가 있는 파일이라 순서의 출처가 하나다. 원본 배열을 복사해 정렬한다: 넘겨받는 것은 쿼리 캐시가 들고 있는 배열이라 제자리 정렬하면 캐시를 건드린다.

⚠️ **음식기록 탭은 고치지 않는다** — 거기는 세그먼트로 한 끼니만 걸러 보므로 끼니 간 순서가 없다.

## D16. 화면 전환 시 스크롤 — 셸이 한 번만 맡는다

SPA는 화면을 바꿔도 문서 스크롤이 그대로다. 긴 홈을 내려보다 "전체보기"를 누르면 **도착한 음식기록 화면이 중간에서 시작한다.**

화면마다 `useEffect`로 처리하면 새 화면을 만들 때마다 빠뜨린다. `AppShell`에서 `pathname`이 바뀔 때 한 번만 처리한다 — 셸을 거치는 모든 탭이 자동으로 해당된다.

## D17. 하단 여백은 안전 영역을 더해야 한다

하단 내비는 `pb-[env(safe-area-inset-bottom)]`으로 **기기에 따라 두꺼워진다.** 그런데 본문은 `pb-24`(96px) 고정이었다. 노치 기기에서는 내비가 96px을 넘어 마지막 카드를 덮는다 — 데스크톱에서는 인셋이 0이라 재현되지 않는다.

`pb-[calc(6rem+env(safe-area-inset-bottom))]` — 같은 인셋을 양쪽이 함께 반영한다.

## D18. 음식기록 탭은 끼니 탭이 첫 줄 — 앱 헤더를 감춘다

이 탭은 화면 하나에 **기록 목록 + 합계 + "지금 추가하기"(3탭 + 목록 + 시트)** 를 다 담는다. 다섯 탭 중 세로 공간이 가장 모자란 화면인데, 맨 위 56px을 서비스명 줄이 상시로 차지하고 있었다.

헤더를 감추고 그 자리를 **끼니 탭이 대신한다.** 프로필 진입은 나머지 네 탭에 그대로 있고, 하단 내비도 그대로라 나갈 길은 막히지 않는다.

**그래서 알약이 아니라 밑줄이다.** 알약 세그먼트(`SegmentedTabs`)는 트랙 면 위에 떠 있어야 하는 컨트롤이라 화면 첫 줄에 놓으면 그만큼 본문이 밀린다. 밑줄 탭은 아래 경계선에 붙어 자리를 덜 먹고, 활성 표시를 브랜드 색이 맡는다.

`UnderlineTabs`를 `ui/`에 새로 둔다 — `SegmentedTabs`에 모드를 더하지 않는다. 둘은 쓰임이 다르다:

| | `SegmentedTabs`(알약) | `UnderlineTabs`(밑줄) |
| --- | --- | --- |
| 자리 | 본문 **안** | 화면 **첫 줄** |
| 면 | 트랙 위에 뜬다 | 경계선에 붙는다 |
| 쓰는 곳 | "지금 추가하기" 3탭 | 끼니 5탭 |

`role="tab"`을 쓰지 않는 것은 `SegmentedTabs`와 같은 이유다 — 화살표 이동·`aria-controls`까지 갖추지 않을 거면 `aria-pressed` 버튼이다.

## D19. 빈 상태는 즐겨찾기와 같은 모양으로

한 줄짜리 문구가 `Card`(24px 라운드) 안에 들어 있었다. 내용에 비해 카드가 커 **알약처럼 떠 보이고**, 정작 "아직 없다"는 사실은 작게 읽혔다.

즐겨찾기 빈 상태(`EmptyFavorites`)와 같은 모양으로 맞춘다 — 일러스트 + 문구. 한 앱 안에서 "비어 있음"이 두 가지 모양이면 그 자체로 정보가 아니라 잡음이다.

**다음 행동 버튼은 두지 않는다.** DESIGN.md §6이 권하는 요소지만, 바로 아래가 "지금 추가하기"다 — 여기에 버튼을 또 두면 같은 곳으로 가는 입구가 한 화면에 둘이 된다.

곁가지로 **`EmptyFavorites`의 일러스트 색을 올렸다.** `border`(#e2e8f0)에 투명도 0.25~0.55를 걸어, 가장 옅은 조각이 흰 면 위에서 #f7f9fa까지 흐려져 **그림이 있는지도 안 보였다.** 바탕을 `muted`로 바꾼다 — 투명도는 그대로라 층위는 유지된다.

## D20. 파괴적 확인 버튼에 색을 채운다

`ConfirmSheet`의 실행 버튼은 흰 바탕 + 빨간 글씨였다. **강조하지 않으려는 의도**였는데(원래 주석에 그렇게 적혀 있다), 결과적으로 **버튼으로 읽히지 않아** 무엇을 눌러야 지워지는지 찾게 됐다.

`Button`에 `danger` 변형을 더한다(`bg-danger` + 흰 글씨, 6.4:1로 AA 통과). 강조하지 않으려던 의도는 **자리와 너비**가 계속 맡는다 — 취소가 왼쪽에서 넓게, 실행이 오른쪽에서 좁게. 눈에 띄는 것과 손이 먼저 가는 것은 다르다.

`SURFACE.danger`와 `PAIRS`의 `onBrand on danger`를 `tokens.ts`에 더했다 — 면으로 쓰는 색이 늘면 대비 검증도 따라와야 한다(DESIGN.md 7).

## D21. 음식기록 탭이 날짜를 갖는다 — 그리고 주소가 그 날짜를 들고 있다

이 탭은 "오늘만 담는 화면"이었고 지난 날짜는 홈에서 넘겨봤다. 그런데 **홈에서 날짜를 옮기고 넘어와도 기록 화면은 늘 오늘이었다** — 두 화면이 서로 다른 날을 보고 있었다.

**날짜는 화면 상태가 아니라 주소가 든다**(`?date=2026-08-06`).

```
홈(8월 6일 보는 중) ── 전체보기 ──▶ /app/records?date=2026-08-06
```

상태로만 두면 넘겨줄 방법이 없고, 뒤로가기·새로고침에도 날아간다. 오늘이면 파라미터를 붙이지 않는다 — 기본값이라 주소만 길어지고, **05시 경계를 넘겼을 때 `today` 동기화가 그대로 따라와야** 한다.

⚠️ 주소창 값은 검증한다. 형식이 아니거나 **미래 날짜면 무시하고 오늘**을 본다 — 아직 먹지 않은 날에 담을 이유가 없다.

**담는 날짜도 함께 바뀐다.** 예전 `recordItems`는 담는 순간 `todayServiceDate()`를 다시 읽어 **무조건 오늘로 밀어넣었다.** 이제 보고 있는 날짜로 간다. `eatenAtFor`가 오늘이면 지금 시각, 과거면 정오를 쓴다(과거에 새벽 시각을 쓰면 05시 경계에 하루 밀린다) — 그 함수의 과거 분기는 "날짜 선택이 생길 때를 위해" 남겨둔 코드였고 이번에 실제로 쓰인다.

**주간 띠는 월요일 시작**이다. 한국 달력·주간 리포트가 모두 월요일부터라 여기만 일요일 시작이면 어긋난다.

곁가지로 `koreanWeekday`를 `features/weight/estimator.ts`에서 `lib/date.ts`로 옮겼다 — 체중 추세선과 주간 띠가 함께 쓰는데 한 곳에 없으면 요일 규칙이 갈린다.

## D22. 옛 홈 화면 아이콘을 랜딩에서 걸러낸다 (배포 차단이던 것)

**증상** — 배포하는 순간, 이미 설치된 아이콘을 누르면 주소창 없는 전체 화면에 앱이 아니라 **소개 페이지**가 뜬다. 이미 설치한 사람에게 "홈 화면에 추가하세요"까지 보여준다.

**원인** — `start_url`이 `/` → `/app`으로 바뀌었는데(50009a1), **그 값은 설치 시점에 박힌다.**

```
$ git merge-base --is-ancestor 50009a1 origin/release
→ release에 랜딩 아직 없음 (배포 전)
```

운영에 나가 있는 빌드는 아직 `start_url: '/'`다. 그래서 지금 설치된 모든 아이콘은 `/`를 연다 — 배포되면 그 `/`가 `LandingPage`다.

| | manifest 갱신 |
| --- | --- |
| iOS | 설치 시점에 고정. **재설치 말고는 방법이 없다** |
| Android | Chrome이 WebAPK를 갱신하지만 하루 남짓 걸린다 |

**왜 코드로 막아야 하나** — `landing-install` 스펙이 이미 규정하고 있다:

> 설치된 앱에서 실행하면 소개 화면을 거치지 않고 곧바로 앱으로 들어가야 한다(MUST)

manifest만으로는 **새로 설치하는 사람에게만** 참이다. 그리고 `isStandalone()`은 이미 있었지만 **설치 안내를 숨길지 정하는 데만** 쓰이고 있었다 — 어디로 보낼지는 아무도 보지 않았다.

**고친 방식** — 루트 라우트에 껍데기를 하나 두고 훅을 부르기 전에 가른다.

```tsx
export function LandingRoute() {
  if (isStandalone()) return <Navigate to={APP_ROOT} replace />
  return <LandingPage />
}
```

`LandingPage` 안에서 조기 반환하면 훅 순서가 조건부가 된다(그 컴포넌트는 훅을 여럿 쓴다). 껍데기를 분리하면 훅이 없어 안전하다.

이렇게 두면 **`start_url`을 앞으로 또 옮겨도 안전하고**, `add-landing-install-guide` 7.5의 "아이콘 삭제 후 재설치"라는 수동 절차도 사라진다(그 항목의 문구도 함께 고쳤다 — 남겨두면 다음 사람이 없는 문제를 손으로 때운다).

⚠️ 이 change의 주제 밖이지만 **배포를 막는 결함**이라 여기서 함께 고친다.

## 구현 이탈

**나이 환산은 별도 힌트가 아니라 라벨에 붙였다** (D1 보완). 처음에는 `Field`에 `hint` 프로퍼티를 더해 입력 아래에 "만 32세"를 두려 했다. 그러려면 힌트를 `aria-describedby`로 입력에 묶어야 하는데, `Field`는 children을 그대로 렌더할 뿐 복제하지 않아 그 배선을 넣을 자리가 없다. 라벨 자체를 `출생연도 (36세)`로 만들면 **연결이 정의상 보장되고** 모든 화면이 쓰는 공유 컴포넌트를 건드리지 않는다.

**체중 탭 카드에서 근거 배지의 자리가 옮겨졌다** (D4의 대가). 공유 전에는 제목 줄 오른쪽(`내 유지칼로리 ────── [최근 14일 실측]`)에 있었는데, 제목은 껍데기가 갖고 배지는 본문이 가지므로 **숫자 줄 오른쪽**으로 내려왔다. 제목을 본문에 넣으면 시트의 제목("유지칼로리 다시 계산")과 겹쳐 두 번 읽힌다. 배지가 근거를 붙이는 대상은 제목이 아니라 숫자이므로 오히려 붙어야 할 자리에 가깝다.

**`Member.updateProfile`이 7인자가 되어 호출부를 함께 고쳤다.** 위치 인자만 늘어난 형태라 `WeightSummaryIntegrationTest`의 두 호출에 `null, null`을 앞에 채웠다. 인자가 더 늘면 파라미터 객체로 바꿀 때가 되지만, 이번 요청 범위 밖이라 두었다.

**홈 끼니 칩은 `bg-track`이 아니라 `bg-brand-soft`다** (D14 갱신). 처음에는 중립 칩으로 뒀는데 "회색이라 존재감이 없다"는 지적을 받아 브랜드 톤으로 올렸다(task 10.1). **D14의 금지선은 그대로 지킨다** — 끼니마다 다른 색을 배정하지 않는다(그러면 같은 줄의 탄단지 칩과 섞인다). 다섯 끼니가 모두 같은 브랜드 톤이라 색은 "끼니 칩"이라는 종류만 말하고, 어느 끼니인지는 글자와 정렬(D15)이 말한다.

**05시 경계 보호를 되살렸다** (D21 보완, PR #42 리뷰). `?date=` 리팩터가 예전 `recordItems`의 서비스일 재읽기를 걷어냈는데, `today`는 마운트와 `visibilitychange`에서만 갱신되므로 **화면을 포그라운드에 열어둔 채 05시를 넘기면 낡는다.** 그 상태로 담으면 `eatenAtFor`가 과거 분기를 타 **전날 정오**로 저장된다 — 05시 경계가 존재하는 이유인 야식 사용자가 정확히 이 경우다. 담는 순간 서비스일을 다시 읽되 **오늘을 보고 있을 때만** 적용해, 지난 날짜 담기(이 change가 새로 연 것)는 그대로 둔다. 화면의 `today`도 함께 갱신해 주간 띠·날짜 상한·목록이 낡은 날에 머물지 않게 했다.

**미래 연도 검증은 어노테이션이 아니라 서비스에 뒀다** (D1대로). `@Max`는 컴파일 시각 상수만 받으므로 "올해"를 넣을 수 없다. `MemberService`가 주입받은 KST `Clock`으로 판정하고, 하한(1920)만 `@Min`으로 남겼다 — 그래서 하한 위반은 검증 400, 상한 위반은 `IllegalArgumentException` → 400으로 **경로가 갈린다.** 응답 형태는 둘 다 ProblemDetail이라 클라이언트에서는 같아 보인다.
