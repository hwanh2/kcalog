# Design: add-observability

## Context

운영은 VM 한 대(t3.small, 2GB)에 Traefik + 백엔드 + Postgres가 docker compose로 올라가 있다. 관측 수단은 `/actuator/health` 하나뿐이고, 그마저 배포 워크플로가 기동을 확인하는 데만 쓴다. 로그는 docker `json-file` 드라이버로 컨테이너당 10MB × 3개만 남는다.

측정한 실사용 메모리는 다음과 같다(`add-deployment` 6.8 확인).

```
전체 1.9Gi, 사용 946Mi, available 960Mi, swap 2.0Gi
backend 397MB, db 54MB, traefik 21MB
```

**컨테이너별 메모리 제한이 없다.** 그래서 `-XX:MaxRAMPercentage=70`이 VM 전체를 기준으로 계산되어 JVM 최대 힙이 약 1.3GB가 된다. 지금 397MB인 것은 아직 그만큼 쓰지 않아서일 뿐이다. 이 사실이 "모니터링을 앱 서버에 올리지 않는다"는 결정의 근거가 된다.

결정은 사용자 그릴링(2026-08-17) 확정. 목적은 **장애 대응**이며 인지와 원인 파악까지를 이번 범위로 한다.

## Decisions

### D1. 모니터링을 전용 VM으로 분리한다

앱 서버에 올리지 않는다. **감시자가 감시 대상과 함께 죽으면 볼 수가 없다.** 메모리 부족으로 VM이 넘어가는 상황이 정확히 로그가 필요한 순간인데, 그때 Grafana도 같이 넘어간다.

앱 서버 사정도 이를 뒷받침한다. 여유가 960MB인데 JVM이 천장 없이 1.3GB까지 자랄 수 있어, 남은 자리는 언제든 JVM이 가져갈 수 있는 자리다. 여기에 모니터링을 얹으면 OOM 킬러가 도는데 **커널은 대체로 가장 큰 프로세스를 죽인다.** 즉 백엔드가 죽는다. 모니터링하려다 서비스를 죽이는 구조다.

**t3.micro(1GB)를 고른다.** 처음에는 t4g.micro(ARM)를 골랐다. 같은 값에 성능이 낫기 때문인데, **프리 티어에 해당하지 않아** 바꿨다. t4g의 무료 체험 프로그램은 끝났고 지금 750시간 무료는 t2, t3 계열이다. 한 대를 24시간 돌리면 그 안에 덮인다.

t2.micro는 여전히 제외한다. 크레딧이 마르면 성능이 급락하는데, 모니터링은 꾸준히 조금씩 CPU를 쓰는 작업이라 서서히 말라 **정작 장애 때 쿼리가 느려진다.** t3는 기본이 unlimited 모드라 크레딧이 떨어져도 계속 돈다. 대가는 기준선(vCPU당 10퍼센트)을 오래 넘기면 초과분에 과금되는 것인데, 이 부하에서는 기준선 안에 들 것으로 본다. 청구서에 `CPUCredits`가 보이면 `standard` 모드로 바꾼다.

ARM에서 x86으로 바뀌었지만 **설정은 하나도 고치지 않았다.** Grafana, Loki, Prometheus, node exporter 모두 두 아키텍처 이미지를 제공한다.

**같은 리전, VPC, AZ에 둔다.** 프라이빗 IP로 통신해 인터넷을 타지 않고, 같은 AZ 안의 데이터 전송은 무료다. AZ 장애 시 둘 다 죽는다는 단점은 감수한다. 서버가 한 대라 그 경우 서비스도 같이 죽고, 인지는 외부 업타임 서비스가 맡는다.

보안 그룹 규칙은 IP가 아니라 **상대 보안 그룹 ID로 참조**한다. 인스턴스를 껐다 켜면 프라이빗 IP가 바뀐다.

### D2. 1GB에 로그와 메트릭을 모두 올린다

```
OS와 도커      약 200MB
Grafana        약 150MB
Loki           약 200MB
Prometheus     약 200MB
              ─────────
               약 750MB / 1GB
```

빠듯하지만 들어간다. **Prometheus 메모리는 시간이 아니라 활성 시계열 수에 비례하고**, kcalog 규모(Spring Boot 기본 + HTTP + 필요 시 exporter)는 2,000~5,000개 수준이라 대체로 평평하다. 스왑을 잡아 순간적인 초과를 흡수한다.

메트릭을 넣는 이유는 **운영 서버가 지는 부담이 거의 없기 때문**이다. micrometer 레지스트리는 JVM 안에서 5~20MB이고 계산은 긁어갈 때만 한다. 반면 "언제부터 이상했나"는 로그만으로 잘 보이지 않는다.

⚠️ 진짜 위험은 **카디널리티 폭발**이다. 라벨에 사용자 ID나 실제 경로값이 들어가면 시계열이 곱셈으로 늘어 메모리가 GB 단위로 뛴다. Spring Boot는 기본적으로 URI 템플릿(`/api/meals/{id}`)을 쓰므로 그냥 두면 안전하고, 커스텀 태그를 추가할 때만 조심하면 된다.

### D3. 메트릭은 긁어가고(pull) 로그는 밀어넣는다(push)

```
운영 → 모니터링   Alloy가 로그를 Loki로 보냄        (Loki 3100)
모니터링 → 운영   Prometheus가 메트릭을 긁어감       (운영 8081)
```

**양방향이 된다.** 단방향(Alloy가 메트릭까지 remote write)으로 만들면 운영 서버 인바운드를 하나도 열지 않아도 되지만, 그 대가로 `up=0`을 잃는다.

`up=0`은 Prometheus가 긁으러 갔다 실패하면 자동으로 기록되는 값이다. **가장 흔한 장애가 "백엔드가 응답을 안 한다"**인데, pull이면 그게 메트릭 한 줄로 잡혀 알림을 바로 건다. push면 "데이터가 안 온다"를 알림으로 만들어야 하는데, 그것은 네트워크 문제나 수집기 문제와 구분되지 않는다.

### D4. actuator를 관리 포트 8081로 분리한다

지금 `/actuator/health`는 인증 없이 공개되어 있다. `include`에 `prometheus`를 더하면 **힙 사용량, 커넥션 풀, 엔드포인트별 호출량이 그대로 인터넷에 공개된다.**

`management.server.port: 8081`을 쓰면 actuator 전체가 그쪽으로 옮겨가고, Traefik은 8080만 라우팅하므로 도메인으로는 닿지 않는다. 8081은 보안 그룹으로 모니터링 서버만 허용한다.

**여기서 배포 헬스체크가 끊긴다.** 워크플로가 `https://api.kcalog.site/actuator/health`를 확인하는데 그 경로가 사라진다. Traefik 라우터를 하나 더 두어 **health 경로만 8081로 공개 라우팅**한다.

```
Host(api.kcalog.site)                            → backend:8080
Host(api.kcalog.site) && Path(/actuator/health)  → backend:8081
```

`/actuator/prometheus`는 어느 규칙에도 걸리지 않아 외부에서 404가 된다.

대안이었던 "워크플로가 SSH로 들어가 localhost를 확인"은 **인증서와 Traefik 라우팅 검증을 잃는다.** 인증서 갱신 실패는 실제로 일어나는 사고인데 배포는 성공으로 뜨게 된다. 지금 체크가 앱 기동과 TLS를 함께 검증하고 있어 그 성질을 유지한다.

### D5. 운영 로그를 JSON으로 찍고 요청 ID를 붙인다

평문 로그의 문제는 검색이 아니라 **자바 스택 트레이스**다. 수집기는 줄 단위로 자르므로 `log.error("...", e)` 한 번이 30여 개의 독립된 기록이 된다. `|= "ERROR"`로 찾으면 첫 줄만 걸리고 정작 필요한 `MealService.java:42`는 빠진다. 동시 요청이 있으면 그 사이에 남의 로그가 끼어 찢어진다.

수집기에 다중행 이어붙이기 규칙을 넣을 수 있으나 정규식으로 "새 기록의 시작"을 판별하는 방식이라 잘 깨지고, **깨져도 조용히 깨진다.**

JSON으로 찍으면 줄바꿈이 `\n` 문자가 되어 물리적으로 한 줄이 된다. Spring Boot 4는 설정 한 줄로 지원하므로 logback XML도 의존성도 필요 없다.

```yaml
logging:
  structured:
    format:
      console: ecs
```

**운영 프로파일에만 켠다.** 로컬은 사람이 읽는 평문을 유지한다. 대신 VM에서 `docker logs`로 직접 볼 때 읽기 어려워지는 것은 감수한다.

**요청 ID를 MDC에 넣고 응답 헤더로도 내보낸다.** 장애를 볼 때 실제로 하는 일은 "이 요청이 왜 실패했나"를 따라가는 것인데, ID가 없으면 시간대로 짐작해야 하고 동시 요청이 섞이면 못 쓴다. 사진 분석처럼 오래 걸리는 요청이 있어 더 그렇다. 헤더로 내보내면 사용자가 알려준 ID로 곧장 찾을 수 있고, 랜덤 값이라 노출 위험이 없다.

### D6. Loki 라벨은 app, container, level까지만

**Loki는 라벨만 인덱싱하고 본문은 훑는다.** 라벨 조합 하나가 스트림 하나이며, Prometheus의 시계열과 같은 방식으로 터진다.

`level`은 값이 다섯 개로 고정이라 스트림이 최대 15개 수준에 그친다. 그러면서 **가장 자주 거는 조건**(`{level="ERROR"}`)을 인덱스로 처리해 준다.

요청 ID, 사용자, 엔드포인트는 **JSON 필드로 두고 쿼리 시점에 거른다.**

```
{app="kcalog", level="ERROR"} | json | requestId = "a1b2c3"
```

앞의 중괄호가 인덱스로 범위를 좁히므로 뒤쪽 훑기는 충분히 빠르다. 이것이 Loki가 의도한 사용법이고, Elasticsearch보다 훨씬 적은 자원으로 도는 이유다.

⚠️ Alloy가 JSON을 파싱해 `level`을 **라벨로 승격**시키도록 설정해야 한다. 그냥 두면 본문 안에만 남고 라벨이 되지 않는다. 설정에서 실수가 잦은 지점이다.

### D7. 수집기는 Grafana Alloy

Promtail은 Alloy로 대체되며 지원이 종료됐다. 새 구성에서 고를 이유가 없다.

docker 로깅 드라이버로 Loki에 직접 보내는 방법도 있으나, 플러그인 설치가 필요하고 Loki가 죽었을 때 동작이 덜 명확하다. 에이전트 방식이 표준이고 디버깅이 쉽다.

### D8. 보관 30일, 디스크 20GB

```
OS와 이미지        약 6GB
Prometheus 30일    약 1.5GB   (5,000 시계열 × 15초 → 하루 약 50MB)
Loki 30일          약 1GB
                  ─────────
                   약 8.5GB / 20GB
```

**30일을 고른 이유**는 "이게 언제부터 이랬지"에 답하기 위해서다. 2주로는 지난달과 비교할 수 없고, 월 단위로 도는 문제는 아예 보이지 않는다. 디스크 값 차이가 월 $0.8이라 아끼는 의미가 없는 반면, 디스크가 차서 로그를 잃으면 그 순간이 정확히 필요할 때다. EBS는 키울 수 있어도 줄일 수 없으니 크게 잡는 쪽이 되돌리기 쉽다.

🔴 **Loki는 기본값이 "안 지움"이다.** Prometheus는 보관 기간이 기본 15일이라 알아서 지우지만, Loki는 compactor와 retention을 명시적으로 켜지 않으면 영원히 쌓인다. 놓치면 디스크가 차고, **Loki는 죽는 대신 로그를 못 받는 상태로 조용히 버틴다.** 정작 장애 때 로그가 없다.

### D9. Grafana는 Tailscale 안에만 연다

장애는 책상 앞에 있을 때 나지 않으므로 **폰에서 볼 수 있어야** 한다. 그 조건에서 세 선택지를 비교했다.

| | 노출면 | 폰 | 추가 비용 |
| --- | --- | --- | --- |
| SSH 터널만 | 없음 | 사실상 불가 | 없음 |
| 공개 도메인 + TLS | 있음 | 됨 | 리버스 프록시 50MB, 인증서, 공개 로그인 화면 |
| **Tailscale** | 없음 | 됨 | 에이전트 30MB |

공개 도메인은 처음엔 무난해 보였으나, **1GB 서버에서 리버스 프록시 50MB가 아깝고** Grafana를 계속 최신으로 유지할 의무가 생긴다. 모니터링 때문에 지켜야 할 것이 늘어나는 건 방향이 거꾸로다.

Tailscale은 에이전트가 밖으로 나가는 연결을 맺으므로 인바운드를 열지 않고, WireGuard가 기기 사이를 암호화하므로 인증서도 필요 없다. 회사에서 Grafana를 VPN이나 SSO 뒤에 두는 구조를 1인 프로젝트에서 재현하는 방법이다.

의존 서비스가 하나 느는 것은 감수한다. Tailscale이 죽어도 SSH는 살아 있어 최후 수단이 남는다.

**네트워크가 막혀 있어도 Grafana 자체 로그인은 켠다.** 기본 계정을 그대로 두지 않는다.

### D10. 감시자를 둘로 둔다

```
외부 업타임 모니터   →  kcalog가 살아있나 (밖에서 찔러본다, 사용자와 같은 경로로)
외부 heartbeat     ←  모니터링 VM이 살아있다고 신호를 보낸다 (끊기면 알림)
Grafana 알림       →  up=0, 디스크 임계
```

외부 서비스가 **모니터링 VM도 감시하는 것**이 핵심이다. 그러지 않으면 모니터링이 조용히 죽었을 때 "알림이 안 오는 것"과 "아무 일 없는 것"이 구분되지 않는다.

⚠️ **두 번째는 방향이 반대다.** 처음에는 이것도 밖에서 찔러보는 것으로 적었는데, 그렇게 할 수 없다. 모니터링 VM은 D9에 따라 Grafana를 Tailscale 안에만 열고 보안 그룹도 SSH만 허용하므로 **밖에서 찌를 대상이 없다.** 억지로 포트를 열면 노출을 없애려던 D9을 스스로 무너뜨린다.

그래서 VM이 밖으로 신호를 보내고, 신호가 끊기면 외부 서비스가 알린다. 이것이 원래 데드맨 스위치의 형태이고, 인바운드를 하나도 열지 않는다.

```bash
*/5 * * * * curl -fsS -m 10 https://hc-ping.com/<uuid> > /dev/null
```

**초기 알림은 행동이 필요한 것만 넣는다.** 알림 설계의 흔한 실패는 알림 피로이고, 하루에 몇 번씩 오면 사람은 곧 안 본다. 그러면 진짜 장애를 놓친다.

**에러 급증 알림은 일부러 뺐다.** 평소 에러가 몇 건인지 모르는 상태에서 임계값을 잡으면 오탐이 쏟아진다. 2주쯤 관찰한 뒤에 넣는다.

**알림은 슬랙으로 보낸다.** 이메일도 검토했으나 두 가지가 걸린다. 메일함에 묻혀 즉시 인지가 어렵고, 무엇보다 **조용히 끊길 수 있다.** 앱 비밀번호 폐기나 스팸 분류로 발송이 실패하면 그 사실을 알려줄 수단이 다시 메일이다. 웹훅은 URL 하나로 끝나고 스팸 필터가 없다. 디스코드도 같은 조건이었으나, 이미 쓰는 도구가 있으면 알림이 그리로 모이는 편이 낫다.

### D11. 구성은 레포에, 배포는 수동

모니터링 VM은 한 번 세우면 거의 건드리지 않는다. 대시보드는 Grafana 안에서 만들고, 파일을 고칠 일은 알림 규칙을 추가할 때 정도다. 그 빈도에 워크플로와 SSH 시크릿 한 벌을 더 두는 것은 손해다.

반대로 **레포에 두는 것은 반드시 한다.** 서버 한 대에만 있는 설정은 그 서버와 함께 사라진다. 특히 D8의 Loki 보관 설정처럼 빠뜨리면 조용히 망가지는 것들은 코드로 남아 있어야 다음에 틀리지 않는다.

앱 서버 쪽 Alloy는 `deploy/compose.prod.yml`에 넣어 **기존 배포 워크플로가 그대로 올린다.** 이미 compose 파일과 `backup.sh`를 scp로 보내고 있다.

⚠️ 이 방식의 함정은 **레포와 서버가 어긋나는 것**이다. 급해서 서버에서 직접 고치고 반영을 잊으면 재구축 때 사라진다. `release` 역머지 누락과 같은 종류의 위험이라 README에 규칙으로 적는다.

### D12. 구성은 로컬에서 확인한 뒤 올린다

모니터링 구성은 **틀려도 조용한 것들**이 많다. D8의 Loki 보관 설정이 대표적이고, Alloy의 라벨 승격도 빠뜨리면 그냥 라벨이 비어 있을 뿐 아무도 알려주지 않는다. 서버에서 처음 돌리면 이런 것을 발견할 수단이 없다.

그래서 맥에서 Loki, Prometheus, Grafana, Alloy를 띄워 대시보드까지 확인한 뒤 VM으로 옮긴다. 지표 수집, `up=0`, 로그 조회, 레벨 라벨, 요청 ID 검색까지 전부 로컬에서 볼 수 있다. VM에서만 확인 가능한 것은 보안 그룹, Tailscale, 두 서버 사이 통신뿐이다.

이를 위해 **스크레이프 대상을 환경변수로 뺀다.** 값을 파일에 박으면 로컬에서 확인한 파일과 운영에 올리는 파일이 달라져서, 확인했다는 사실이 의미를 잃는다.

```
로컬   host.docker.internal:8081
운영   <앱 서버 사설 IP>:8081
```

### D13. 두 서버 모두에 node exporter를 둔다

micrometer는 **JVM 안만 본다.** 힙이 90퍼센트인 것은 알려주지만 디스크가 찼는지, 서버 메모리가 말라 스왑으로 밀리는지는 모른다. 그리고 실제로 서비스를 죽이는 것은 대개 아래쪽이다.

구현 중에 이 구멍이 드러났다. D10에서 "디스크 85퍼센트 초과"를 알림 항목으로 정해 놓고, **그것을 관측할 수단을 설계에 넣지 않았다.** 특히 모니터링 VM의 디스크는 차면 Loki가 죽는 대신 로그를 못 받는 상태로 조용히 버티는 자리라(D8), 감시가 없으면 그 상황을 알 방법이 아예 없다.

**앱 서버에도 둔다.** 지금 컨테이너 메모리 제한이 없어 JVM 최대 힙이 VM 전체의 70퍼센트(약 1.3GB)로 잡히는데, 그 값을 다음 change에서 정하려면 **서버 전체가 어떻게 흘러가는지**를 봐야 한다. 앱이 OOM으로 죽은 뒤에는 앱 지표가 오지 않으므로, 그때 남는 증거가 호스트 지표뿐이기도 하다.

대가는 시계열이다. 기본 설정이면 호스트당 500에서 1000개인데, 쓸 일 없는 수집기(mdadm, nfs, zfs 등)를 끄고 도커 overlay 마운트를 제외해 **두 서버 합쳐 610개**로 줄였다. 전체는 약 1,043개로 D2에서 예상한 범위 안이다.

cAdvisor(컨테이너별 지표)는 두지 않는다. 컨테이너 수에 비례해 시계열이 더 늘어나는데, 컨테이너가 몇 개 안 되어 얻는 것에 비해 비싸다.

⚠️ 표준 예제의 `rslave` 마운트 전파를 쓰지 않는다. macOS Docker Desktop이 지원하지 않아 로컬에서 뜨지 않고, 그러면 로컬에서 확인한 파일과 운영 파일이 갈린다(D12). 대가는 컨테이너가 뜬 뒤 새로 생긴 마운트를 못 보는 것뿐이다.

## Risks / Trade-offs

- **[SSH가 인터넷에 열려 있음]** 앱 서버와 같은 상태다. 키 인증만 허용되므로 자동화된 시도는 로그만 남긴다. Tailscale이 붙은 뒤에는 22번 규칙을 지워 노출을 없앨 수 있다(D9의 부수 효과). 다만 Tailscale이 죽으면 접속 수단이 사라지므로, 실제로 되는 것을 확인한 뒤에 닫는다.
- **[1GB에 750MB]** 여유가 250MB뿐이라 Grafana에서 무거운 쿼리를 돌리면 순간적으로 조인다. 스왑으로 흡수하되, 카디널리티가 늘면 t4g.small(2GB, 월 $6 추가)로 올려야 한다.
- **[관리 포트 이전이 배포를 막을 수 있음]** Traefik 라우팅이 의도대로 돌지 않으면 배포 헬스체크가 실패해 배포 전체가 막힌다. 되돌리기는 쉽지만(이전 커밋을 release에 올림) 배포 직후 반드시 확인해야 한다.
- **[운영 서버 인바운드가 하나 늘어남]** D3의 대가. 8081을 보안 그룹으로 모니터링 서버만 허용해 실질적으로 닫지만, 규칙이 잘못 열리면 내부 지표가 노출된다.
- **[JSON 로그의 가독성]** VM에서 `docker logs`로 급히 볼 때 읽기 어렵다. `| jq -r '.message'`를 쓰게 된다.
- **[Tailscale 의존]** 접속 경로가 외부 서비스에 묶인다. 장애 시 SSH가 최후 수단이다.
- 🔴 **[감시자를 감시하는 수단이 없음]** D10은 외부 서비스가 모니터링 VM도 감시하게 하려 했으나 이번 범위에서 뺐다. 그 결과 **Grafana가 죽으면 아무도 알려주지 않는다.** 조용한 상태가 "정상"인지 "감시가 멈춤"인지 구분되지 않는다. 서비스 자체는 여전히 Grafana 알림으로 감시되므로, 잃는 것은 그 감시가 살아 있다는 보장뿐이다. heartbeat 하나로 닫을 수 있다.
- **[모니터링 VM은 백업 대상이 아님]** 날아가면 그때까지의 로그와 메트릭을 잃는다. 구성은 레포에 있어 재구축은 되지만 데이터는 복구하지 않는다. 관측 데이터는 유실을 감수하는 성질의 것으로 본다.
- **[비용 증가]** 월 $8 내외. 프리 티어 해당 여부는 계정 생성 시점에 따라 다르다.
- **[재발 방지가 미뤄짐]** 백엔드에 헬스체크가 없어 JVM이 응답 못 하는 상태로 살아 있으면 자동 복구되지 않는 상태가 유지된다. 다음 change에서 메트릭을 근거로 다룬다.

## Migration Plan

**PR 하나로 간다.** 처음에는 셋으로 나눌 생각이었으나, 혼자 하는 프로젝트에서 리뷰 단위로 쪼개는 이득이 작다. 절반이 콘솔에서 하는 수동 작업이라 PR에 드러나지도 않는다.

대신 **배포 순서에 제약이 생긴다.**

```
머지 → 모니터링 VM 생성하고 Loki 기동 → 그다음 release 배포
```

Alloy가 `compose.prod.yml`에 있어 배포되는 순간 뜬다. 그때 Loki가 없으면 보낼 곳이 없어 재시도하며 에러 로그를 쌓는다. 모니터링을 붙이려다 로그를 더럽히는 모양이 된다.

나눌 이유로 유일하게 남았던 것은 **관리 포트 이전의 배포 위험**이었다. 따로 나가면 되돌릴 때 그 커밋 하나만 되돌리면 되고, 합치면 모니터링 구성까지 함께 빠진다. 다만 그 시점에 모니터링은 아직 운영에서 아무 일도 하지 않으므로 실질적인 손해가 없다고 보고 합쳤다.

구성 파일은 **로컬에서 먼저 띄워 확인한 뒤** VM에 올린다. Loki 보관 설정처럼 틀려도 조용한 것들은 서버에서 처음 돌리면 틀렸는지 알 수 없다. 그래서 스크레이프 대상은 환경변수로 빼서 같은 파일이 로컬과 운영 양쪽에서 돌게 한다(D12).

## 구현 이탈 (design 대비)

### Spring Security가 관리 포트에도 적용된다 (D4 보강)

설계 때는 관리 포트가 별도 컨텍스트라 인증 밖일 것으로 보았으나, **실측 결과 메인 필터 체인이 그대로 적용됐다.**

```
8081/actuator/health      200
8081/actuator/prometheus  401   WWW-Authenticate: Bearer
```

그대로 두면 Prometheus 수집이 통째로 막힌다. `/actuator/**`를 인증 없이 열되, **노출을 막는 근거가 인증이 아니라 포트라는 사실**을 코드로 못 박았다. `management.server.port`가 없거나 애플리케이션 포트와 같으면 `ConfigurationSanityCheck`가 운영 프로파일 기동을 막는다. 누군가 그 설정을 지우면 인증 없이 열어둔 규칙이 공개 도메인에 그대로 걸리기 때문이다.

### MDC가 비동기 스레드로 전파되지 않는다 (D5 보강)

D5는 "사진 분석처럼 오래 걸리는 요청"을 요청 ID의 근거로 들었는데, **그 분석이 정확히 식별자가 끊기는 지점**이었다. MDC는 스레드에 매인 값이고 `analysisExecutor`는 별도 스레드 풀이라, 필터만 넣으면 정작 필요한 로그에 ID가 붙지 않는다.

실행기에 `TaskDecorator`를 달아 제출 시점의 MDC를 옮긴다. 실행 후에는 **되돌린다.** 풀이 스레드를 재사용하므로 지우지 않으면 다음 작업에 이전 요청의 식별자가 붙고, 거부 정책이 `CallerRunsPolicy`라 요청 스레드에서 그대로 실행되는 경우 호출자의 MDC를 덮어쓸 수도 있다.

### ECS 포맷의 필드 위치 (D6에 영향)

실제 출력을 확인한 결과 **레벨은 중첩, MDC는 최상위**다.

```json
{"@timestamp":"...","log":{"level":"DEBUG","logger":"..."},"requestId":"9be1d3cb5c53","message":"..."}
```

Alloy에서 `level`을 라벨로 승격할 때 경로가 `log.level`(중첩)이고 요청 ID는 `requestId`(최상위)다. 평평한 `log.level` 키를 기대하면 조용히 비어 있게 된다.

### 처리하지 못한 예외의 스택 트레이스에는 요청 ID가 없다 (D5의 한계)

로컬에서 실제로 예외를 내보고 확인한 결과다. 요청 도중의 로그에는 식별자가 붙지만, **정작 스택 트레이스가 담긴 줄에는 없다.**

```
[WARN]  HikariPool-1 - Connection is not available   requestId=9b028a1d291d
[ERROR] Servlet.service() ... threw exception        requestId 없음, error.stack_trace 26줄
```

catch-all 예외 핸들러를 넣지 않아 예외가 Tomcat까지 올라가고, **그 로그는 필터 바깥에서 찍히므로 MDC가 이미 비워진 뒤**다.

`@ExceptionHandler(Exception.class)`를 추가하면 붙는다. 하지만 그것은 Spring이 이미 상태 코드를 아는 예외(지원하지 않는 메서드 405, 잘못된 본문 400)까지 잡아 **전부 500으로 바꾼다.** 관측을 붙이려다 API 동작을 바꾸는 일이라 하지 않는다.

**대신 스레드 이름으로 잇는다.** 스택 트레이스와 그 요청의 로그가 같은 스레드에서 나오므로 한 쿼리로 묶인다(로컬에서 19건으로 확인).

```
{app="kcalog"} | json | process_thread_name = "http-nio-8080-exec-3"
```

### Alloy는 kcalog 컨테이너만 읽는다

처음에는 도커의 모든 컨테이너 로그를 읽게 두었다. 운영 VM에는 kcalog 컨테이너뿐이라 문제가 없어 보였으나, **로컬에서 돌리니 다른 프로젝트 컨테이너에까지 `app="kcalog"` 라벨이 붙었다.** 이름으로 거르는 규칙을 앞에 두었다.

### 통합 테스트에서는 관리 포트를 되돌린다

관리 포트를 분리하면 actuator가 별도 컨텍스트로 가서 `MockMvc`가 닿지 못한다. `@IntegrationTest`에 `management.server.port=`를 넣어 테스트에서만 애플리케이션 컨텍스트로 되돌렸다. 컨텍스트를 갈라 Testcontainers가 하나 더 뜨는 것을 피하기 위해서다.

그래서 **포트 분리 자체는 통합 테스트가 검증하지 못한다.** 대신 `ConfigurationSanityCheckTest`가 규칙을 단위로 검증하고, 배포 후 외부에서 지표가 닿지 않는지 사람이 확인한다(tasks 4.3).
