# Design: revamp-food-record-tab

## Context

현재 `RecordsPage`는 날짜 입력 + 그날 식사 목록(수정·삭제)뿐이고, 등록은 FAB → `/meals/new`라는 별도 페이지가 전담한다. `MealItem`은 `name·kcal·carbG·proteinG·fatG` 다섯 필드가 전부라 수량 개념이 없고, `MealType`은 4개(야식 없음)다. 분석은 `POST /api/analyses`가 **멀티파트 이미지 필수**이며 `analysis_job.image_key`가 NOT NULL이라 사진 없는 분석이 구조적으로 불가능하다.

한편 개인 보정치(`FoodCorrection`)는 이미 "정규화된 음식 이름 → 내 확정 영양값"을 저장하고, 분석 시 덮어쓰기·프롬프트 주입으로 반영한다. 이번 change의 즐겨찾기와 데이터 모양이 겹치므로 관계 정리가 필요하다.

결정은 사용자 그릴링(2026-08-12) 확정. 사용자가 제시한 화면 캡처 3장(끼니 세그먼트·기록 카드/카탈로그 그리드/사진+프롬프트)을 기준으로 삼되, 세 번째는 참고용으로만 쓴다.

## Decisions

### D1. 음식기록 탭 = 끼니 세그먼트 + 기록 목록 + 지금 추가하기 (한 화면)

```
[ 아침 ① ]  점심 ②  저녁 ②  간식   야식      ← 세그먼트(배지 = 그 끼니 기록 수)
──────────────────────────────────────
🥣 그릭 요거트 볼    08:24   320 kcal        ← 선택된 끼니의 기록
아침 합계   320 kcal · 탄 34 단 22 지 9
──────────────────────────────────────
지금 추가하기
[ 자주먹는 ] [ 즐겨찾기 ] [ AI로 기록 ]
```

- 세그먼트는 **보기 필터이자 등록 대상**이다. "아침"이 선택된 상태에서 무엇을 담든 아침으로 기록된다. 담기 버튼 문구에 끼니를 박는다("아침에 기록하기") — 잘못된 끼니에 담는 사고를 문구로 막는다.
- 날짜 선택은 유지한다(과거 날짜 조회·수정). 과거 날짜를 보는 중에도 등록은 가능하며, 이때 `eatenAt`은 **그 날짜의 현재 시각**으로 둔다.

### D2. 기록 카드 = `Meal` 1건 (끼니당 여러 건 허용)

프리셋·즐겨찾기·AI 무엇으로 담든 **새 `Meal`을 만든다**. "끼니당 Meal 1개 + 항목 덧붙이기"를 택하지 않은 이유:

- `Meal.imageKey`가 **1개**다. 끼니당 Meal 1개로 강제하면 같은 끼니에 사진을 두 번 찍을 때 사진 하나를 버려야 한다.
- `Meal.source`(AI/MANUAL)도 Meal 단위다. 한 Meal에 AI 항목과 수동 항목이 섞이면 의미를 잃는다.
- 삭제 단위가 자연스럽다("방금 담은 달걀만 취소" = `DELETE /api/meals/{id}`). 항목 병합 방식은 items 전체 재전송(PATCH)이 필요하다.
- upsert 병합에 따르는 동시성(같은 끼니 동시 추가 시 Meal 중복) 문제가 없다.

끼니 배지 숫자와 "끼니 합계"는 **그 끼니 Meal들의 합산**으로 계산한다.

### D3. 수량·단위를 저장한다 (V13)

`meal_item`에 `quantity NUMERIC(6,2)`, `unit VARCHAR(20)` 추가(둘 다 nullable — 기존 기록·수량 개념이 없는 항목).

- **영양값은 이미 곱해진 총량을 저장한다.** `quantity`는 표시·재편집용 메타이며, 합계 계산(`Meal.recalculateTotals`)은 그대로 항목 값을 더한다.
- 단위는 **자유 텍스트**다("개·공기·g·알·컵·1/2개"). 열거형으로 묶으면 "1/2개" 같은 표기가 즉시 어긋난다.
- 이렇게 하는 이유: (1) "달걀 2개 → 3개"를 수량만 고쳐 재계산할 수 있다, (2) 즐겨찾기·개인 보정치에 **1인분 기준값**으로 환산해 저장할 수 있다. 수량이 없으면 2개분(140kcal)이 1개 기준값으로 오염된다.

### D4. 자주먹는 = 큐레이션 카탈로그 30개 (V14)

`food_catalog` 테이블에 시드로 넣는다. 공개 영양 DB(식약처 등) 연동은 하지 않는다 — 항목이 100g 기준이라 "1공기·1개" 같은 **먹는 단위**로 쓰려면 어차피 환산표를 우리가 만들어야 하고, 지금 필요한 건 검색 가능한 만물 DB가 아니라 탭 한 번에 담기는 30개다.

컬럼: `name` · `emoji` · `aliases`(쉼표 구분) · `base_quantity` · `unit` · `kcal` · `carb_g` · `protein_g` · `fat_g` · `sort_order`.

프론트 상수가 아니라 **서버 테이블**에 두는 이유: 값 보정에 앱 재배포가 필요 없고, 즐겨찾기·개인 보정치와 같은 자리에서 이어붙일 수 있다.

### D5. 즐겨찾기 = 나만의 음식 라이브러리 (V15)

`member_favorite_food` — `member_id` · `name` · `normalized_name` · `emoji`(nullable) · `quantity` · `unit` · 영양 4필드.

- **음식 1개 단위**로 담는다. 조합(세트)은 이번 범위 밖 — `favorite` + `favorite_item` 2테이블이 되고 수량 조절도 성립하지 않는다(세트를 풀어야 해서 세트의 이점이 사라진다). 단위 저장 위에 나중에 얹을 수 있다.
- 담는 경로 **3곳**: ① 카탈로그 카드의 ★ ② AI 분석 결과 항목의 ★ ③ 즐겨찾기 탭의 "직접 만들기". 기록 카드에서 담기는 넣지 않는다(②에서 이미 기회가 있었고 ③으로 언제든 만들 수 있다).
- 아이콘: 카탈로그에서 담은 항목은 **이모지를 물려받고**, 그 외는 **이름 첫 글자 배지**로 렌더한다(사용자에게 이모지를 고르게 하지 않는다).
- `normalized_name`은 `FoodNames.normalize`(공백 제거·소문자)를 재사용해 중복 저장을 막는다.

### D6. 즐겨찾기와 개인 보정치는 별개다

같은 데이터(이름 + 영양값)를 담지만 목적이 다르다 — 즐겨찾기는 **"빨리 담고 싶다"**, 보정치는 **"AI가 틀렸다"** 이다. 자동 연동하면 "담기 편하려고 눌렀는데 AI 분석 결과가 바뀌는" 부작용이 생긴다.

대신 즐겨찾기 저장 시트에 **"이 값을 AI 분석에도 반영" 체크박스**를 둔다. 체크하면 기존 "기억하기"와 같은 경로로 `FoodCorrection`도 저장한다.

**저장 값의 의미는 "그 섭취량 기준의 총량"이다** — 나누지 않는다(D14 참조).

### D7. 끼니 5개 · 자동 선택은 세그먼트 초기값에만

`MealType`에 `LATE_NIGHT` 추가. `meal_type`이 `VARCHAR(20)`이고 CHECK 제약이 없어 **마이그레이션이 필요 없다**.

자동 추정(`defaultMealType`)의 역할은 **탭 진입 시 어느 세그먼트가 눌려 있을지**로 축소된다. 저장되는 끼니는 언제나 눌려 있는 세그먼트다.

| 시각 | 초기 선택 |
|---|---|
| 00:00 ~ 05:00 | 야식 |
| 05:00 ~ 11:00 | 아침 |
| 11:00 ~ 15:00 | 점심 |
| 15:00 ~ 21:00 | 저녁 |
| 21:00 ~ 24:00 | 야식 |

**간식은 자동 선택하지 않는다** — 간식은 시간이 아니라 성격(끼니 사이)이라 시각으로 추정할 대상이 아니다.

### D8. 서비스 하루 = 05:00 ~ 다음날 05:00

`eatenAt`은 **실제 시각 그대로 저장**하고(변경 없음), **조회·집계 경계만** 옮긴다. `ServiceDay` 유틸 하나로 통일해 호출부가 각자 계산하지 않게 한다.

```java
ServiceDay.of(LocalDate, ZoneId)   // [date 05:00, date+1 05:00)
ServiceDay.today(Clock)            // now.minusHours(5).toLocalDate()
```

| 적용 | 이유 |
|---|---|
| 식사 날짜별 조회(`DayRange`) · 홈 대시보드 · 리포트 집계(`MealDailyIntake`) · TDEE 실제 섭취 · 코칭 시그널 | **부분 적용하면 숫자가 어긋난다.** 새벽 2시 기록이 음식기록 탭에서는 어제, 홈에서는 오늘로 잡히면 사용자가 설명할 수 없다 |
| 제외: 체중 기록 | 체중은 아침 공복 측정이고 추세·목표 계산이 전부 달력 날짜 기준이다. 새벽 4시 측정치를 전날로 넣으면 오히려 어긋난다 |
| 제외: 일일 분석 횟수 제한 | 비용 통제 장치이고, 카운터 키(`analysis_usage.usage_date`)를 옮기면 기존 데이터와 어긋난다. 얻는 것이 없다 |

미배포 상태라 과거 데이터 보정은 하지 않는다.

### D9. 분석 API는 통로 하나 (V16)

`POST /api/analyses`가 **사진(선택) · 설명(선택)** 을 받고 **최소 하나**를 요구한다. `analysis_job.image_key`를 nullable로 바꾸고 `note`를 추가한다.

- 텍스트 전용도 **같은 비동기 작업·폴링**을 탄다. 별도 동기 엔드포인트를 두지 않는 이유: 결과를 받는 쪽(프론트 `pollAnalysis`·결과 화면·실패 폴백·확인 저장)이 하나로 유지되고, 재시작 복구·미확인 정리가 그대로 따라온다. 동기 방식은 느린 LLM 호출 동안 HTTP 요청이 매달리고 재시작 시 유실된다.
- 대가: 텍스트 분석도 폴링 왕복이 생긴다. **첫 폴링을 지연 없이 즉시** 수행해 완화한다.
- 프롬프트는 사진 유무로 분기한다. 사진이 없으면 `image_url` 파트를 빼고 위치 박스(`box`)를 스키마에서 제외한다.
- **일일 횟수는 사진·텍스트가 같은 카운터를 공유**한다. 텍스트가 더 싸지만 카운터를 둘로 나누면 스펙·UI가 복잡해진다. 필요하면 상한값(설정)을 올린다.

### D10. 재분석은 기존 작업을 갱신, 작업당 2회

`analysis_job.reanalysis_count`를 추가하고, 재분석 시 같은 행의 상태를 `ANALYZING`으로 되돌린 뒤 결과를 덮어쓴다. 사진은 재업로드하지 않고 기존 `image_key`를 재사용한다.

새 작업을 만들지 않는 이유: 사진 하나를 여러 작업이 공유하게 되면 **사진 삭제 시점 판단이 무너진다**(현재 미확인 정리·고아 삭제가 "작업 하나 = 사진 하나"를 전제한다). 이력 보존은 지금 아무도 쓰지 않는다.

- **각 회차가 일일 횟수를 차감한다** — 실제 LLM 호출이므로.
- **되돌리기는 제공하지 않는다.** 재분석이 실패하면 프론트가 들고 있던 직전 결과를 복원한다. 성공했는데 마음에 안 들면 항목을 직접 수정하면 된다.
- 사용자가 이미 수정한 항목이 있으면 **덮어쓰기 경고**를 띄운다("수정한 값이 사라집니다").
- 프롬프트 전용 분석도 재분석할 수 있다(같은 규칙).

### D11. AI 분석 응답에 항목별 양을 포함한다

응답 스키마의 항목에 `amount`(수량) · `unit`을 추가한다. 지금까지는 "양은 응답에 없으니 지어내지 않는다"는 원칙이었지만, AI는 이미 **양을 추정해서 칼로리를 내고 있다.** 양만 숨기면 사용자가 "150g이 아니라 100g이었어"로 고칠 방법이 없다.

- 대가: `eval/` 기대값과 프롬프트가 바뀐다. 양은 사진만으로 부정확하므로 **수정 가능한 추정치**로 제시한다(고정된 사실로 보이지 않게).
- 이득: 이미지 3의 "180g · 185kcal" 배지가 가능해지고, AI 결과를 즐겨찾기에 담을 때 1인분 환산이 성립한다(D5·D6).

### D12. 검색 = 통합 · 클라이언트 필터 · 3단 매칭

- 범위: **카탈로그 + 즐겨찾기 통합**. 사용자는 찾는 음식이 기본 목록에 있는지 자기가 저장한 것인지 모른다. 결과 카드에 ★로 출처를 구분한다.
- 방식: 전체를 한 번 받아 캐시(TanStack Query)하고 **클라이언트에서 필터**한다. 30개 + 즐겨찾기 수십 개 규모에서 글자마다 서버를 때릴 이유가 없다. 목록이 커지면 서버 검색으로 바꿔도 API 모양은 유지된다.
- 매칭 단계:
  1. **정규화** — `FoodNames.normalize`와 같은 규칙(공백 제거·소문자). 띄어쓰기 차이를 흡수한다.
  2. **이름·별칭 순위 매칭** — 정확 일치 → 앞부분 일치 → 부분 일치 → 별칭 정확 → 별칭 부분. 별칭(`aliases` 컬럼: "계란,에그" → 삶은달걀)은 자카드로는 원리상 못 잡는 동의어를 해결한다. 30개라 손으로 채울 수 있다.
  3. **음절 bigram 자카드 폴백**(임계 0.3) — 2단계 결과가 **하나도 없을 때만**. 오타("닥가슴살")를 잡되 무관한 음식을 끌어오지 않는다. 의존성 없는 순수 함수라 TDD 대상.
- 정렬: 위 순위 오름차순, 같은 순위끼리는 원래 목록 순서(즐겨찾기가 카탈로그보다 앞).
- **초성 검색은 넣지 않는다** — 자모 분해 코드와 테스트 경우의 수가 늘어나는데 30개 규모에서 이득이 작다.
- 결과가 없으면 **"'짜장라면' 직접 추가하기"** 버튼을 띄운다(검색어가 이름으로 들어간다).

### D13. 등록 경로 일원화 — `/meals/new` 폐기

FAB은 **음식기록 탭으로 이동하며 카메라를 즉시 연다.** 같은 일을 하는 문이 둘이면 "저장 후 어느 화면의 어느 끼니로 돌아가는가"가 매번 문제가 된다.

`MealRecordPage`는 삭제하되 구성 요소(`PhotoOverlay`·`AnalysisSummary`·`AnalyzedItemList`·`ItemEditSheet`·`pollAnalysis`·`imageResize`·`mealItems`)는 **AI 결과 시트로 그대로 재사용**한다. 결과 확인은 정보량이 많아 인라인이 아닌 **풀스크린급 시트**로 띄운다.

## Risks / Trade-offs

- **[PR2가 크다]** `RecordsPage` 전면 재작성 + 신규 컴포넌트 대여섯 개. 리뷰가 한 번에 안 끝날 수 있다 → 재사용 가능한 기존 컴포넌트를 최대한 그대로 쓰고(D13), 순수 로직(검색 매칭·수량 계산)을 테스트 가능한 함수로 분리해 리뷰 표면을 줄인다.
- **[05시 경계가 5개 도메인을 건드린다]** → `ServiceDay` 한 곳에 계산을 모으고 호출부는 그것만 쓰게 한다. 각 도메인의 통합 테스트로 경계 시각(04:59 / 05:00)을 검증한다.
- **[AI가 양을 지어낼 수 있다]** → 양은 수정 가능한 추정치로 제시하고, 신뢰도가 낮으면 기존 "확인 필요" 유도가 그대로 작동한다.
- **[카탈로그 영양값의 정확도]** → 30개는 손으로 검수한다. 값이 틀려도 서버 테이블이라 마이그레이션 한 줄로 고칠 수 있다(프론트 상수였다면 재배포).
- **[일일 횟수 공유로 텍스트 등록이 막힐 수 있다]** → 상한이 설정값이라 코드 수정 없이 올릴 수 있다. 카탈로그·즐겨찾기 등록은 애초에 AI를 타지 않으므로 대체 경로가 있다.
- **[수량 도입이 기존 기록과 섞인다]** → nullable이라 기존 기록은 수량 없이 그대로 보인다. 화면은 수량이 있을 때만 표시한다.

### D14. 개인 보정치에 기준 섭취량을 도입한다 (V17 — PR 리뷰 대응)

보정치는 **"그 섭취량 기준의 총량"** 으로 저장하고(`base_quantity`·`unit` 동반), 분석에 반영할 때 **단위가 같으면 비례 조정**한다.

배경: 처음 구현은 즐겨찾기 저장에서만 값을 수량으로 나눠(per-unit) 넣었는데, 소비 측(`applyOverride`)은 스케일 없이 총량을 대체하고 형제 경로(`MealService.rememberCorrections`)는 총량을 저장한다. 같은 테이블·같은 키를 공유하므로 **"닭가슴살 100g 165kcal"이 1.65kcal로 저장돼 이후 분석마다 2kcal로 대체**되는 버그가 있었다.

- **저장**: 두 경로(식사 "기억하기" · 즐겨찾기 "AI에도 반영") 모두 총량 + 기준 섭취량. 저장 경로에 따라 값의 뜻이 달라지지 않는다.
- **소비**: `PersonalCorrection.scaledTo(amount, unit)` — 단위가 같고 양이 양수일 때만 `저장값 × (분석량 / 기준량)`. 단위 비교는 `FoodNames.normalize`로 표기 차이를 흡수한다.
- **조정 불가 시 저장값 그대로**: 단위 불일치("2개" 보정치 vs "50g" 분석), 기준 섭취량 없음(구 데이터·직접 입력), 양이 0 이하. **임의 환산 규칙을 만들지 않는다** — 잘못 환산한 값보다 사용자가 확정한 값이 예측 가능하다.
- **프롬프트 주입**도 기준을 함께 적는다("삶은달걀(2개 기준): 140kcal…").

대안이었던 "저장을 총량으로 통일하고 조정은 하지 않기"는 변경이 3줄로 끝나지만, "달걀 2개로 기억한 값이 1개짜리 사진에 그대로 붙는" 원래 한계가 남는다. 수량 개념을 이번 change에서 이미 도입했으므로(D3) 여기서 함께 푸는 편이 일관된다.

## 구현 이탈 (design 대비 — PR1)

- **카탈로그·즐겨찾기로 담기에 전용 엔드포인트를 두지 않았다.** 프론트가 선택 수량으로 영양값을 계산해 기존 `POST /api/meals`에 항목으로 보낸다. 전용 API(`{catalogId, quantity}`)를 두면 사용자가 시트에서 값을 미세 조정한 경우를 표현할 수 없고, 저장 경로가 둘로 갈린다.
- **`GET /api/foods`가 카탈로그와 즐겨찾기를 합쳐 내려준다** — 즐겨찾기가 앞(최근 갱신 순), 카탈로그가 뒤(정렬 순). 통합 검색(D12)이 한 목록만 필터하면 되도록.
- **끼니 추가에 마이그레이션이 없다.** `meal_type`이 `VARCHAR(20)`에 CHECK 제약이 없어 enum 값만 늘리면 된다(proposal에 마이그레이션으로 잘못 적었던 것을 정정).
- **코칭 채팅 일일 상한은 달력 날짜를 유지한다.** D8은 분석 횟수 제한만 제외 대상으로 적었지만, 코칭 채팅 상한도 같은 성격의 비용 통제 카운터라 함께 제외했다. 코칭 **브리핑**의 "오늘"은 섭취 기반이라 05시 경계를 따른다.
- **재분석 상한 초과는 400이다.** 429(횟수 초과)와 구분한다 — 일일 횟수와 무관하게 이 작업에서 더는 못 한다는 뜻이라 사용자가 다른 사진으로 다시 시도하면 된다.
- **`eval/` 기대값 갱신은 대상이 없었다.** 디렉터리에 `.gitkeep`만 있어 평가 세트가 아직 만들어지지 않았다.
- **AI 응답의 섭취량 필드 이름은 `amount`·`unit`이다**(저장 필드는 `quantity`·`unit`). 분석 결과의 추정치와 저장된 확정값을 이름으로 구분한다.

## 구현 이탈 (design 대비 — PR2 프론트)

- **프론트의 "오늘"도 05시 경계로 옮겼다**(`todayServiceDate`). tasks에 없던 항목인데, 서버만 바꾸면 새벽 2시에 홈·음식기록이 `8/12`를 조회하고 서버는 `8/12 05:00~` 구간을 돌려줘 **방금 담은 야식이 사라진다.** 체중은 달력 날짜라 `todayLocalDate`를 그대로 쓴다.
- **음식기록 탭에서 날짜 선택을 뺐다**(사용자 요청). 이 탭은 "오늘 담는 화면"이 되고, 지난 날짜는 홈에서 넘겨본다. D1의 "과거 날짜에도 담을 수 있다"는 경로는 코드(`eatenAtFor`)에 남아 있으나 화면에는 진입점이 없다.
- **과거 날짜에 담을 때 `eatenAt`은 그 날 정오**로 둔다. D1은 "그 날짜의 현재 시각"이라고 적었지만, 새벽 시각을 그대로 쓰면 05시 경계 때문에 하루 전으로 밀린다.
- **자주먹는 목록은 2열 그리드가 아니라 1열**이고 **이모지를 쓰지 않는다**(사용자 요청). ★이 즐겨찾기 토글을 겸한다.
- **끼니 기록은 카드 나열이 아니라 한 장의 표**로 쌓이고 합계가 그 표의 마지막 줄이다(사용자 요청) — 아래 "지금 추가하기"와 구분하기 위함.
- **사진 오버레이는 테두리 상자 대신 말풍선 배지**다. 값이 바로 읽히고 탭 대상이 커지며, 선택된 항목은 사진·목록 양쪽에서 함께 강조된다.
- **분석 대기 화면에 스캔 애니메이션과 결과 자리 스켈레톤**을 넣었다(`AnalyzingView`). `prefers-reduced-motion`이면 움직임을 멈춘다.
- **디자인 토큰 2개 추가**: `--color-track`(페이지 배경 위에 얹는 눌린 면 — 테두리만으로는 구분되지 않는 곳), `--radius-tile`(작은 조각용 12px). 라운드는 card(24)/2xl(16)/tile(12)/full 네 종류로 정리했다.
- **프로필 화면 개편을 이 PR에 포함**했다(사용자 요청). change 범위 밖이지만 같은 UI 정리 흐름이라 함께 진행했다 — 요약 카드·체중 진행·영양 목표·주간 요약으로 재구성하고, 기존 편집 폼은 시트로 옮겼다. 서버 변경은 없다(기존 API 조합).
- **탭바·기록 카드의 식기 아이콘이 잘려 있던 것을 고쳤다** — 나이프 path가 닫히지 않아 오른쪽 변이 없었다. 공용 `UtensilsIcon`으로 합쳤다.
