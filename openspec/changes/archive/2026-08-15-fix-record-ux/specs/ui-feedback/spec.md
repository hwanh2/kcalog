# ui-feedback (delta)

## ADDED Requirements

### Requirement: 되돌릴 수 없는 동작은 확인을 받는다

데이터가 사라지고 되돌릴 수 없는 동작은 **실행 전에 확인을 받아야 한다**(MUST). 확인은 무엇이 사라지는지 알 수 있어야 하며(MUST), 기본 선택은 **취소 쪽**이어야 한다(MUST) — 습관적으로 한 번 더 누르는 것으로 데이터가 지워져서는 안 된다.

확인 창은 **앱이 그리는 화면이어야 한다**(SHALL). 브라우저 기본 `confirm`은 PWA로 설치했을 때 출처 문구가 그대로 노출되고 앱 디자인과 어긋난다.

되돌릴 수 없는 동작의 실행 버튼은 **탭 대상 44px 이상**이어야 하며(MUST), 인접한 다른 동작과 오조작이 일어나지 않게 떨어져 있어야 한다(SHALL).

#### Scenario: 기록 삭제 확인
- **WHEN** 회원이 기록의 삭제를 누르면
- **THEN** 무엇을 지우는지 보여주는 확인 화면이 뜨고, 확인하기 전에는 삭제되지 않는다

#### Scenario: 확인 취소
- **WHEN** 회원이 확인 화면에서 취소하거나 Esc를 누르면
- **THEN** 아무것도 삭제되지 않고 원래 화면으로 돌아간다

### Requirement: 실패는 빠짐없이 알린다

서버 요청이 실패하면 화면은 **반드시 그 사실을 사용자에게 알려야 한다**(MUST). 조용히 지나가서는 안 된다(MUST NOT) — 사용자가 저장됐다고 믿게 만드는 것이 실패 자체보다 나쁘다.

안내는 `role="alert"`로 즉시 읽히고 오류 색으로 표시해야 하며(MUST), **무엇이 실패했는지와 다음에 무엇을 할 수 있는지**를 담아야 한다(MUST).

#### Scenario: 즐겨찾기 해제 실패
- **WHEN** 회원이 ★을 눌러 즐겨찾기를 뺐는데 요청이 실패하면
- **THEN** 실패했다는 안내가 오류로 표시되고, 목록의 ★ 상태는 실제 저장 상태와 어긋나지 않는다

#### Scenario: 기록 삭제 실패
- **WHEN** 삭제를 확인했는데 요청이 실패하면
- **THEN** 실패 안내가 뜨고 기록은 목록에 그대로 남는다

#### Scenario: 프로필·체중 저장 실패
- **WHEN** 프로필이나 체중 저장이 실패하면
- **THEN** 입력한 값은 화면에 남아 있고 실패 안내가 뜬다

### Requirement: 성공은 조용히 알린다

동작의 결과가 **화면 상태로 이미 드러나는 경우**, 별도의 성공 문구를 띄우지 않아야 한다(MUST NOT). ★이 채워지고 비워지는 것, 목록에 줄이 하나 늘어나는 것 자체가 결과다.

문구를 띄워야 하는 경우에는 **일정 시간 뒤 자동으로 사라져야 한다**(MUST). 화면에 남아 다음 동작의 결과처럼 읽히면 안 된다.

#### Scenario: 즐겨찾기 저장·해제
- **WHEN** 회원이 음식을 즐겨찾기에 넣거나 빼면
- **THEN** ★ 표시만 바뀌고 별도의 안내 문구는 뜨지 않는다

### Requirement: 저장 실패 시 입력한 내용을 지킨다

기록 저장이 실패하면 사용자가 담은 항목을 **버려서는 안 된다**(MUST NOT). 같은 내용을 한 번의 조작으로 다시 보낼 수 있어야 한다(MUST).

AI 분석으로 담은 항목은 분석 결과와의 연결(`analysisJobId`)까지 유지해야 한다(MUST) — 다시 분석하면 일일 횟수를 또 쓰게 된다.

#### Scenario: 담기 실패 후 재시도
- **WHEN** 음식을 담았는데 저장이 실패하고 회원이 "다시 시도"를 누르면
- **THEN** 직전과 같은 항목·끼니로 다시 저장을 시도한다

#### Scenario: AI 분석 결과 저장 실패
- **WHEN** 분석 결과를 저장하다 실패하면
- **THEN** 재시도해도 분석 횟수가 추가로 차감되지 않는다

### Requirement: 목록 로딩은 들어설 자리를 보여준다

목록을 불러오는 동안 **자리를 차지하는 표시**를 보여야 한다(MUST). 텍스트 한 줄만 두어 빈 화면이 갑자기 채워지게 해서는 안 된다(MUST NOT).

#### Scenario: 기록·음식 목록 로딩
- **WHEN** 끼니 기록이나 음식 목록을 불러오는 중이면
- **THEN** 실제 목록과 비슷한 높이의 자리표시가 보이고, 로드가 끝나도 화면이 크게 튀지 않는다

### Requirement: 누를 수 있는 것은 눌러 보인다

탭하면 동작하는 영역은 **눌릴 수 있음이 시각적으로 드러나야 한다**(MUST). 넓은 영역이 통째로 버튼인데 아무 단서가 없으면 사용자는 그 기능을 찾지 못한다.

#### Scenario: 기록 카드에서 수정 진입
- **WHEN** 회원이 기록 목록을 보면
- **THEN** 각 기록을 눌러 고칠 수 있다는 것이 드러난다

### Requirement: 사진은 로드 전에 자리를 잡는다

크기를 아는 이미지는 **로드 전부터 자리를 차지해야 한다**(MUST). 이미지가 뜨면서 아래 내용이 밀려 내려가면(레이아웃 이동), 누르려던 버튼이 움직여 오조작이 생긴다.

#### Scenario: 분석 결과의 사진
- **WHEN** 분석 결과 시트가 열리고 사진이 로드되면
- **THEN** 사진 아래 항목과 버튼의 위치가 움직이지 않는다

### Requirement: 비교되는 숫자는 자릿수로 정렬한다

세로로 쌓여 서로 비교되는 숫자(칼로리·매크로 등)는 **고정폭 숫자**로 표시해야 한다(MUST).

#### Scenario: 기록 목록의 칼로리
- **WHEN** 여러 기록의 칼로리가 세로로 나열되면
- **THEN** 자릿수가 세로로 맞아 크기를 눈으로 비교할 수 있다
