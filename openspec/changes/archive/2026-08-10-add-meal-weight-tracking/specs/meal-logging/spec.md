# meal-logging

## ADDED Requirements

### Requirement: 사진 기반 식사 분석 (저장 없음)
시스템은 이미지와 끼니 구분을 받아 AI(GPT-5.4 mini 계열)로 총 칼로리·탄수화물·단백질·지방을 추정해 반환해야 한다(SHALL). 분석 시점에는 어떤 데이터도 저장하지 않아야 하며(MUST NOT), 사진은 분석 입력으로만 사용하고 응답 후 폐기해야 한다(MUST). 응답은 구조화된 JSON(총 kcal, 탄·단·지 g, 신뢰도, 비고)이어야 한다(MUST).

#### Scenario: 정상 분석
- **WHEN** 로그인한 회원이 음식 사진과 끼니 구분으로 `POST /api/meals/analyze`를 호출하면
- **THEN** 총 칼로리·탄단지 추정값과 신뢰도를 담은 JSON을 반환하고, DB에는 아무것도 저장하지 않는다

#### Scenario: 음식이 아닌 사진
- **WHEN** 음식이 식별되지 않는 사진을 분석하면
- **THEN** 빈 결과 신호와 안내(비고)를 반환하고 오류로 처리하지 않는다

#### Scenario: 분석 실패 폴백
- **WHEN** AI 호출이 타임아웃되거나 응답 파싱이 실패하면
- **THEN** 1회 재시도 후에도 실패하면 실패를 응답해 프론트가 수동 입력으로 폴백할 수 있게 한다

### Requirement: 일일 분석 횟수 제한
시스템은 회원당 하루 분석(analyze) 호출 횟수를 설정된 상한으로 제한해야 한다(SHALL). 상한을 초과하면 분석을 수행하지 않고 429와 안내를 반환해야 한다(MUST).

#### Scenario: 상한 초과
- **WHEN** 회원이 당일 분석 상한을 초과해 `POST /api/meals/analyze`를 호출하면
- **THEN** 429와 "오늘 분석 가능 횟수를 초과했어요" 안내를 반환하고 AI를 호출하지 않는다

### Requirement: 식사 기록 저장
시스템은 확인·수정된 영양값(총 kcal, 탄·단·지)과 끼니 구분·섭취 시각·출처(AI/MANUAL)를 받아 식사 기록을 저장해야 한다(SHALL). 사진 없이 숫자만으로도 저장할 수 있어야 한다(MUST). 영양값은 음수가 아니어야 하며 허용 범위를 검증해야 한다(MUST).

#### Scenario: AI 결과 확인 후 저장
- **WHEN** 회원이 분석 결과를 확인·수정해 `POST /api/meals`로 제출하면
- **THEN** 해당 회원의 식사 기록이 source=AI로 저장되고 저장된 기록을 반환한다

#### Scenario: 수동 입력 저장
- **WHEN** 회원이 사진 없이 영양값을 직접 입력해 제출하면
- **THEN** source=MANUAL로 저장된다

#### Scenario: 범위 밖 입력
- **WHEN** 영양값이 음수이거나 허용 범위를 벗어나면
- **THEN** 400과 항목별 오류를 반환하고 저장하지 않는다

### Requirement: 식사 기록 조회·수정·삭제
시스템은 회원이 자신의 식사 기록을 날짜별로 조회하고, 개별 기록을 수정·삭제할 수 있게 해야 한다(SHALL). 다른 회원의 기록에는 접근할 수 없어야 한다(MUST).

#### Scenario: 날짜별 조회
- **WHEN** 회원이 `GET /api/meals?date=YYYY-MM-DD`를 호출하면
- **THEN** 해당 날짜 자신의 식사 기록 목록을 섭취 시각 순으로 반환한다

#### Scenario: 기록 수정
- **WHEN** 회원이 자신의 기록에 대해 영양값·끼니 구분을 수정하면
- **THEN** 변경된 기록이 저장되고 반환된다

#### Scenario: 타인 기록 접근 차단
- **WHEN** 회원이 다른 회원의 기록을 조회·수정·삭제하려 하면
- **THEN** 접근이 거부된다(404)

#### Scenario: 기록 삭제
- **WHEN** 회원이 자신의 기록을 삭제하면
- **THEN** 해당 기록이 제거된다
