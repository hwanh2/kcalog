## Context

kcalog 프론트는 Vite + React 19 SPA다. 웹은 Vercel(`kcalog.site`), API는 `api.kcalog.site`에 있다. 인증은 카카오 OAuth이고, access 토큰은 메모리(`api/client.ts`)에, refresh 토큰은 HttpOnly 쿠키(`SameSite=Lax`, path `/api/auth`)에 둔다. 다크모드는 원래 없다(`color-scheme: light`).

앱인토스(SDK 3.x, 2026-10 기준 3.7.0)에서 이 구조와 부딪히는 사실은 다음과 같다. 근거는 앱인토스 개발자센터 문서다.

- iOS 13.4 이상 WebView는 서드파티 쿠키를 막는다. 문서는 토큰 방식을 쓰라고 한다.
- 미니앱 origin은 `https://<appName>.apps.tossmini.com`(라이브), `https://<appName>.private-apps.tossmini.com`(QR 테스트)이다. SDK 3.1.1 이상 기준이다.
- 토스 공통 내비바가 항상 위에 붙는다. 자체 로고를 넣으면 안 되고, 토스 뒤로가기와 자체 뒤로가기가 동시에 보이면 안 된다. 첫 화면에서 뒤로가기를 누르면 미니앱이 닫혀야 한다.
- 하단 탭이 필요하면 토스 UX 가이드의 플로팅 탭바 형태(탭 2~5개)를 따라야 한다.
- 비게임 미니앱은 `User.createAnonymousKeyAuthCode()`(SDK 3.6.0 이상)로 1회용 코드(300초)를 받을 수 있다. 서버는 이 코드를 `POST /api-partner/v1/apps-in-toss/users/anon-key/exchange`(mTLS)에서 익명 키로 바꾼다. 익명 키는 미니앱마다 고유하고, 앱을 지우거나 기기를 바꿔도 같다.
- 3.x는 샌드박스 앱을 지원하지 않는다. 실기기 확인은 콘솔에 번들을 올린 뒤 QR로 한다. 로컬 브라우저에서는 AIT Devtools를 쓴다.

## Goals / Non-Goals

**Goals:**
- 같은 저장소, 같은 백엔드로 토스 미니앱 출시
- 웹 빌드의 동작은 그대로 유지
- 사업자 등록 없이 출시할 수 있는 회원 식별

**Non-Goals:**
- 토스 로그인(이름, 전화번호 수집). 사업자 등록 후 필요해지면 별도 change로 한다.
- 카카오 회원과 토스 회원의 계정 연동
- 인앱결제, 토스페이, 인앱광고
- 토스 번들 배포 CI. 이번에는 수동 `ait deploy`로 한다.
- TDS(토스 디자인 시스템) 도입. 기존 디자인 토큰을 유지하고 앱인토스 출시 기준에 걸리는 부분만 바꾼다.

## Decisions

### D1. 빌드 타임 분기 (Vite mode `toss`)

토스 빌드는 `vite build --mode toss`로 만든다. `.env.toss`에 `VITE_PLATFORM=toss`와 `VITE_API_BASE_URL=https://api.kcalog.site`를 둔다. 코드는 `IS_TOSS` 상수 하나로 분기한다. 토스 모드에서는 `VitePWA` 플러그인을 넣지 않는다.

런타임 판별을 고르지 않은 이유: 앱인토스에는 "일반 브라우저인지" 알려 주는 공식 API가 없다. `Environment.environment`는 `'toss' | 'sandbox'`만 돌려주고, SDK 밖에서는 에러를 던진다. UA 문자열은 문서에 없다. 빌드 타임 상수로 나누면 웹 번들에서 SDK 코드가 트리 셰이킹으로 빠지는 이점도 있다.

### D2. 플랫폼 모듈로 SDK를 가둔다

SDK import는 `src/platform/toss.ts` 한 파일에만 둔다. 이 파일이 앱이 쓰는 SDK 기능을 얇게 감싼다(`createAuthCode`, `pickPhoto`, `requestPhotoPermission`, `subscribeBack`, `closeApp`). 화면 코드는 `platform/index.ts`의 `IS_TOSS`로 분기하고, SDK가 필요하면 `loadToss()`로 이 파일을 동적 import한다. 그래야 기존 테스트(jsdom)가 SDK 없이 돈다. 토스 경로 테스트는 `vi.mock('../platform')`으로 `IS_TOSS`를 참으로 바꿔 끼운다.

처음에는 웹 구현과 토스 구현이 같은 인터페이스를 갖는 구조를 생각했다. 구현해 보니 웹 쪽은 대부분 "아무것도 안 한다"(뒤로가기, 앱 닫기)거나 이미 있는 코드(파일 입력, refresh 쿠키)라서 인터페이스가 빈 구현만 늘렸다. 분기 지점이 다섯 군데 정도라 `IS_TOSS` 분기가 더 읽기 쉽다.

⚠️ `loadToss`의 삼항은 `platform/index.ts` 안에 있어야 한다. 상수 접기가 모듈 경계를 넘지 못해서, 호출하는 쪽에서만 `IS_TOSS`로 막았더니 웹 빌드에도 SDK 청크(약 58KB)가 만들어지고 PWA 프리캐시에 실렸다. 같은 모듈 안에서 접히게 옮긴 뒤 사라진 것을 빌드로 확인했다.

### D3. 회원 식별은 익명 키, 클라이언트 해시는 믿지 않는다

`User.getAnonymousKey()`가 주는 해시를 그대로 서버에 보내면 누구든 다른 사람의 해시를 보내 그 계정으로 들어갈 수 있다. 그래서 프론트는 1회용 코드(`createAnonymousKeyAuthCode`)만 보내고, 서버가 앱인토스 API에서 직접 익명 키를 받는다.

토스 로그인 대신 익명 키를 고른 이유(2026-10-10 사용자 결정):
- 토스 로그인은 사업자 등록이 필수다. 익명 키는 사업자 필요 기능 목록에 없다.
- kcalog는 개인정보가 필요 없다. 동의 화면이 없으니 첫 진입도 빠르다.
- 토스 로그인 심사 항목(약관 URL, 연결 끊기 콜백, 연결 끊을 때 데이터 삭제)이 붙지 않는다.

대가로 토스 회원은 가입할 때 닉네임이 없다. 처음 구현에서 이걸 빠뜨려 홈에 "좋은 저녁이에요, 님", 프로필 카드에 빈 이름이 나왔다. 그래서 온보딩에서 기본 닉네임을 붙인다(D14). 온보딩 전처럼 닉네임이 없는 순간에는 홈은 인사만, 프로필 카드는 "칼로그 회원"으로 보여 준다.

### D4. 토스 빌드는 refresh 토큰을 쓰지 않는다

access 토큰이 만료되면 새 1회용 코드로 `POST /api/auth/toss`를 다시 부른다. 사용자 눈에는 아무것도 안 보인다.

| 선택지 | 문제 |
| --- | --- |
| 지금처럼 refresh 쿠키 | iOS WebView에서 서드파티 쿠키가 막힌다 |
| refresh 토큰을 본문으로 주고 localStorage에 저장 | XSS에 노출되고, WebView의 저장소 유지 기간이 문서에 없다 |
| **익명 키 재로그인** | 저장할 비밀이 없다. 코드는 언제든 조용히 다시 받을 수 있다 |

대가는 access 토큰 수명(30분)마다 앱인토스 API를 한 번 부르는 것이다. 앱인토스 파트너 API 한도는 앱당 분당 3,000건이라 지금 규모에서는 문제없다.

`api/client.ts`의 refresh 단일화 로직(동시 401을 한 번으로 합침)은 그대로 쓰고, 갱신 함수만 플랫폼별로 바꾼다. 웹은 `/api/auth/refresh`, 토스는 새 인가 코드로 `/api/auth/toss`를 부른다. 인가 코드도 1회용이라 단일화가 그대로 필요하다.

갱신이 끝내 실패했을 때도 갈린다. 웹은 `/login`으로 보내고, 토스는 `onSessionLost` 리스너로 AuthProvider에 알려 다시 시도 화면(`SessionRetryScreen`)을 띄운다. 토스 빌드에는 로그인 화면이 없기 때문이다. 이 처리를 `handleSessionLost()` 하나로 모아, 직접 401을 다루던 멀티파트 업로드(`analysis.ts`)와 스트리밍(`coach.ts`)도 같은 길을 타게 했다.

### D5. 백엔드: mTLS 클라이언트와 엔드포인트

- `AppsInTossClient`는 `RestClient`에 클라이언트 인증서로 만든 `SSLContext`를 붙인다. 설정은 `app.apps-in-toss.{base-url, certificate, private-key, timeout}`이고, 값은 환경 변수로 주입한다.
- 인증서는 PKCS12 키스토어가 아니라 PEM으로 받는다. 앱인토스 문서가 "인증서와 키 파일"이라고만 해서 PEM 두 개로 받을 가능성이 높고, Spring Boot의 `PemSslStoreDetails`가 PEM 내용과 `file:` 위치를 둘 다 받아 변환 단계가 필요 없다. 실제 발급 형식이 다르면 이 부분을 고친다.
- 인증서가 설정되지 않은 환경(로컬, 테스트)에서는 꺼진 클라이언트를 등록한다. 이때 엔드포인트는 503을 돌려준다. 카카오 키가 없을 때 로컬이 계속 동작하는 것과 같은 방침이다.
- 앱인토스 응답 봉투는 비즈니스 오류도 HTTP 200에 `resultType: FAIL`로 준다. 오류 코드 `4011`(코드 무효)만 401로 보내고, 한도 초과(`4095`), 네트워크 오류, 5xx는 503으로 보낸다. 4011은 프론트가 새 코드로 다시 시도하면 되고, 나머지는 기다려야 하는 문제라 나눈다.
- `TossAuthService.login`에는 트랜잭션을 걸지 않는다. 외부 API를 기다리는 동안 DB 커넥션을 잡지 않기 위해서다. 같은 사용자의 첫 로그인이 동시에 오면 유니크 제약 위반이 나는데, 이때는 먼저 만든 회원을 다시 조회해 쓴다.
- `TossAuthService`는 익명 키로 `findByProviderAndProviderId(TOSS, key)`를 하고, 없으면 `Member.signUp(TOSS, key, null, null)`으로 만든다. 이메일과 닉네임은 원래 선택 값이다.
- `POST /api/auth/toss`는 `/api/auth/**` permitAll 아래에 들어가므로 SecurityConfig는 바뀌지 않는다.
- `Provider` enum에 `TOSS`를 더한다. 컬럼이 `VARCHAR(20)` 문자열이고 유니크 제약이 `(provider, provider_id)`라 마이그레이션은 필요 없다.

### D6. 뒤로가기 처리 순서

토스 SDK의 `backEvent` 리스너를 등록하면 기본 뒤로가기가 막힌다. 그래서 앱이 직접 처리한다(`shell/backNavigation.ts`, `shell/TossBackBridge.tsx`).

1. 열린 시트가 있으면 맨 위 것을 닫는다. `useDialog`가 이미 열린 다이얼로그 스택을 관리하므로, 거기에 닫기 함수를 함께 기록하고 `closeTopDialog()`로 꺼낸다. Esc와 같은 동작이다.
2. 화면이 `useBackHandler`로 등록한 처리(온보딩 단계 되돌리기)를 최근 것부터 부른다. true를 돌려주면 끝낸다.
3. 라우터 히스토리에 이전 화면이 있으면 `navigate(-1)` 한다.
4. 없으면 `Screen.close()`로 미니앱을 닫는다.

시트를 먼저 닫는 이유: 시트가 열린 채 화면을 옮기면 사용자는 시트를 닫으려고 누른 뒤로가기에 화면을 잃는다.

"이전 화면이 있는지"는 react-router가 `history.state`에 남기는 `idx`로 판별한다. 처음 설계한 `location.key === 'default'`는 쓸 수 없었다. 진입하자마자 `/`에서 `/app`으로(또는 온보딩으로) replace하면 key가 바뀌어 첫 화면을 알아보지 못한다. `idx`는 replace해도 0으로 남는다.

온보딩 `WizardShell`은 토스 빌드에서 자체 뒤로가기 버튼과 첫 단계의 로고를 숨기고, 단계 되돌리기를 핸들러로 등록한다.

### D7. 헤더와 탭바

- 앱 헤더: 토스 빌드에서는 그리지 않는다. 로고와 앱 이름은 토스 내비바가 등록값으로 보여 주고, 프로필 진입은 내비바 기능 버튼(`initialAccessoryButton`, 아이콘 `icon-user-mono`)이 맡는다. 버튼을 누르면 SDK `tdsEvent`의 `navigationAccessoryEvent`가 오고 `TossNavigationBridge`가 프로필로 보낸다. 음식기록 날짜 머리의 프로필 링크도 같은 이유로 토스 빌드에서 숨긴다.
  - 처음에는 헤더에서 로고만 빼고 프로필 아이콘을 남겼다. 실제 미니앱 화면을 보니 내비바 바로 아래에 아이콘 하나뿐인 줄이 한 줄 더 생겨 본문이 그만큼 밀렸다(2026-10-10 사용자 결정으로 변경).
  - 기능 버튼 아이콘은 토스 아이콘 세트 이름만 받는다. 이름은 `static.toss.im/icons/png/4x/<이름>.png`가 열리는지로 확인했다.
- 탭바: 탭 구성과 경로는 그대로 두고 모양만 바꾼다. UX 가이드 그림은 화면 양옆과 아래에서 띄운 흰 알약에 그림자, 아이콘 아래 라벨이다. 그대로 `rounded-full`, `shadow-lg`, 양옆 1rem, 아래 0.75rem(+안전 영역)으로 띄웠다. 알약 높이가 기존 내비와 비슷해서 코치 FAB 위치와 본문 아래 여백은 바꾸지 않았다.
  - 처음에는 토스 빌드에만 적용했다. 두 빌드의 모양이 갈리는 것보다 하나로 두는 편이 낫다고 보고 웹도 같은 모양으로 바꿨다(2026-10-10 사용자 결정). DESIGN.md의 하단 내비 규칙도 함께 고쳤다.
- 안전 영역: 처음에는 상단을 SDK `SafeArea` 값으로 처리하려 했다. 비게임 미니앱은 토스 내비바가 WebView 위에 따로 있어 본문이 상태바와 겹치지 않을 것으로 보고 코드를 넣지 않았다. 실기기 테스트(tasks 5.4)에서 겹치면 그때 넣는다. 하단은 기존 `env(safe-area-inset-bottom)` 처리를 유지한다.

### D8. 사진은 SDK API로

`<input type="file" capture>`가 토스 WebView에서 동작하는지 문서에 없다. SDK의 `Device.openCamera` / `Device.getPhotos({ maxCount: 1 })`는 권한 처리(거부 에러, 다시 요청 다이얼로그)까지 문서화되어 있어 이쪽을 쓴다. 결과를 Blob으로 바꿔 기존 업로드 경로(`resizeImage` 후 `createAnalysis`)에 넘긴다. 분석 요청 형식은 바뀌지 않는다.

`base64: true`로 받는다. 기본값(false)일 때 `dataUri`가 어떤 형식인지 문서에 없어서, 형식이 확실한 base64를 직접 디코딩한다. SDK가 촬영과 앨범을 따로 여므로 "촬영"과 "앨범" 두 버튼을 둔다.

웹도 같은 두 버튼으로 통일했다(`PhotoPicker`, 2026-10-10 사용자 결정). 웹의 촬영은 `capture` 입력, 앨범은 `capture` 없는 입력을 연다. 예전 웹은 카드 전체가 하나의 파일 입력이라 OS가 "촬영/사진 보관함"을 묻는 한 단계가 있었는데, 버튼이 나뉘면서 그 단계가 사라졌다. 홈 촬영 카드로 들어오면 카메라를 바로 여는 동작(design D13)은 두 빌드 모두 유지한다.

`apps-in-toss.config.ts`의 `permissions`에 `camera`(access)와 `photos`(read)를 선언한다. 이 선언은 심사에도 쓰인다.

### D9. 생성형 AI 고지

앱인토스 서비스 오픈 정책(2-4)은 생성형 AI 기능을 처음 쓰는 시점에 AI 사용 사실을 알리고, 결과물에 라벨이나 배지로 표시하라고 한다.

- 사진 분석: 분석 버튼 위에 고지 문장, 분석 결과 시트 제목 옆에 "AI 추정" 배지
- AI PT: 화면 위에 고지 문장. 의료 관련 서비스 제한이 있어 "진단이나 처방을 대신하지 않는다"를 함께 적는다

처음에는 "처음 한 번만" 보여 주고 본 기록을 localStorage에 두려 했다. 늘 보이게 바꿨다. 문장이 한 줄이라 방해가 적고, 기록이 사라지거나 저장소가 막힌 WebView에서도 고지가 빠질 일이 없다. 늘 보이면 "처음 쓸 때"도 당연히 포함된다.

웹에도 똑같이 그린다. 처음에는 토스 빌드에만 넣었는데, 정책이 고지 의무의 근거를 법령으로 들고, 같은 모델을 쓰는 자사 웹에도 같은 기준을 요구해서 통일했다(2026-10-10 사용자 결정).

### D10. WebView 설정

- `webView.pullToRefreshEnabled: false`: 앱에 자체 당겨서 새로고침(`usePullToRefresh`)이 있어 둘이 겹치면 안 된다.
- `webView.allowsBackForwardNavigationGestures: false`: iOS 스와이프 뒤로가기가 D6의 핸들러를 건너뛰지 않게 한다. 실기기에서 확인한다.
- 핀치 줌은 이미 `user-scalable=no`와 gesture 이벤트 차단으로 막혀 있다.

### D11. 코치 대화 안전장치

앱인토스 AI 채팅 기준(정책 점검 참고)을 맞추려고 코치 대화에 검사 단계를 넣었다. 같은 백엔드라 웹에도 함께 적용된다. 정책도 같은 모델을 쓰는 자사 웹에 같은 기준을 요구한다.

```
질문 ─▶ 검사(Moderation + 키워드) ─┬─ 걸림 ─▶ 고정 안전 응답 (모델 호출 없음)
                                   └─ 통과 ─▶ 모델 스트리밍 ─▶ 답 검사(Moderation만) ─┬─ 걸림 ─▶ 저장할 답을 고정 응답으로 교체
                                                                                    └─ 통과 ─▶ 그대로 저장
```

- 문맥 판정은 OpenAI Moderation(`omni-moderation-latest`)이다. 무료이고 이미 쓰는 OpenAI 키로 부른다. `ModerationClient`가 `openAiRestClient`를 함께 쓴다.
- 키워드(`CoachSafety`)는 Moderation이 놓치는 한국어 은어(먹토, 씹뱉)와 짧은 표현(죽고 싶어)을 잡는다. 띄어쓰기를 지우고 맞춘다. 목록이 넓으면 평범한 질문이 막혀서 좁게 뒀다. "굶"은 "아침 굶었어"처럼 흔해서 뺐고, 하루 이상 굶는 방법 같은 요청은 프롬프트 규칙이 거절한다. "토하"는 "토마토하고"에 걸려서 앞 글자가 '마'인 경우를 뺐다.
- 고정 응답은 셋이다. 자해 신호는 자살예방상담전화 109와 정신건강위기상담전화 1577-0199, 섭식 위험 행동은 1577-0199, 그 밖의 금지 내용은 식단 관련 질문으로 돌리는 거절.
- 답은 키워드로 판정하지 않는다. "설사약보다 식이섬유를 늘려 보세요"처럼 위험한 방법을 말리는 정상 답에도 같은 단어가 들어간다.
- 답 검사는 스트리밍이 끝난 뒤에야 할 수 있다. 걸리면 저장할 답을 바꾸고, 프론트는 done 뒤에 대화를 다시 불러오므로 화면도 바뀐다. 그 사이 원래 답이 잠깐 보이는 것은 스트리밍(첫 글자까지 기다리지 않는 것)을 유지하는 대가로 받아들였다. 전부 받은 뒤 검사하고 보내면 답이 짧아도 몇 초씩 빈 화면이 된다.
- 검사가 실패하면 대화를 멈춘다(fail-closed). 검사 없이 이어가지 않는다. 같은 OpenAI라 검사가 실패할 때는 대개 모델도 실패한다.
- 안전 응답으로 끝난 대화는 하루 대화 수에서 뺀다. 모델을 부르지 않았고, 힘든 이야기를 꺼낸 사람의 대화 기회를 줄일 이유가 없다.
- 프롬프트(`CoachingPrompt.PERSONA`)에 거절 규칙을 더했다. 극단적 절식, 구토나 약물, 복용량, 범위 밖 주제는 거절하고, "소설이나 교육 목적"이라는 우회도 같게 다룬다. 브리핑도 같은 페르소나를 쓴다.
- 안전 응답이 나가면 `memberId`, 단계(질문, 답), 판정만 로그에 남긴다. 대화 내용은 개인적인 고민일 수 있어 로그에 남기지 않는다. 내용은 DB의 대화 기록으로 본다.
- 문제가 생겼을 때 대화를 바로 막는 방법은 기존 설정으로 된다. `OPENAI_DAILY_COACH_CHAT_LIMIT=0`으로 재배포하면 모든 대화가 상한에 걸린다. 안내 문구가 "오늘 대화를 다 사용했어요"라 정확하지는 않지만, 긴급 차단 수단으로는 충분해 새 설정을 만들지 않았다.
- 앱인토스에 출시한 뒤 코치 모델이나 프롬프트를 바꾸려면 앱인토스에 배포 검토를 먼저 요청해야 한다. 코드가 아니라 운영 약속이다.

### D12. 회원 탈퇴

`DELETE /api/members/me`(`MemberWithdrawalService`). 처리방침에 "어떻게 지우는지"를 쓸 수단이 필요했고, 그전까지 앱에는 탈퇴가 없었다.

- 회원 행 하나를 지우면 DB 기록은 외래 키 CASCADE로 함께 지워진다. 테이블마다 지우는 코드를 두면 새 테이블이 생길 때 빠뜨린다. `food_correction`, `member_favorite_food`, `member_favorite_meal` 세 곳만 CASCADE가 없어서 `V24`로 걸었다. 통합 테스트가 `member_id`를 가진 모든 테이블을 세어 확인한다.
- 사진은 DB 밖(R2)이라 따로 지운다. 확정 식사 사진과 미확정 분석 사진의 key를 먼저 모으고, DB 삭제가 끝난 뒤 지운다. 순서를 거꾸로 하면 DB 삭제가 실패했을 때 기록은 남고 사진만 사라진다. 사진 삭제가 실패하면 로그만 남긴다. 회원은 이미 지워져 다시 시도할 곳이 없다.
- 메서드에 트랜잭션을 걸지 않는다. 사진 삭제가 DB 커밋 뒤에 와야 하기 때문이다. 회원 삭제는 리포지토리 트랜잭션 하나로 끝난다.
- 응답은 웹의 refresh 쿠키를 만료시킨다. DB의 refresh 토큰은 CASCADE로 지워지지만 브라우저의 쿠키는 서버가 지워 줘야 한다.
- 탈퇴 후 웹은 `/`로 새로 읽어 들여 남은 상태를 버린다. 토스는 미니앱을 닫는다. 그대로 두면 다음 요청이 익명 키로 다시 로그인해 빈 새 회원이 바로 생긴다.
- 프로필 맨 아래 작은 글씨로 두고, `ConfirmSheet`로 되돌릴 수 없다는 확인을 받는다.
- 하지 않은 것: 카카오 "연결 끊기" API 호출. 카카오 쪽에는 앱 연결이 남아, 다시 로그인하면 동의 화면 없이 새 회원으로 들어온다. 카카오 액세스 토큰을 보관하지 않아 어드민 키가 필요하다. 별도 change로 다룬다.
- DB 백업에는 최대 14일 남는다. 처리방침에 그대로 적었다.

### D13. 개인정보 처리방침

`/privacy` 공개 페이지(`PrivacyPage`). 앱인토스 등록에 필요할 가능성이 높고, 웹도 처리방침 없이 운영되고 있었다. 개인정보 보호법은 처리방침 공개를 요구한다.

- 내용은 실제 운영 구성에서 옮겼다. 사진과 백업은 Cloudflare R2(백업 14일), 서버는 AWS EC2 서울 리전(운영 API 주소의 IP를 AWS 공개 IP 대역과 대조해 확인), 서버 로그 30일, 웹 화면은 Vercel, 의견 알림은 Gmail SMTP, AI는 OpenAI. 보관 기간이나 업체를 바꾸면 이 페이지도 고쳐야 해서 컴포넌트 주석에 출처 설정을 적었다.
- OpenAI 국외 이전은 처리방침 공개로 알린다. 개인정보 보호법은 계약 이행에 필요한 국외 이전을 처리방침 공개로 갈음할 수 있게 하고, 사진 분석은 서비스의 핵심 기능이다.
- 개인정보 보호책임자는 "칼로그 운영자", 연락처는 운영자 계정 이메일로 적었다(2026-10-10 사용자 결정).
- 로그인 없이 열리고 토스 빌드에서도 열린다. 웹 전용 경로(`/`, `/login`)와 달리 토스 빌드에서 `/app`으로 돌리지 않는다.

### D14. 기본 닉네임과 닉네임 변경

온보딩을 마칠 때 목표에서 이름을 딴다(2026-10-11 사용자 결정). 감량 "익명의 다이어터", 유지 "익명의 유지어터", 증량 "익명의 증량러"에 무작위 네 자리 숫자를 붙인다(`DefaultNickname`). 증량 이름은 사용자가 정하지 않아 제안값이다.

- 웹과 토스가 같은 규칙을 쓴다. 카카오 닉네임도 덮어쓴다. 카카오 닉네임은 실명인 경우가 많고, 두 입구의 회원이 같은 모양으로 시작하는 편이 낫다. 이미 온보딩을 마친 기존 회원의 닉네임은 그대로 둔다(마이그레이션 없음).
- 숫자는 회원 id가 아니라 무작위다. id를 쓰면 가입자 수가 드러난다. 겹쳐도 된다. 닉네임은 부르는 이름일 뿐 식별자가 아니다.
- 온보딩 뒤에 목표를 바꿔도 닉네임은 그대로다. 사용자가 고친 이름을 덮어쓰지 않기 위해서다.
- 프로필 편집에 닉네임 칸을 더했다. 앞뒤 공백을 지우고, 비었거나 20자(`NICKNAME_MAX`)를 넘으면 거절한다. 20자는 홈 인사말과 프로필 카드 한 줄에 들어가는 길이다.

### D15. 앱인토스 UX 가이드 반영

출시 직전에 현재 게시된 UX 가이드를 다시 읽었다(2026-10-12). 기준을 지키지 않으면 "검수가 승인되지 않"는다고 적혀 있어 반영했다.

- 해요체: "제품 안의 모든 문구는 해요체"가 규칙이다. 튜토리얼, 입력 오류, 삭제 확인, 프로필 편집, 의견 보내기, 처리방침에 남아 있던 "~합니다"를 바꿨다. 입력 오류는 "~여야 합니다" 대신 "~사이로 입력해주세요"로 바꿨다. 코치 프롬프트에도 해요체 지시를 넣었다. 랜딩과 설치 안내는 웹 전용이라 두었다.
- 확인 시트 왼쪽 버튼: "취소"는 하던 작업이 취소된다고 읽힐 수 있어 가이드가 "닫기"로 통일하라고 한다. `ConfirmSheet`의 버튼 이름을 바꾸면 시트 오른쪽 위 X 버튼(이름이 "닫기")과 같은 이름이 둘이 된다. 확인 시트에서는 X를 빼도록 `Sheet`에 `closeButton` 옵션을 두었다.
- 브라우저 기본 확인창: 분석 결과를 고친 뒤 재분석할 때 `window.confirm`을 썼다. 토스 WebView와 설치한 PWA에서는 출처 주소가 찍힌 시스템 창이 뜬다. `ConfirmSheet`로 바꿨다.
- AI 결과물 표시: 정책은 결과물마다 라벨이나 배지를 요구한다. 사진 분석 결과(이미 있음) 외에 코치 답 말풍선, 브리핑 카드, 홈의 AI 코칭 카드에 배지를 붙였다. 숫자를 추정한 것은 "AI 추정", 글을 지어낸 것은 "AI 생성"으로 나눴다.
- 메일 링크: 토스 WebView에서 `mailto:`가 열리는지 문서에 없다. 토스 빌드에서만 SDK의 `Device.openURL`로 연다.
- 콘솔 로고: 600×600, 각진 정사각형, 배경 필수가 요건이다. 기존 512 아이콘이 흰 배경이 꽉 찬 정사각형이라 형태가 맞아, 600으로 고품질 리샘플링한 파일을 만들었다(저장소 밖 `docs/apps-in-toss/kcalog-logo-600.png`).
- 하지 않은 것: 코치 캐릭터(만화적 표현 지양 권고), 브리핑과 프로필의 그라데이션("과한 그라데이션" 지양), 온보딩 직후 튜토리얼 오버레이. 셋 다 권고 수준이거나 해당 여부가 모호해 심사 결과를 보고 판단한다.

## Risks / Trade-offs

- [mTLS 인증서 발급 형식이 PEM이 아닐 수 있음] → PKCS12로 오면 `AppsInTossConfig`에서 `JksSslStoreDetails`로 바꾼다. 설정 이름만 바뀐다.
- [사업자 없이 mTLS 인증서를 받을 수 있는지 모름] → 콘솔 가입 직후 가장 먼저 확인한다. 막히면 백엔드 작업은 스텁 테스트까지만 하고, 사업자 등록 후 붙인다. 프론트 작업은 영향이 없다.
- [익명 키 기반 계정은 토스 계정에 묶인다] → 토스 회원 탈퇴나 다른 토스 계정으로 바꾸면 기록에 다시 들어갈 방법이 없다. 개인정보를 받지 않는 대가로 받아들인다.
- [플로팅 탭바나 튜토리얼 오버레이가 심사에서 걸릴 수 있음] → 체크리스트의 "진입 즉시 바텀시트 금지"에 튜토리얼이 해당하는지 불분명하다. 반려되면 토스 빌드에서 튜토리얼 자동 표시를 끈다.
- [AI PT 채팅 정책] → 앱인토스 정책은 AI 채팅 서비스에 유해 응답 필터링, 자해 관련 안전 응답, 모델이나 프롬프트를 바꿀 때 사전 검토를 요구한다. 검토 요청 전에 코치 프롬프트와 응답 처리를 이 기준으로 점검한다(tasks). 기준을 맞추기 어려우면 토스 빌드에서 AI PT 탭을 빼는 것을 다시 논의한다.
- [의료 관련 서비스 제한] → 칼로리와 체중 안내 문구가 진단이나 처방으로 읽히지 않는지 점검한다.
- [SDK와 React 19 호환] → `@apps-in-toss/web-framework` 자체의 React 의존 여부를 설치 시 확인한다. TDS는 쓰지 않으므로 TDS의 `react@^18` 요구는 해당 없다.
- [재로그인마다 외부 API 호출] → 앱인토스 API 장애가 곧 토스 빌드 로그인 장애다. 503과 다시 시도 화면으로 드러나게 하고, 기존 관측(지표, 로그)에 호출 결과를 남긴다.

## Migration Plan

1. 백엔드 배포(`release`): `TOSS` provider와 `/api/auth/toss`가 추가되지만 인증서가 없으면 503만 돌려준다. 웹 사용자에게는 영향이 없다.
2. 운영 `.env`에 인증서와 CORS origin을 추가하고 재배포한다. PEM은 여러 줄이라 `.env`에 그대로 넣기 어렵다. VM에 파일로 두고 `file:` 위치를 넘기는 방식을 그때 정한다.
3. 토스 번들을 빌드해 콘솔에 올리고 QR로 실기기 테스트한다.
4. 체크리스트를 점검하고 검토를 요청한 뒤 출시한다.

되돌리기: 콘솔에서 이전 번들로 롤백하거나 출시를 내린다. 백엔드는 엔드포인트가 쓰이지 않을 뿐 그대로 둬도 된다.

## Open Questions

법률 전문가가 아닌 상태에서 정한 것들이다. 출시 전에 확인을 권한다.
- 체중, 식단이 개인정보 보호법의 "건강에 관한 정보"(민감정보)에 해당하는지. 해당하면 가입 때 별도 동의를 받아야 한다. 지금은 동의 화면이 없다.

- 개인정보 보호책임자를 실명이 아닌 "칼로그 운영자"로 적어도 되는지.

- 익명 키의 길이와 문자 형식. `provider_id`가 `VARCHAR(100)`이라 넘으면 마이그레이션이 필요하다. 첫 교환 응답에서 확인한다.
- 플로팅 탭바의 정확한 모양과 치수(UX 가이드 그림 확인).
- `appName`. 한 번 정하면 바꿀 수 없다. `kcalog`를 제안한다.

## 정책 점검 (tasks 4)

### AI PT 채팅과 앱인토스 AI 채팅 기준

앱인토스 서비스 오픈 정책의 "AI 채팅·상담" 필수 운영 요건과 현재 코치(`CoachingPrompt`)를 대조했다.

| 요건 | 현재 | 판정 |
| --- | --- | --- |
| 위험 키워드와 문맥을 함께 판단하는 필터링 | Moderation과 키워드로 질문을 검사 | 충족 (D11) |
| 금지, 부적절 요청에 명확하고 일관된 거절 | 고정 거절 응답과 프롬프트 거절 규칙 | 충족 (D11) |
| 자살, 자해 발화 시 안전 응답 프로토콜 | 모델을 부르지 않고 위기 상담 안내 | 충족 (D11) |
| 모델이나 프롬프트를 바꿀 때 사전 검토 요청 | 운영 절차 문제. 코드로 할 일은 없다 | 출시 후 지킬 일 |
| 문제 응답을 즉시 수정하거나 차단하는 체계 | 답 검사 후 교체, 상한 0으로 긴급 차단 | 충족 (D11) |
| 같은 모델을 쓰는 자사 웹에도 같은 기준 | 같은 백엔드라 웹에도 적용됨 | 충족 |
| 의학적 진단 단정 금지 | 프롬프트에 "의학적 진단·단정은 하지 않는다" 있음 | 충족 |

식단 앱이라 섭식 장애(극단적 절식, 구토 유도 등)가 자해와 맞닿는다. 안전 응답을 넣는다면 이 경우도 포함해야 한다.

처음 점검 때는 위 요건 대부분이 미충족이었다. 안전장치를 붙이고 AI PT까지 함께 출시하기로 했고(2026-10-10 사용자 결정), D11로 구현했다. 표는 구현 후 상태다.

### 의료 관련 서비스

정책이 금지하는 것은 비대면 진료 제공이나 연결, 병원 예약, 병원 광고 수익 구조다. kcalog에는 해당 기능이 없다. 화면 문구에서 진단, 처방, 치료 같은 단어를 검색했고 주석에만 나왔다.
