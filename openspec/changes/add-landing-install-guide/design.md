# Design: add-landing-install-guide

## Context

PWA 배선(`add-deployment` 4.3·4.4)은 끝나 있다 — manifest, 192/512/180 아이콘, `apple-mobile-web-app-capable`, `display: standalone`. 빠진 것은 **그것을 사용자에게 알리는 화면** 하나뿐이다.

참고 대상으로 같은 문제를 푼 다른 PWA(스톡잇, `~/Frontend`)를 읽었다. `start_url`을 `/pwa`로 두어 랜딩과 앱을 가른 구조, 설치 가능 여부에 따라 CTA 문구를 바꾸는 패턴, iPadOS를 `maxTouchPoints`로 구분하는 처리는 가져왔다. 반대로 그쪽에서 드러난 문제 — 설치 판정이 세 파일에 흩어져 한쪽에 standalone 검사가 빠진 것, iOS에서 Safari를 강제하는 낡은 안내 — 는 이 설계가 피해야 할 지점으로 삼았다.

경쟁 서비스의 랜딩도 함께 뜯었다(Cal AI, MacroFactor, 인아웃). 셋 다 **히어로에 실제 앱 화면이 있고**, 기능 설명 카드는 그 뒤에 온다. 신뢰는 숫자로 만든다 — "5M users ⭐4.9", 감량 사례, 1위 배지.

여기서 두 가지가 갈린다.

- **저들의 랜딩은 스토어 버튼에서 끝난다.** 우리는 스토어가 없고, 사용자가 한 번도 해본 적 없는 제스처를 배워야 한다. iOS는 버튼조차 없다. 그래서 **설치 안내 자체가 이 화면의 본체**다. PWA 설치 자료는 iOS 설치를 5단계 깔때기로 보고 "공유 버튼이 어디 있는지 안다고 가정하는 빈 페이지는 매 단계에서 설치를 흘린다"며 **화살표로 위치를 가리키라**고 권한다.
- **우리는 내세울 숫자가 없다.** 사용자가 0명이다. 없는 숫자를 만들 수 없으니 신뢰를 다른 것으로 채운다 — 실제 화면, 의심을 푸는 FAQ, 1인 개발이라는 사실을 숨기지 않는 것.

## Goals / Non-Goals

**Goals**
- 링크·검색·QR로 온 사람이 서비스를 이해하고 설치까지 가는 경로를 만든다
- 기기별로 **그 기기에서 실제로 되는 방법만** 보여준다
- 이미 설치한 사람에게는 설치 이야기를 하지 않는다
- 프론트 변경만으로 끝낸다 — 백엔드·인프라를 건드리지 않는다

**Non-Goals**
- 브라우저 접근 차단 (불가능하고, 데스크톱 사용과 디버깅을 막는다)
- 랜딩에서의 비로그인 체험 — 설치 유도 하나로 좁힌다
- 설치율 측정·실험

## Decisions

### 1. 앱을 `/app` 아래로 옮기고 `/`를 랜딩으로

`start_url`이 곧 분기점이 된다.

```
manifest start_url = /app

홈 화면 아이콘 탭   →  /app       →  앱
구글·카카오톡 링크  →  /          →  랜딩
```

브라우저가 설치된 앱을 `start_url`로 직접 열기 때문에, **"설치했으면 앱, 아니면 랜딩"이 자바스크립트 감지 없이 성립한다.** `display-mode: standalone`을 검사해 루트에서 분기하는 방법도 있지만, 그러면 랜딩과 앱이 같은 주소를 공유해 공유·북마크·검색 색인이 모두 애매해진다.

**대안 — 루트에서 분기(경로 유지):** 백엔드·manifest를 안 건드리고 기존 설치본도 그대로 동작한다. 변경 비용이 가장 작지만 주소가 하나라 SEO와 공유가 흐려진다. 지금은 사용자가 개발자 본인뿐이라 재설치 비용이 사실상 0이므로, 구조가 명확한 쪽을 택한다.

**대안 — 랜딩을 `/welcome`에:** 가장 싸지만 `kcalog.site`를 그냥 연 사람이 여전히 로그인 화면부터 만난다. 이 change의 목적 자체를 달성하지 못한다.

### 2. `/login`과 `/auth/callback`은 루트에 남긴다

백엔드가 이 두 경로를 하드코딩한다.

```java
// OAuth2SuccessHandler.java:34
sendRedirect(..., props.frontendBaseUrl() + "/auth/callback");
// SecurityConfig.java:48
response.sendRedirect(props.frontendBaseUrl() + "/login?error=oauth");
```

옮기면 백엔드 수정 → `release` 머지 → 재배포가 따라오고, 프론트와 백엔드 배포 순서가 어긋나는 순간 로그인이 깨진다. 프론트만으로 끝낼 수 있는 일을 양쪽 배포로 키울 이유가 없다.

`/auth/callback`은 그대로 두되 착지 경로만 `/app` 계열로 바꾼다. `landingPathFor()`가 이미 착지 경로의 단일 출처라 이 함수 하나만 고치면 콜백과 가드가 함께 따라온다.

### 3. 설치 상태 판정은 훅 하나, 상태는 우선순위가 있는 여섯 가지

```
useInstallState() → 'installed' | 'in-app' | 'desktop' | 'installable' | 'ios' | 'android'

installed     display-mode: standalone (또는 iOS navigator.standalone)  → 설치 UI 숨김
in-app        카카오톡 등 웹뷰                                           → 브라우저로 열기 안내
desktop       모바일이 아님                                              → QR
installable   beforeinstallprompt를 잡았다                               → 설치 프롬프트
ios           iOS인데 프롬프트가 없다(항상 그렇다)                        → 공유 → 홈 화면에 추가
android       안드로이드인데 프롬프트가 없다(소비했거나 미지원 브라우저)   → 메뉴 안내
```

**판정 순서가 곧 설계다.**

- `installed`가 가장 먼저다 — 참고한 구현은 설치 판정이 훅·랜딩·모달 세 곳에 흩어져 있었고, 그중 모달에만 standalone 검사가 빠져 **이미 설치한 사용자에게도 "홈 화면에 추가하세요"가 뜬다.** 판정을 한 곳에서 하고 UI는 결과만 받으면 이런 누락이 구조적으로 생기지 않는다.
- `desktop`이 `installable`보다 앞선다 — 데스크톱 크롬도 `beforeinstallprompt`를 쏘지만, 사진으로 기록하는 앱이라 데스크톱 설치는 의미가 없다. 프롬프트가 와도 QR을 유지한다.
- `android`가 따로 있어야 한다 — 프롬프트는 **한 번 쓰면 재사용할 수 없다.** 사용자가 설치를 거절하면 되돌아갈 자리가 필요하고, 그 자리가 `desktop`이면 안드로이드 사용자에게 QR을 보여주게 된다.
- `in-app`이 플랫폼보다 앞선다 — **앱 안에 박힌 웹뷰에서는 홈 화면 추가가 막히거나 망가진다.** 그런데 우리가 링크를 뿌릴 가장 유력한 경로가 카카오톡이다. 감지하지 못하면 카톡으로 받은 사람은 iOS 안내를 그대로 따라 해도 실패한다 — 안내가 틀린 게 아니라 그 자리에서 불가능한 것이라, 다른 말을 해야 한다.

iPadOS 13+는 UA가 `Macintosh`로 나오므로 `navigator.maxTouchPoints > 1`로 구분한다. 이게 없으면 아이패드 사용자가 데스크톱 안내(QR)를 보게 된다.

### 4. iOS 안내에서 브라우저를 제한하지 않는다

**iOS 16.4부터 Chrome·Edge·Firefox에서도 홈 화면 추가가 된다.** "반드시 Safari로 여세요" 같은 안내는 크롬 사용자를 그냥 돌려보낸다. 안내는 브라우저 이름 대신 **공유 버튼 → 홈 화면에 추가**라는 동작만 가리킨다.

### 5. 의존성을 추가하지 않는다

현재 프론트 런타임 의존성은 `react`, `react-dom`, `react-router`, `@tanstack/react-query`, `tailwindcss`가 전부다. 랜딩 하나 때문에 애니메이션·아이콘·QR 라이브러리 세 개를 들이지 않는다.

- 아이콘 → 인라인 SVG
- QR → 정적 이미지를 `public/`에 넣는다 (주소가 `kcalog.site` 고정이라 런타임 생성이 필요 없다)
- 애니메이션 → CSS transition

### 6. 화면 구성

`frontend/DESIGN.md`의 면 3층 구조·라운드 3단계·색 토큰을 그대로 쓴다. 랜딩만 다른 디자인 언어를 쓰면 설치 후 앱에 들어갔을 때 다른 서비스처럼 보인다.

```
헤더        로고 + [설치 방법]  (fixed, 히어로 위에서는 투명·흰 글씨 → 스크롤하면 밝은 면)
히어로      화면을 꽉 채우는 어두운 면 (min-h-dvh) · 가치 제안 | 눕힌 앱 화면
사용 흐름   찍기 → AI가 읽기 → 확인하고 저장
기능        3장 (첫 장이 가로로 넓은 비대칭 배치)
설치 안내   기기별 + 눌러야 할 곳을 가리키는 그림 (앵커 #install)
FAQ         무료 / 스토어에 없는 이유 / 사진 저장 / 정확도 / 로그인
푸터        어두운 면 · 서비스 한 줄 + 1인 개발이라는 사실
```

**구획마다 배경을 전폭으로 깐다.** 가운데 정렬된 기둥 하나로 죽 내려가면 문서처럼 보인다. `canvas`(밝음) → `track`(눌린 면) → `ink`(어두움)를 번갈아 써서 스크롤에 리듬을 준다.

히어로가 `bg-ink`(#0f172a)인 것은 우연이 아니다 — 이미 토큰에 있는 값이라 새 색을 만들지 않고도 어두운 면을 얻는다. 그 위의 글씨는 `text-on-brand`(흰색)와 `text-canvas/70`처럼 **기존 토큰에 투명도만 얹어** 쓴다. 다크용 색을 새로 정의하면 `tokens.ts`의 대비 검증 목록까지 따라 늘어난다.

**히어로에 앱 화면을 둔다.** 참고한 세 서비스가 모두 그렇게 하고, 기능 설명 카드 세 장보다 화면 하나가 세다.

**FAQ는 장식이 아니다.** 숫자로 만들 신뢰가 없으니 의심을 직접 푼다. 특히 "앱스토어에 없나요?"는 스토어 없는 설치를 처음 보는 사람이 반드시 하는 질문이다.

**이 화면만 반응형이다.** 앱(5탭 셸)은 `max-w-md`로 폰 너비를 고정하지만, 랜딩은 데스크톱에서 링크를 받아 서비스를 훑어보는 것이 본업이라 `max-w-6xl`에 `sm:`·`lg:` 그리드를 쓴다. 폰 너비 기둥 하나로 데스크톱에 뜨면 소개 페이지 구실을 못 한다.

분량은 처음에 확정하지 않았다 — 사용자가 "차차 생각"으로 미룬 부분이라 최소 구성으로 만든 뒤 실물을 보고 사용 흐름·헤더·푸터를 더했다. 스펙은 **무엇이 전달되어야 하는지**만 규정하고 섹션 수는 구현에서 정한다.

### 7. 스크린샷 대신 앱 컴포넌트를 그대로 렌더한다

히어로의 폰 프레임 안은 캡처 이미지가 아니라 **앱이 실제로 쓰는 컴포넌트**(`CalorieRing`·`MacroProgress`·`Card`)를 가짜 값으로 렌더한 것이다.

- 화면을 고치면 미리보기도 따라온다 — 캡처처럼 낡지 않는다
- 이미지 자산과 그 크기·`loading` 관리가 사라진다
- 데이터를 채우고 캡처하는 사람 손이 필요 없다

대가는 프레임 안을 만드는 코드가 늘어난다는 것과, 앱 화면 전부가 아니라 홈 상단만 보여준다는 것이다. 아래를 그라디언트로 흐리게 잘라 "이어진다"는 신호를 준다.

이 컴포넌트들이 **표시용 props만 받는 순수 컴포넌트**라서 가능한 선택이다 — 쿼리나 인증 컨텍스트를 물고 있었다면 랜딩에서 재사용할 수 없었다.

### 8. 움직임은 CSS와 IntersectionObserver로만 만든다

랜딩에 연출을 넣기로 했지만 `framer-motion`을 들이지 않는다(결정 5의 연장). 참고한 구현이 쓰는 것들은 전부 대체된다.

| 참고 구현 | 여기서는 |
| --- | --- |
| `motion.div` scale/opacity 루프 | `@keyframes drift` + `.animate-drift` |
| `useInView` + variants | `IntersectionObserver` + Tailwind 전환 클래스 (`Reveal`) |
| 3D 마우스 패럴랙스 | `transform: perspective() rotateY()` + hover 전환 |

**구현 이탈 — `lenis`는 예외로 들였다.** 스크롤에 관성을 주는 연출(휠을 굴리면 목표까지 감속하며 미끄러지는 느낌)은 **CSS로 대체할 수 없다.** `scroll-behavior: smooth`는 앵커 점프만 다루고, 휠 입력을 가로채 보간하는 일은 자바스크립트만 가능하다. framer-motion(50KB, CSS로 대체 가능)과 달리 이건 5KB(gzip)이고 대체 수단이 없어서 받아들였다.

다만 **랜딩에서만 걸고**(앱은 목록을 훑고 시트를 여닫는 화면이라 스크롤을 가로채면 조작이 굼떠진다), **터치 기기에서는 걸지 않으며**(브라우저 관성 스크롤이 이미 좋다), **동적 import로 분리**해 랜딩을 볼 일 없는 앱 사용자는 내려받지 않는다.

**`Reveal`의 기본값은 "보임"이다.** 움직임을 줄여달라는 설정이거나 `IntersectionObserver`가 없으면 연출을 아예 걸지 않는다. 숨긴 채로 시작했다가 관찰자가 동작하지 않으면 **콘텐츠가 영원히 안 보이고**, 그건 연출이 없는 것보다 훨씬 나쁘다.

목록 안에서는 `as="li"`로 렌더한다 — `ol`/`ul` 바로 아래에 `div`가 끼면 목록 구조가 깨져 스크린리더가 항목 수를 읽지 못한다.

## Risks / Trade-offs

- **기존 설치본이 랜딩으로 열린다.** `start_url`이 바뀌어도 이미 만들어진 홈 화면 바로가기는 갱신이 보장되지 않는다(특히 iOS). 지우고 다시 추가해야 한다. 현재 사용자가 개발자 본인뿐이라 수용한다.
- **iOS standalone에서의 카카오 로그인 — 확인 완료.** 홈 화면 실행 상태에서 외부 사이트로 나갔다 돌아오면 세션이 유지되지 않는 사례가 있어, 랜딩이 설치를 1순위 동선으로 만들기 전에 먼저 확인했다. 실기기에서 로그인 후 앱을 완전히 종료했다 다시 열어도 세션이 유지된다(`add-deployment` 6.4도 이로써 닫힘). 이 change의 전제가 성립한다.
- **딥링크 주소가 바뀐다.** `/weight` → `/app/weight`. 외부에 공유된 링크가 아직 없어 지금이 바꾸기 가장 싼 시점이다.
- **데스크톱에서 랜딩으로 온 사람은 들어갈 길이 없다.** 설치 유도만 두기로 했으므로 QR로 폰에 넘기는 것이 유일한 경로다. 주소로 `/app`을 직접 치면 동작한다. 나중에 "브라우저로 둘러보기" 링크를 추가하면 되돌릴 수 있다.
- **인앱 브라우저 감지는 UA 문자열에 기댄다.** 앱이 UA를 바꾸면 감지에서 새고, 그러면 그 사용자는 따라 해도 안 되는 안내를 보게 된다. 완전한 해결책은 없다 — 알려진 웹뷰(카카오톡·인스타그램·페이스북·네이버·라인) 위주로 잡고, 안내에 "다른 브라우저로 열기"를 항상 남겨 둔다.
- **미리보기가 앱 화면 전부는 아니다.** 홈 상단만 보여주므로 음식기록·리포트·AI PT 화면은 글로만 설명된다.

## Migration Plan

기존 라우트에서 새 라우트로 옮기는 것뿐이라 데이터 이동은 없다. 순서는 라우트 재편 → 착지 경로 수정 → 내부 링크 수정 → manifest → 랜딩 화면. 라우트를 먼저 옮기면 내부 링크가 깨진 상태가 되므로 같은 PR에서 함께 처리한다.
