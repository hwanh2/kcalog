# 설계: 재분석에 직전 맥락을 넘긴다

## D1. 직전 결과는 지우지 않고 옮긴다

`reanalyze`가 `resultJson`을 null로 만들던 것을 `previousResultJson`으로 옮기는 것으로 바꾼다.

```java
this.previousResultJson = this.resultJson;
this.resultJson = null;
```

`resultJson`을 비우는 것 자체는 유지한다. 상태가 ANALYZING인데 결과가 남아 있으면 폴링하는 화면이 낡은 값을 새 결과로 착각할 수 있다.

별도 컬럼을 두는 이유는 "지금 결과"와 "직전 결과"가 서로 다른 것이기 때문이다. 한 컬럼을 상태로 구분하면 워커와 화면이 같은 값을 다르게 읽는다.

## D2. 설명은 최초와 이후를 나눠 담는다

기존 `note` 컬럼은 **최초 설명**으로 뜻을 좁히고, 재분석 때 덧붙인 것은 새 컬럼 `reanalysis_notes`에 JSON 배열로 쌓는다.

`note`를 이력으로 바꾸지 않는 이유가 둘이다.

- 이미 쌓인 데이터가 그대로 유효하다. 마이그레이션이 컬럼 추가 하나로 끝난다.
- 배포를 되돌려도 옛 코드가 `note`를 그대로 읽는다. 컬럼의 뜻을 바꿔버리면 롤백 시 최초 설명 자리에 이력 JSON이 들어앉는다.

줄바꿈으로 이어 붙이지 않고 JSON 배열을 쓴다. 사용자가 설명에 줄바꿈을 넣으면 구분자가 깨진다.

재분석은 작업당 2회라 설명은 많아야 셋이다(최초 1 + 재분석 2).

## D3. 직전 추정은 JSON이 아니라 목록으로 넘긴다

저장된 `previousResultJson`을 그대로 프롬프트에 넣지 않고, 항목별 한 줄로 풀어 쓴다.

```
직전 추정(이 값을 기준으로 사용자 설명을 반영해 고치세요. 언급되지 않은 항목은 그대로 두세요):
- 흰쌀밥 210g: 300kcal, 탄 66g, 단 5g, 지 1g
- 김치찌개 1인분: 400kcal, 탄 12g, 단 20g, 지 28g
```

JSON을 그대로 주면 위치 박스와 내부 플래그(`corrected`)까지 딸려 간다. 모델이 고쳐야 할 것은 이름과 양과 영양값이지 좌표가 아니다.

**"언급되지 않은 항목은 그대로 두세요"가 핵심이다.** 이 문장이 없으면 밥 이야기를 했는데 국의 값까지 바뀌어, 회차를 거듭할수록 사용자가 손대지 않은 항목이 흔들린다.

## D4. 맥락은 재분석에만 붙인다

최초 분석에는 직전 추정이 없고 설명도 하나뿐이라 지금과 같다. 프롬프트가 달라지는 것은 재분석 회차부터다.

`eval/` 평가 세트는 최초 분석을 재는 것이라 이 변경에 영향받지 않는다.

## D5. 개인 보정 이력과 순서를 정한다

프롬프트에 들어가는 참고 자료가 셋이 된다. 순서는 이렇게 둔다.

1. 개인 보정 이력 (이 사용자가 과거에 정정한 값)
2. 직전 추정 (이번 작업의 직전 회차)
3. 사용자 설명 (최초 + 덧붙인 것 전부)

뒤에 올수록 이번 요청에 가깝다. 충돌하면 사용자가 방금 한 말이 이겨야 하므로 설명을 맨 뒤에 둔다.

## D6. 설명이 비어도 재분석은 가능하다

지금 `ReanalyzeRequest`는 `@NotBlank`라 설명 없이 재분석할 수 없다. 이 제약은 그대로 둔다.

직전 추정만 넘기고 "다시 봐줘"라고 하는 것도 말이 되지만, 그러면 같은 입력으로 같은 호출을 반복하는 셈이라 횟수만 깎인다. 무엇을 고쳐야 하는지 사용자가 한마디는 해야 한다.
