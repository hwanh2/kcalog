## Context

add-meal-weight-tracking로 총량 기반 식사 기록(사진→총 칼로리·탄단지→저장)이 동작한다. 이 change는 사용자 요청에 따라 **음식별 분석 + 사진 위 좌표 오버레이 + 음식별 저장**으로 확장한다.

현재 상태:
- 백엔드: `meal`(사진 단위 총량, meal_item 없음), `POST/GET/PATCH/DELETE /api/meals`, `POST /api/meals/analyze`(총량 반환). 분석은 `MealAnalysisPrompt`/`MealAnalysisService`/`OpenAiClient`.
- 프론트: `MealRecordPage`(총량 확인·수정), `RecordsPage`(총량 목록), `features/meal/`.
- 사진은 저장하지 않는 방침 유지.

## Goals / Non-Goals

**Goals:**
- 음식별 분석: 항목(이름·칼로리·탄단지·위치 박스) 배열 + 합계
- 촬영 세션에서 사진 위에 박스+라벨 오버레이 (사진·박스 미저장)
- 좌표 부정확 시 목록형 자동 폴백
- 음식별 수정·추가·삭제, 합계 자동 재계산
- meal_item 저장, meal 합계 재계산, 음식별 조회
- eval로 음식별·좌표 정확도 초기 실측

**Non-Goals:**
- 사진 영구 저장(스토리지), 기록 탭에서 사진+박스 재열람
- 음식 DB 검색·바코드
- 대화형 코치, 주간 리포트

## Decisions

### D1. 분석 출력: 음식별 항목 + 합계 + 위치 박스
구조화 출력 스키마를 재설계한다:
```
{ foodFound, items: [{ name, kcal, carbG, proteinG, fatG, box: {x,y,w,h} }],
  overallConfidence, notes }
```
- `box`는 이미지 정규화 좌표(0~1). 오버레이 렌더링 전용이며 **저장하지 않는다**.
- 합계는 서버·클라이언트 어디서든 items 합으로 계산(별도 total 필드는 두지 않고 파생). 저장 시 meal.total_*에 합계를 비정규화.
- `foodFound=false`면 items 빈 배열 + notes(수동 입력 유도).

### D2. 확인 화면 인터랙션 — 오버레이-편집 하이브리드 (개정 2026-08-09)
> **개정 배경**: 초판은 "오버레이=보기 전용, 편집=아래 목록"이었다. 사용자 요청으로 **오버레이를 편집 주체로 승격**(박스 탭→그 자리서 확대 편집)하고 하단은 총량 위주로 바꾼다. 경쟁 서비스(SnapCalorie·Cal AI·Foodvisor) 조사 결과 리더들은 대부분 "사진+항목 리스트+상단 총량" 리스트형을 쓰고 박스 편집은 소수파였다 — 박스에 UX를 통째로 거는 건 아래 두 구조적 제약 때문에 위험. 그래서 **하이브리드**(박스 좋을 때만 오버레이-편집, 아니면 리스트 폴백)로 절충한다.

비전 모델은 음식 인식은 잘 하나 위치는 부정확하다(박스가 어긋나거나 누락). 확인 화면은 박스 품질에 따라 두 모드로 나뉘고, 편집·저장 로직은 공유한다:

- **오버레이-편집 모드** — `shouldOverlay`(모든 item에 유효 box + `overallConfidence` 임계 이상)일 때:
  - 사진 위 각 박스에 라벨(이름 + 탄·단·지 요약) 표시
  - **박스 탭 → 그 항목이 팝오버/바텀시트로 확대되어 이름·kcal·탄단지 편집·삭제**
  - 하단: **총량(총 kcal + 탄단지)** + 좌표 없는 항목 영역(아래 구조적 제약 참고)
- **리스트 폴백 모드** — 그 외:
  - 사진은 썸네일로 위에 두고, 아래 항목 카드 리스트에서 편집(현행 그룹 3 UI)

**구조적 제약 2가지** — "박스=유일한 편집 UI"로 못 가는 이유, 하이브리드가 이를 흡수한다:
1. **좌표 없는 항목**: 사용자가 "+추가"한 항목·AI가 box를 못 준 항목·수동 입력은 사진에 놓을 좌표가 없다. → 하단에 **"위치 없는 항목" 칩 영역**을 두어 여기서 편집·추가. 목록을 완전히 없애지 않는 이유.
2. **박스 품질 저하**: 박스가 겹치거나 어긋나면 탭 편집이 더 답답하다. → `shouldOverlay` 판정으로 나쁜 날엔 통째로 리스트 폴백.

두 모드 전환은 `shouldOverlay` 플래그(임계값 상수)로 제어하며, eval(D6) 실측이 나쁘면 오버레이를 기본에서 내리고 리스트를 기본으로 둔다. **기록 탭은 사진이 없으므로(미저장) 항상 리스트 편집** — 오버레이-편집은 확인 화면 전용.

### D3. meal_item 저장 — 애그리거트 내 객체 참조
`meal`(애그리거트 루트) ↔ `meal_item`(1:N)은 **애그리거트 내부**라 객체 참조(`@OneToMany`, cascade, orphanRemoval)로 매핑한다. (member↔meal 같은 애그리거트 간 참조는 지금처럼 ID 참조 유지.)
- `meal_item(id, meal_id, name, kcal, carb_g, protein_g, fat_g)`. 위치 박스 컬럼 없음(미저장).
- 저장·수정 시 items로 meal_item을 교체하고 meal.total_*를 합계로 재계산(서비스 계층 규칙).
- Flyway `V6__meal_item.sql`, meal FK CASCADE.

### D4. 저장 API — items 수용, 합계 파생
- `POST /api/meals`: `{ eatenAt, mealType, source, items: [{name,kcal,carbG,proteinG,fatG}] }`. 서버가 합계를 계산해 meal에 저장, items를 meal_item으로 저장.
- `PATCH /api/meals/{id}`: items 전체 교체(간명). 부분 항목 수정도 클라이언트가 전체 items로 보낸다.
- `GET /api/meals?date=`: 각 meal에 items 포함.
- 하위호환: source=MANUAL로 items 하나(직접 입력)도 동일 경로.

### D5. 프론트 확인 화면 — 오버레이-편집으로 개정 (2026-08-09)
그룹 3에서 "사진+리스트 편집"을 이미 구현했다. 이 개정은 그 위에 **오버레이-편집 모드**를 얹는 후속 작업(그룹 6):
- 오버레이 모드: 박스 라벨에 이름 + 탄·단·지 요약, **박스 탭 → 확대 편집 팝오버/바텀시트**(이름·kcal·탄단지·삭제)
- 하단: 총량 표시 + **"위치 없는 항목" 칩 영역**(box 없는 항목 편집·추가) — D2 제약 1 해소
- 리스트 폴백 모드: 현행 `MealItemsEditor` 그대로 재사용
- 편집·검증·저장 로직(`mealItems.ts`·`validateItems`·`toSaveItems`)은 두 모드 공유, 표현만 분기
- 저장 → items로 `POST /api/meals` (기존 배선 유지)

`PhotoOverlay`를 표시 전용 → 탭 가능한 편집 진입점으로 확장하고, `MealRecordPage`가 오버레이/리스트 + 위치 없는 항목 칩을 조합한다.

### D6. eval 확장
`eval/` 채점에 음식별 지표 추가: 항목 개수 정확도, 이름 매칭, 항목별 영양 오차, **박스 IoU/위치 정확도**. 초기 실측으로 오버레이 실효성을 판단(D2 플래그 결정 근거).

### D7. 향후 인식 고도화 옵션 — 백로그 (조사 2026-08-09)
현재 정확도 지형(연구 종합): 사람 눈대중 40~53%, 범용 비전 LLM(현재) ~35% MAPE, depth 결합(SnapCalorie) ~15%. **칼로리 오차의 진짜 병목은 인식이 아니라 양(부피)** — 2D 사진 한계라 depth가 최대 레버.

MVP는 비전 LLM 유지. eval(D6)에서 박스/항목 정확도가 나쁘다고 나오면 아래를 **이 순서로** 검토(지금 도입 안 함):
1. **상용 음식 인식 SDK/API** — Passio(온디바이스, iOS/Android/RN SDK), LogMeal·Calorie Mama(REST). 직접 학습·호스팅 없이 박스+영양 획득. 1순위.
2. **직접 파인튜닝** (학습 목적일 때) — AI Hub 한식 데이터셋(150종 세그먼트 태깅 / 400종 84만장+영양 / 500종), Nutrition5k(depth). 모델은 YOLOv8(연구상 v7·v9 대비 우위). 별도 추론 인프라(파이썬/ONNX·DJL) 필요.
3. **Depth/부피** — 칼로리 정확도 핵심이나 LIDAR 하드웨어 의존 → 훨씬 나중·선택.
- OCR은 플레이팅 음식엔 무용, 포장식품 라벨/바코드라는 **별도 트랙**으로만 의미.

## Risks / Trade-offs

- [비전 모델 위치 좌표 부정확 → 오버레이 어긋남] → D2 리스트 폴백 + eval 초기 검증. 최악의 경우 리스트 기본.
- [오버레이-편집이 박스 정밀도에 UX를 크게 의존] → D2 하이브리드(박스 좋을 때만) + 위치 없는 항목 칩. 경쟁사 다수가 리스트형인 이유이므로 eval로 오버레이 유지 여부를 실측 판단.
- [항목 분해로 총 영양 오차가 더 벌어질 수 있음(항목마다 오차 누적)] → 사용자 확인·수정이 안전장치. eval로 총량 대비 오차 비교.
- [사진 미저장이라 기록 탭에서 오버레이 재열람 불가] → 1차 수용. 음식별 목록으로만 재조회.
- [meal_item 도입으로 기존 총량 스키마·API 변경] → 미배포 상태라 V6 additive + API 확장으로 흡수. 총량만 저장된 기존 로컬 데이터는 items 없는 meal로 조회(빈 items 허용).

## Migration Plan

- Flyway `V6__meal_item.sql` additive. meal 테이블은 유지(total_* 그대로, 이제 items 합계).
- 분석 스키마 변경은 배포 전이라 자유. API 변경은 프론트와 함께 배포.
- 롤백: 미배포라 마이그레이션 수정 가능(머지 후 V7+).

## Open Questions

- overallConfidence 임계값 — eval 실측 후 확정.
- PATCH를 items 전체 교체로 할지 항목 단위로 할지 — 전체 교체로 시작(간명), 필요 시 세분화. ✅ 전체 교체로 확정(구현됨).
- 확인 화면 인터랙션(오버레이-편집 vs 리스트) — ✅ 하이브리드로 확정(D2 개정, 그룹 6에서 구현).
- 오버레이 편집 UI 형태(팝오버 vs 바텀시트) — 구현 시 확정(모바일 우선이면 바텀시트 유력).
