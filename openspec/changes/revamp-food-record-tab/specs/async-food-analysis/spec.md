# async-food-analysis (delta)

## MODIFIED Requirements

### Requirement: 비동기 분석 작업 생성
시스템은 **사진과 설명(프롬프트)** 을 입력으로 받아 분석 작업을 만들고 **즉시 작업 식별자를 반환**해야 한다(SHALL). 사진과 설명은 각각 선택 입력이며, **최소 하나는 있어야 한다**(MUST — 둘 다 없으면 400). 끼니 구분은 확인 저장 시점(`POST /api/meals`)에 정한다. 사진이 있으면 스토리지에 저장하고(MUST), 실제 AI 분석은 백그라운드에서 수행해야 한다(MUST). 작업 생성 시점에 어떤 식사 기록(meal)도 만들지 않아야 한다(MUST NOT — meal은 확인 저장 시에만 생성).

설명은 분석 프롬프트에 함께 제공해 사진에 보이지 않는 정보(조리법·섭취량·제외한 재료)를 반영해야 한다(MUST). 사진이 없는 작업은 위치 박스 없이 항목만 분석해야 한다(MUST).

#### Scenario: 사진으로 작업 생성
- **WHEN** 로그인한 회원이 음식 사진으로 `POST /api/analyses`를 호출하면
- **THEN** 사진이 저장되고 ANALYZING 상태의 작업이 만들어지며 작업 id가 즉시 반환된다(분석 완료를 기다리지 않는다)

#### Scenario: 사진과 설명을 함께
- **WHEN** 회원이 사진과 "드레싱은 절반만 뿌렸어요"를 함께 제출하면
- **THEN** 설명이 작업에 저장되고 분석 프롬프트에 반영된다

#### Scenario: 설명만으로 작업 생성
- **WHEN** 회원이 사진 없이 "김밥 한 줄이랑 라면 반 개"만 제출하면
- **THEN** 사진 없이 작업이 만들어지고, 위치 박스 없는 음식 항목이 분석된다

#### Scenario: 입력 없음
- **WHEN** 회원이 사진도 설명도 없이 호출하면
- **THEN** 400을 반환하고 작업을 만들지 않는다

#### Scenario: 백그라운드 분석
- **WHEN** 작업이 생성되면
- **THEN** 백그라운드에서 AI 분석이 수행되고, 완료 시 결과(음식별 항목·신뢰도)가 작업에 기록된다

### Requirement: 분석 상태·결과 폴링
시스템은 작업의 현재 상태와 완료 결과를 조회하는 엔드포인트를 제공해야 한다(SHALL). 상태는 ANALYZING / COMPLETED / FAILED / NO_FOOD 중 하나여야 하며(MUST), 완료 시 음식별 항목·전체 신뢰도·비고를 포함해야 한다(MUST). 사진이 있는 작업은 사진 참조를 포함해야 하고(MUST), **사진 없는 작업은 사진 참조가 비어 있어야 한다**(MUST). 다른 회원의 작업에는 접근할 수 없어야 한다(MUST).

#### Scenario: 진행 중 조회
- **WHEN** 회원이 `GET /api/analyses/{id}`를 분석 완료 전에 호출하면
- **THEN** ANALYZING 상태를 반환한다

#### Scenario: 완료 결과 조회
- **WHEN** 분석이 완료된 뒤 조회하면
- **THEN** COMPLETED 상태와 음식별 항목·신뢰도를 반환하며, 사진이 있으면 사진 참조를 함께 반환한다

#### Scenario: 사진 없는 작업 조회
- **WHEN** 설명만으로 만든 작업을 조회하면
- **THEN** 사진 참조 없이 결과가 반환되고, 프론트는 목록형으로 표시한다

#### Scenario: 음식 미검출
- **WHEN** 음식이 식별되지 않으면
- **THEN** NO_FOOD 상태와 안내를 반환하고 오류로 처리하지 않는다

#### Scenario: 분석 실패
- **WHEN** AI 호출이 타임아웃·파싱 실패로 재시도 후에도 실패하면
- **THEN** FAILED 상태를 반환해 프론트가 재시도·수동 입력으로 폴백할 수 있게 한다

#### Scenario: 타인 작업 접근 차단
- **WHEN** 회원이 다른 회원의 작업을 조회하면
- **THEN** 접근이 거부된다(404)

### Requirement: 일일 분석 횟수 제한
시스템은 회원당 하루 분석 작업 생성 횟수를 설정된 상한으로 제한해야 한다(SHALL). 상한을 초과하면 작업을 만들지 않고 429와 안내를 반환해야 한다(MUST). 동시 요청에서도 상한을 정확히 지켜야 한다(MUST). **사진 분석·설명 분석·재분석은 같은 카운터를 공유해야 한다**(MUST). 카운터의 하루는 달력 날짜 기준이어야 한다(MUST — 서비스 하루 경계를 적용하지 않는다).

#### Scenario: 상한 초과
- **WHEN** 회원이 당일 상한을 초과해 `POST /api/analyses`를 호출하면
- **THEN** 429와 "오늘 분석 가능 횟수를 초과했어요" 안내를 반환하고 AI를 호출하지 않으며 작업을 만들지 않는다

#### Scenario: 설명 분석도 차감
- **WHEN** 회원이 사진 없이 설명만으로 분석하면
- **THEN** 같은 일일 카운터가 1 차감된다

### Requirement: 미확인 작업 정리
시스템은 확인 저장되지 않은 분석 작업을 보존 기간 후 정리해야 한다(SHALL). 정리 시 작업과 연결된 사진을 함께 삭제해야 한다(MUST). 사진이 없는 작업은 작업 행만 삭제해야 한다(MUST).

#### Scenario: 미확인 작업 만료
- **WHEN** 확인 저장되지 않은 작업이 보존 기간을 넘기면
- **THEN** 주기적 정리가 그 작업과 사진을 삭제한다

#### Scenario: 사진 없는 작업 만료
- **WHEN** 설명만으로 만든 작업이 보존 기간을 넘기면
- **THEN** 작업 행만 삭제되고 스토리지 접근은 발생하지 않는다

## ADDED Requirements

### Requirement: 설명을 덧붙인 재분석
시스템은 완료된 분석 작업에 설명을 덧붙여 다시 분석할 수 있게 해야 한다(SHALL). 재분석은 **기존 작업을 갱신**해야 하며(MUST — 새 작업을 만들지 않는다), 사진이 있으면 저장된 사진을 재사용해야 한다(MUST — 재업로드하지 않는다). 재분석 횟수는 작업당 **최대 2회**로 제한해야 하고(MUST), 각 회차는 일일 분석 횟수를 차감해야 한다(MUST). 사진 없는 작업도 재분석할 수 있어야 한다(SHALL).

#### Scenario: 설명으로 결과 보정
- **WHEN** 회원이 완료된 작업에 "드레싱은 절반만 뿌렸어요"를 덧붙여 재분석하면
- **THEN** 같은 작업이 ANALYZING으로 되돌아가고, 새 결과가 기존 결과를 대체한다

#### Scenario: 사진 재사용
- **WHEN** 사진이 있는 작업을 재분석하면
- **THEN** 저장된 사진을 그대로 사용하며 사진을 다시 올리지 않는다

#### Scenario: 재분석 상한
- **WHEN** 이미 2회 재분석한 작업을 다시 재분석하려 하면
- **THEN** 거부되고 안내를 반환한다

#### Scenario: 재분석도 횟수 차감
- **WHEN** 회원이 재분석을 요청하면
- **THEN** 일일 분석 횟수가 1 차감되며, 상한을 넘으면 429를 반환하고 재분석하지 않는다

#### Scenario: 타인 작업 재분석 차단
- **WHEN** 회원이 다른 회원의 작업을 재분석하려 하면
- **THEN** 접근이 거부된다(404)
