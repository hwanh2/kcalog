# 설계

## D1. 스팟라이트는 구멍이 아니라 그림자다

타겟 자리에 빈 div를 놓고 화면보다 큰 그림자를 준다.

```
shadow-[0_0_0_9999px_rgba(0,0,0,0.6)]
```

`clip-path`나 SVG 마스크로 진짜 구멍을 뚫는 방법도 있으나, 사각형 하나로 끝나는 일에 두 배로 복잡하다. 그림자는 `border-radius`를 따라오므로 라운드도 공짜로 맞는다(D6).

**부작용은 타겟을 누를 수 없다는 것이다.** 그림자는 부모의 `fixed inset-0` 안에 있어서, 타겟 위에도 막이 덮인다. 이것은 결함이 아니라 이 튜토리얼이 원하는 동작이다. 회원이 탄단지 카드를 눌러 다른 화면으로 새면 안내가 끊긴다. 진행은 말풍선의 버튼으로만 한다.

참고한 구현(스톡잇)은 이 때문에 `action: 'click'`을 두어 다음 버튼이 대신 타겟을 눌러준다. 여기서는 라우트 전환 한 번뿐이라 `navigate()`로 직접 옮긴다(D7).

## D2. 타겟은 DOM id 문자열로 느슨하게 잇는다

스텝 배열이 `targetId: 'tutorial-calorie'`를 들고, 화면 쪽은 `id`만 박는다. ref를 스텝 배열까지 끌어오려면 홈, 셸, 기록 화면이 모두 튜토리얼을 알아야 한다.

**대가는 오타가 조용하다는 것이다.** 못 찾으면 스팟라이트 없이 말풍선만 뜬다. 그래서 id 상수를 `steps.ts` 한 곳에 모아 `export const TUTORIAL_IDS`로 두고, 화면 쪽에서도 그 상수를 쓴다. 문자열을 양쪽에 손으로 적지 않는다.

## D3. 위치는 프레임마다 다시 잰다

타겟 사각형이 바뀌는 경우가 넷이다.

- 스텝이 바뀔 때
- 타겟을 화면 가운데로 데려오는 스크롤이 도는 동안 (부드럽게 움직여서 여러 프레임에 걸친다)
- 회원이 직접 스크롤하거나 화면을 돌릴 때
- 라우트가 바뀌어 타겟이 **아직 없다가 나타날 때** (홈에서 음식기록으로)

`scroll`, `resize` 리스너에 MutationObserver까지 붙이면 네 가지를 각각 막게 된다. 대신 `requestAnimationFrame` 한 줄로 전부 덮는다.

```
매 프레임: getElementById -> getBoundingClientRect -> 이전과 다르면 setState
```

**값이 같으면 setState를 하지 않아서** 실제 리렌더는 움직일 때만 일어난다. 튜토리얼이 열려 있는 동안만 도는 루프이고, 프레임당 비용은 `getBoundingClientRect` 하나다.

MutationObserver를 `document.body` 전체에 `subtree: true`로 거는 쪽이 오히려 비싸다. 튜토리얼과 무관한 DOM 변경마다 콜백이 돈다.

## D4. 배경 스크롤을 잠그지 않는다

`useDialog`는 열려 있는 동안 `body`의 `overflow`를 `hidden`으로 만든다. 그대로 쓰면 **화면 밖에 있는 타겟을 데려올 수 없다.** 홈에서 체중 미니 카드는 390px 화면의 첫 화면 아래에 있다.

그래서 `useDialog(onClose, { lockScroll: false })`로 옵션을 하나 늘리고, 튜토리얼만 잠금을 끈다. Esc, 포커스 이동, 포커스 가둠, 포커스 복귀는 그대로 쓴다. 오버레이가 껍데기를 직접 만들면 그중 몇 개를 빠뜨린다(`frontend/DESIGN.md` 7절).

스텝이 바뀔 때 `scrollIntoView({ block: 'center' })`로 타겟을 가운데로 옮긴다. `prefers-reduced-motion`이면 `behavior: 'auto'`로 즉시 옮긴다.

## D5. 말풍선은 아래에 붙여두고 겹칠 때만 넘긴다

참고한 구현은 말풍선을 타겟 바로 옆에 붙여 따라다니게 한다. 여기서는 **화면 아래에 붙여둔다.**

스텝마다 자리가 옮겨 다니면 다음 버튼을 누르려고 엄지를 매번 다시 옮겨야 한다. 여섯 번을 누르는 동안 버튼이 여섯 번 움직인다. 어디를 가리키는지는 스팟라이트가 이미 말하고 있어서 말풍선까지 따라다닐 이유가 없다.

비추는 자리와 겹칠 때만 위로 넘긴다. 실제로 넘어가는 것은 코치 FAB 하나뿐이고, 나머지는 `scrollIntoView`가 대상을 화면 가운데로 데려오므로 아래가 늘 비어 있다.

겹침을 보려면 말풍선 높이가 필요하다. 그려놓고 재되 **스텝이 바뀔 때만** 잰다(설명 줄 수와 이전 버튼 유무 말고는 높이가 달라질 일이 없다). 매 렌더마다 재면 setState가 렌더를 다시 부르는 고리가 된다.

모든 스텝이 대상을 가리키므로 가운데 배치는 **대상을 못 찾았을 때의 대비책**이다. 라우트 전환 직후의 한두 프레임이나 id 오타에서 그리로 떨어진다. 그때는 스팟라이트가 없어 아래에 붙일 기준도 없다.

## D6. 스팟라이트는 대상의 라운드를 물려받는다

값을 `rounded-card`로 고정했다가 고쳤다. 원형인 FAB이 사각으로 비춰져 무엇을 가리키는지가 흐려졌다.

`getComputedStyle(el).borderRadius`를 그대로 쓴다. 한 값이 아니라 모서리별로 다른 경우도 문자열 그대로 넘기면 맞는다. 8px 넓힌 만큼 반지름도 키우는 편이 더 정확하지만, 값이 모서리별 문자열이라 파싱이 필요하고 카드에서는 눈에 띄지 않는 차이다.

## D7. 라우트 전환은 스텝이 들고 있다

스텝마다 **자기가 사는 화면의 경로**를 들고, 오버레이는 지금 경로가 그것과 다르면 옮긴다.

처음에는 다음 버튼에 `goTo`를 달았다가 바꿨다. 그러면 앞으로만 옮겨져서, 음식기록 스텝에서 이전을 누르면 안내는 홈 스텝으로 돌아가는데 화면은 음식기록에 남는다. 스텝이 경로를 들면 양쪽이 한 규칙으로 맞는다.

**`?camera=1`을 붙이지 않는다.** 그 파라미터로 들어가면 `AiRecordPanel`이 마운트되자마자 `<input capture>`를 눌러 OS 카메라를 띄운다(`AiRecordPanel.tsx:55`). 카메라가 오버레이를 덮어 튜토리얼이 거기서 끊기고, 취소하면 설명 없는 빈 화면에 남는다. 촬영은 튜토리얼이 끝난 뒤 회원이 직접 한다.

오버레이는 **`AppShell` 안에** 둔다. 홈과 음식기록이 같은 셸의 `Outlet`이라 라우트가 바뀌어도 오버레이는 마운트를 유지한다. 페이지마다 두면 그 전환에서 언마운트되며 진행 상태가 날아간다.

## D8. 완료 여부는 서버 컬럼이다

`onboardingCompleted`는 컬럼이 아니라 `dailyKcalTarget != null`로 계산하는 파생값이다(fix-macro-targets D4). 튜토리얼 완료는 파생시킬 근거가 없어 새로 만든다.

```sql
ALTER TABLE member ADD COLUMN tutorial_completed BOOLEAN NOT NULL DEFAULT FALSE;
```

localStorage에 두는 안을 검토했으나 세 가지가 걸렸다.

- 기기를 바꾸거나 브라우저 데이터를 지우면 다시 뜬다
- 온보딩을 끝낸 기기와 튜토리얼을 본 기기가 어긋난다
- 프로필의 "다시 보기"가 기기별로 따로 논다

기존 회원은 전부 `FALSE`다. 백필하면 이미 앱을 쓰고 있던 사람이 튜토리얼을 못 본다. 반대로 두면 다음 접속에 한 번 뜨는데, 그쪽이 낫다. 이 change의 목적이 안내를 붙이는 것이다.

## D9. 열림 여부를 서버 상태에서만 판정한다

오버레이는 `member.tutorialCompleted`만 본다. "이번 세션에 이미 닫았다"는 지역 상태를 따로 두지 않는다. 두 곳에 진실이 있으면 프로필의 "다시 보기"가 지역 상태에 막힌다.

```
열림 = !member.tutorialCompleted
끝내기 = POST /api/members/me/tutorial -> reloadMember -> 플래그가 참이 되어 닫힌다
다시 보기 = DELETE -> reloadMember -> 플래그가 거짓이 되어 열린다
```

요청이 오가는 동안(약 200ms) 오버레이가 마지막 스텝을 붙들고 있으므로, 지역 `finishing`으로 즉시 감춘다. 이 값은 **플래그가 거짓으로 돌아오면 함께 풀린다.** 풀지 않으면 다시 보기를 눌러도 오버레이가 감춰진 채로 남는다.

## D10. 탭과 인사말을 뺀다

처음에는 여덟 스텝이었다. 맨 앞에 "1분만 둘러볼까요?" 인사 카드가 있었고, 중간에 하단 탭 다섯 개를 한 번에 비추는 스텝이 있었다. 둘 다 뺐다.

- **인사 카드**는 아직 아무것도 보여주지 않은 채로 다음을 한 번 더 누르게 한다. 안내를 시작하는 가장 좋은 방법은 첫 화면을 바로 가리키는 것이다.
- **하단 탭**은 이름이 그 자체로 읽힌다(홈, 음식기록, 체중, 리포트, AI PT). 읽으면 아는 것을 스텝 하나로 붙잡아 두면 나머지 스텝의 무게까지 같이 가벼워진다.

참고한 구현은 탭 4개를 4스텝으로 나눠 하나씩 비춘다. 그 반대편으로 간 셈이다.

## D11. 체중 카드가 이 튜토리얼의 이유다

체중 카드에서 말하는 것은 조작법이 아니라 **왜 매일 재야 하는지**다. 공식으로 낸 유지칼로리는 개인차가 10~15% 나고, 2주치 기록이 쌓이면 실제로 먹은 양과 체중 변화로 역산한 값으로 바뀐다(`TdeeService`). 이것이 다른 칼로리 앱과 갈리는 지점인데 지금은 앱 어디에도 그 말이 없다.

온보딩 결과 화면에도 비슷한 문구가 있지만, 그때는 앱을 본 적이 없어 무슨 말인지 모른다. 실제 체중 카드를 보면서 들어야 한다.

## D12. 완료로 치는 범위

건너뛰기도 완료로 저장한다. 건너뛴 회원에게 다음 접속에 다시 띄우면 그것은 안내가 아니라 방해다. 되돌릴 길은 프로필에 있다.

중간에 앱을 닫으면 저장되지 않아 다음 접속에 처음부터 다시 뜬다. 스텝별 진행률까지 서버에 두는 것은 여섯 스텝짜리 안내에 과하다.

## D13. 애니메이션

말풍선은 스텝이 바뀔 때 살짝 떠오른다. `PlanBuilding`이 쓰는 `animate-drop-in`과 같은 결로 `index.css`에 keyframes를 하나 더 둔다. 스팟라이트는 `transition`으로 자리를 옮긴다.

`transform`과 `opacity`만 움직이고, `prefers-reduced-motion`에서 멈춘다(`frontend/DESIGN.md` 7절).

**스팟라이트의 자리 이동은 `top`, `left`, `width`, `height`라 transform이 아니다.** 이 넷은 transform으로 대체할 수 없다(크기가 실제로 달라져야 그림자 구멍이 맞는다). 짧게(200ms) 두고 reduced-motion에서 끈다.

## D14. 테스트가 잡지 못하는 것

jsdom은 레이아웃을 계산하지 않아 `getBoundingClientRect`가 전부 0을 준다. 그래서 다음은 자동 테스트로 확인할 수 없다.

- 스팟라이트가 실제로 타겟을 감싸는지
- 말풍선이 화면 밖으로 나가지 않는지
- 위, 아래 배치가 뒤집히는 지점

자동 테스트는 **스텝 진행, 라우트 전환, 완료 저장, 건너뛰기, 다시 보기**를 본다.

배치는 헤드리스 크롬으로 확인했다. 그 과정에서 두 가지를 알았고, 다시 확인할 때 같은 데서 막히지 않도록 적어둔다.

- **`--virtual-time-budget`을 쓰면 rAF가 사실상 멈춘다.** 4초를 돌려도 프레임이 6번밖에 안 돌아, 스팟라이트가 첫 측정값에 얼어붙고 `scrollIntoView`도 움직이지 않는다. 스크린샷만 보면 위치 계산이 틀린 것처럼 보인다. CDP로 붙어 **진짜 시간으로** 기다려야 한다.
- **이 크롬은 `--window-size`를 무시한다.** 390px를 줘도 500px로 그려, 화면 밖으로 나가는지 판단할 수 없다. CDP의 `Emulation.setDeviceMetricsOverride`로 잡는다.

390x844에서 잰 값이다. 세 배치가 모두 의도대로 나온다.

```
대상                  스팟라이트            말풍선          판정
칼로리 카드            120..360            605..828        아래
탄단지 카드            334..510  (가운데)   605..828        아래
체중 카드              372..548  (스크롤)   581..829        아래
우하단 원형 FAB        708..780 (원형)      16..239         위로 넘김
기록 화면의 블록        188..460            605..828        아래
대상 없음              none                311..534        가운데
```

⚠️ **이 표는 스텝을 여섯으로 줄이기 전, 코치 FAB이 들어오기 전에 잰 것이다.** 그래도 지금 여섯 스텝이 전부 이 표의 어느 줄에 해당한다. 배치를 가르는 것은 스텝 번호가 아니라 **대상의 생김새**이기 때문이다.

- 코치 FAB은 그때 같은 자리에 있던 카메라 FAB과 클래스가 글자 그대로 같다(`fixed bottom-[calc(4.5rem+env(safe-area-inset-bottom))] right-4 h-14 w-14 rounded-full`)
- 음식기록의 사진 영역과 설명 입력은 그때 통째로 쟀던 그 블록 안에 있다

다시 재보려 했으나 vite dev의 SPA 폴백이 브라우저 내비게이션을 `index.html`로 돌려보내 검증용 페이지가 뜨지 않았다(curl로는 정상). 진입점을 바꿔 우회해도 페이지가 1.5초마다 다시 로드돼 렌더가 남지 않았다. 원인을 못 찾아 여기서 멈췄고, 남은 확인은 실기기 몫이다(tasks 8.1).
